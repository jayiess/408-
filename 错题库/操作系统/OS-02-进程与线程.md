# OS-02 进程与线程错题

## 2026-08-23｜06｜单处理器下运行态进程的数量（2.1）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | A |
| 我的选择 | C |
| 错误类型 | 概念不清 |

**原题：下列关于进程的叙述中，正确的是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 进程获得处理器运行是通过调度得到的 |
| B | 优先级是进程调度的重要依据，一旦确定就不能改动 |
| C | 在单处理器系统中，任何时刻都只有一个进程处于运行态 |
| D | 进程申请处理器而得不到满足时，其状态变为阻塞态 |

错误原因：<span style="color: red;">把 KP6 的「最多一个」记成了「只有一个」，没想到「零个」这种极端情形；而且被自己在 KP10 写的「CPU 永远不可能空转」反向误导了。</span>

复盘结论：C 错在**下界**。KP6 原文是「单 CPU 下任一时刻**最多一个**进程处于运行态」——「最多」允许 0 个，「只有」把恰好一个也钉死了。反例：**死锁时所有进程都可能处于阻塞态，CPU 空闲，运行态进程数为 0**。

这里要把 KP10 的笔记和王道的口径对齐，两者看着冲突其实问的不是一件事：

| 问法 | 答案 | 理由 |
| --- | --- | --- |
| 任何时刻是否**恰好**有一个进程在运行 | **否** | 全部阻塞时为 0 个 |
| 调度程序会不会「没得选」 | **不会** | 兜底的闲逛进程始终就绪 |

王道在这道题里不把闲逛进程算进「进程」的计数，所以说「CPU 空闲」。按语境走：问**运行态进程的数量**就承认可以是 0，问**CPU 会不会空转、调度会不会失败**就答有闲逛进程。

另外三项：B 错在优先级分静态和动态，**动态优先级随运行情况随时调整**；D 错在申请处理器得不到满足是**就绪态**（KP6：就绪态只缺 CPU），不是阻塞态；A 是正确答案，进程上 CPU 必经调度。

## 2026-08-23｜10｜导致创建新进程的事件（2.1）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | D |
| 我的选择 | A |
| 错误类型 | 记忆遗漏 |

**原题：下列选项中，导致创建新进程的操作是（）。**

I. 用户登录　II. 高级调度发生时　III. 操作系统响应用户提出的请求　IV. 用户打开了一个浏览器程序

| 选项 | 内容 |
| --- | --- |
| A | 仅 I 和 IV |
| B | 仅 II 和 IV |
| C | I、II 和 IV |
| D | 全部 |

错误原因：<span style="color: red;">漏判 II 和 III。KP8 卡片上「引起创建进程的事件」列了四条，做题时只想起两条。</span>

复盘结论：这道题的四个罗马数字**和 KP8 那四个事件一一对应**，是照着卡片出的：

| 题目 | KP8 卡片原文 |
| --- | --- |
| I 用户登录 | 终端用户登录系统 |
| II 高级调度发生时 | 作业调度启动批处理任务 |
| III OS 响应用户请求 | 系统提供服务 |
| IV 打开浏览器 | 用户程序发起应用请求 |

II 的关键：**高级调度 = 作业调度**，它的定义就是「从后备队列选一个作业调入内存**并为之创建进程**」——创建进程是这个动作的组成部分，不是副作用。

必须配对记的反例是本卷 58 题（2010 真题）：I 用户登录成功、II **设备分配**、III 启动程序执行 → 答 **C（仅 I、III）**。**设备分配不创建进程**，它只是给已有进程分资源。

一句话判据：**有新的执行主体出现才创建进程。** 新用户登录、作业进内存、请求要人干活、程序被打开，都有新主体；分配设备没有。

## 2026-08-23｜11｜OS 控制管理进程的依据（2.1）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | B |
| 我的选择 | C |
| 错误类型 | 概念不清 |

**原题：操作系统是根据（）来对并发执行的进程进行控制和管理的。**

| 选项 | 内容 |
| --- | --- |
| A | 进程的基本状态 |
| B | 进程控制块 |
| C | 多道程序设计 |
| D | 进程的优先权 |

错误原因：<span style="color: red;">答非所问——题目问的是「靠什么载体」，选了一个「技术思想」。</span>

复盘结论：KP3 第一句就是答案：**PCB 是进程存在的唯一标志，系统唯有通过它才能感知并管理进程**。

这道题的选项设计有个可利用的结构：**A（状态）和 D（优先级）都是 PCB 调度信息栏里的字段**，是 B 的组成部分。**选项之间存在包含关系时选包含者**——看出 A、D 被 B 吃掉，就只剩 B 和 C 两个候选。

C 是范畴错误：多道程序设计是一种**技术 / 设计思想**，不是 OS 手里的**数据结构**。题目问「根据什么」，要的是可读可写的实体。

自查动作：遇到「根据什么 / 通过什么 / 依靠什么」这类问法，先确认答案该是**一个实体**还是**一种方法**，再看选项。

## 2026-08-23｜12｜进程状态变化的相互影响（2.1）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | A |
| 错误类型 | 概念不清 |

**原题：在任何时刻，一个进程的状态变化（）引起另一个进程的状态变化。**

| 选项 | 内容 |
| --- | --- |
| A | 必定 |
| B | 一定不 |
| C | 不一定 |
| D | 不可能 |

错误原因：<span style="color: red;">把「状态变化」和「进程切换」当成了一回事。进程切换确实成对发生，但状态变化不是。</span>

复盘结论：这是「必定 / 一定不 / 不一定」三选一的模板题，做法固定——**各找一个例子，一正一反，答案就是「不一定」**：

| 会引起 | 不会引起 |
| --- | --- |
| 时间片用完：运行→就绪，同时另一就绪进程→运行 | 阻塞→就绪：只是从等待队列插回就绪队列，别人毫无变化 |

右边那个反例就是 KP10 的 Wakeup 原语三步——**从等待队列移出、置就绪态、插入就绪队列，全程只动一个进程的 PCB**，既不触发调度也不改别人的状态。

这个题型第二次栽了：2026-08-19 的 19 题结论就是「遇到必须 / 只能 / 需要这类措辞，先找反例再判断」。这次量词换成「必定」，手法没变。

## 2026-08-23｜14｜释放独占资源的影响范围（2.1）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | A |
| 错误类型 | 概念不清 |

**原题：一个进程释放了一台打印机，它可能改变（）的状态。**

| 选项 | 内容 |
| --- | --- |
| A | 自身进程 |
| B | 输入/输出进程 |
| C | 另一个等待打印机的进程 |
| D | 所有等待打印机的进程 |

错误原因：<span style="color: red;">因果倒置。进程结束时确实会释放打印机并转终止态，但那是「因为结束才释放」，不是「因为释放才结束」。</span>

复盘结论：题目问的是**释放这个动作造成的后果**。它的后果只有一个：从打印机的等待队列里**唤醒一个**进程（阻塞→就绪），正是 KP10 的 Wakeup。

两个错项各有一处要拿捏：

| 选项 | 错在哪 |
| --- | --- |
| A 自身进程 | 因果方向反了。释放资源这个动作本身不改变自己的状态 |
| D 所有等待者 | 打印机是**独占资源**，一次只能给一个进程，其余继续阻塞。Wakeup 是「找到目标进程的 PCB」，不是清空队列 |

判据：**独占资源释放 → 唤醒一个；共享资源或条件满足 → 才可能唤醒一批。** 看到「所有」先确认资源类型。

## 2026-08-23 · 2.1 五题共同错因

五道题，三道踩在同一个坑上——**量词**。

| 题 | 量词 | 反例 |
| --- | --- | --- |
| 06 | 任何时刻**只有一个**运行态 | 死锁时 0 个 |
| 12 | **必定**引起另一进程状态变化 | 阻塞→就绪不影响任何人 |
| 14 | 改变**所有**等待者的状态 | 独占资源只唤醒一个 |

这三道都不需要新知识，**只需要在判断前花五秒找一个反例**。2026-08-19 的 19 题已经写下过同样的结论（「遇到必须 / 只能 / 需要，先找反例」），所以这是**第二次**栽在量词上——第 1 章的主线是归属边界题，第 2 章换成了量词。

对策：看到下面这些词，先找反例再判对错。

| 类型 | 词 | 先试的反例 |
| --- | --- | --- |
| 下界 | 只有、恰好、总是 | **0 个**（全部阻塞、队列为空） |
| 全称 | 所有、全部、任何 | **只有一个**（独占资源、单播唤醒） |
| 必然 | 必定、一定、必然 | 找一个**不发生**的场景 |
| 禁止 | 一定不、不可能 | 找一个**发生**的场景 |

极端情形三件套先过一遍：**0 个 / 1 个 / 全部**。

另外两道各是独立的毛病：10 是卡片上写了四条只想起两条（记忆遗漏，回去把 KP8 那四个事件背成一句话）；11 是把「靠什么载体」答成了「什么技术」（问法没读准）。

## 2026-08-26｜10｜FCFS 与 CPU/IO 繁忙型作业的适配（2.2）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | B |
| 我的选择 | C |
| 错误类型 | 概念不清 |

**原题：（）有利于 CPU 繁忙型的作业，而不利于 I/O 繁忙型的作业。**

| 选项 | 内容 |
| --- | --- |
| A | 时间片轮转调度算法 |
| B | 先来先服务调度算法 |
| C | 短作业（进程）优先调度算法 |
| D | 优先级调度算法 |

错误原因：<span style="color: red;">映射方向记反了。KP36 明明写着 FCFS 有利于 CPU 繁忙型，我却选了 SJF。</span>

复盘结论：这题只要先做一步**翻译**就不会错。

| 题目说法 | 等价于 |
| --- | --- |
| CPU 繁忙型作业 | 长作业（占 CPU 久，很少请求 I/O） |
| I/O 繁忙型作业 | 短作业（频繁让出 CPU，每次只用一小段） |

翻译完直接对上 KP36：**FCFS 有利于长作业、不利于短作业**，所以答 B。SJF 恰好相反，它有利于短作业也就是有利于 I/O 繁忙型，正是本题要排除的那个。

另两项都属于「无偏好」：RR 给长短作业同样的时间片，地位几乎一样；优先级调度只看优先级，而优先级和作业长度没有必然联系。

判据：**看到「有利于 X 型作业」，先把 CPU 型 / I/O 型换成长 / 短作业，再套算法偏好。** 有偏好的只有两个——FCFS 偏长，SJF 偏短。

## 2026-08-26｜24｜作业与进程的本质区别（2.2）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | B |
| 我的选择 | C |
| 错误类型 | 概念不清 |

**原题：作业是用户提交的，进程是由系统自动生成的，除此之外，两者的区别是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 两者执行不同的程序段 |
| B | 前者以用户任务为单位，后者以操作系统控制为单位 |
| C | 前者是批处理的，后者是分时的 |
| D | 后者是可并发执行，前者则不同 |

错误原因：<span style="color: red;">把「典型出现场合」当成了「本质区别」。作业主要出现在批处理系统，但那是场合，不是定义。</span>

复盘结论：本质区别就一句——**作业是用户视角的任务单位，进程是 OS 视角的执行单位**，正是 KP25 那个答案里写下的话。

C 的两半都站不住：分时系统里也有作业（只是不设独立的作业调度模块），批处理系统里当然有进程。**概念的本质属性不随系统类型变化。**

A 错在两者可以执行同一段程序（作业步就是由进程去执行的）；D 错在作业之间同样能并发，多道批处理系统的全部意义就是并发跑多个作业。

判据：区分两个概念时先问自己**要的是「本质属性」还是「典型场合」**。拿典型场合冒充定义的选项一律判错——这和 11 题（用「技术思想」冒充「数据结构」）是同一族的范畴错误。

值得单独记一笔：这个知识点三天前才写进 KP25 的答案里，照样错了。说明**「写进去」和「变成判据」是两件事**，背下来的结论要主动改写成「看到什么 → 答什么」的形式才用得上。

## 2026-08-26｜38｜降低进程优先级的合理时机（2.2，2010 统考真题）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | A |
| 我的选择 | B |
| 错误类型 | 概念不清 |

**原题：【2010 统考真题】下列选项中，降低进程优先级的合理时机是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 进程时间片用完 |
| B | 进程刚完成 I/O 操作，进入就绪队列 |
| C | 进程长期处于就绪队列 |
| D | 进程从就绪态转换为运行态 |

错误原因：<span style="color: red;">挑中了应该「提高」优先级的那一项。刚完成 I/O 的进程要尽快处理结果，方向完全反了。</span>

复盘结论：一句判据管住全部四项——**用得多就降，等得久就升。**

| 选项 | 它此刻在干什么 | 该怎么调 |
| --- | --- | --- |
| A | 刚占掉一整个时间片的 CPU | **降**（正确答案） |
| B | 刚等完 I/O，还没用 CPU | 升，尽快处理 I/O 结果 |
| C | 在就绪队列干等 | 升，防饥饿（KP39 动态优先级） |
| D | 才刚拿到 CPU，还没用 | 不调，要降也得等时间片用完 |

背后是两条已学过的规则：KP39 动态优先级「等待时间越长优先级越高」，KP43 多级反馈队列「时间片用完就降一级」。**A 就是多级反馈队列的降级规则本身。**

配套记 42 题（2013 统考）：I/O 繁忙型进程的优先级应高于计算繁忙型，因为 I/O 数据留不住、要及时处理，也能提高设备利用率。和本题的 B 是同一个道理。

判据：看到「提高 / 降低优先级的时机」，先判断这个进程此刻**是在用 CPU 还是在等**。用 → 降，等 → 升。

## 2026-08-26｜41｜不能进行处理机调度的情形（2.2，2012 统考真题）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | D |
| 错误类型 | 概念不清 |

**原题：【2012 统考真题】若某单处理器多进程系统中有多个就绪态进程，则下列关于处理机调度的叙述中，错误的是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 在进程结束时能进行处理机调度 |
| B | 创建新进程后能进行处理机调度 |
| C | 在进程处于临界区时不能进行处理机调度 |
| D | 在系统调用完成并返回用户态时能进行处理机调度 |

错误原因：<span style="color: red;">没看出 C 的「临界区」前面缺了四个字，反而把 D 这个最常规的调度时机当成了错项。</span>

复盘结论：C 的毛病是**限定语被抽掉了**。真正不能调度的是**内核程序临界区**，不是任何临界区。

| 临界区类型 | 访问什么 | 能否调度 |
| --- | --- | --- |
| **内核程序**临界区 | 内核数据结构（就绪队列、PCB 链表） | **不能**，此期间通常屏蔽中断 |
| 普通临界区 | 普通临界资源（打印机等） | **能**。这类资源可能被占用很久，禁止调度会严重拖垮系统效率 |

再补一层：处于普通临界区的进程还可能**主动**让出 CPU——它在临界区里申请打印机而拿不到，就得阻塞。

D 是对的，而且是最常规的调度时机之一：系统调用完成、中断处理结束、返回用户态之前，内核会检查调度标志（对照 KP29 的「置调度请求标志、事后补做」）。

**本节 06 题考的是同一句话**（D 项「处于临界区的进程在退出临界区前，无法被调度」，答案也是它错）。06 对了 41 错了，说明 06 大概是蒙对的，这个点没真正拿住。

判据：见到「临界区 → 不能调度」，先找**「内核程序」**这四个字，没有就是错项。

## 2026-08-26｜45｜指定时刻的作业调度选择（2.2，2017 统考真题）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | D |
| 我的选择 | A |
| 错误类型 | 审题错 |

**原题：【2017 统考真题】假设 4 个作业到达系统的时刻和运行时间如下表。系统在 t = 2 时开始作业调度。若分别采用先来先服务和短作业优先调度算法，则选中的作业分别是（）。**

| 作业号 | 到达时刻 | 运行时间 |
| --- | --- | --- |
| J1 | 0 | 3 |
| J2 | 1 | 3 |
| J3 | 1 | 2 |
| J4 | 3 | 1 |

| 选项 | 内容 |
| --- | --- |
| A | J2, J3 |
| B | J1, J4 |
| C | J2, J4 |
| D | J1, J3 |

错误原因：<span style="color: red;">默认 J1 已经在跑了，把它从候选里划掉。题目说的是 t=2 才「开始」作业调度，在那之前一次调度都没发生过。</span>

**第二步，各算法各选一个。**

| 算法 | 依据 | 选中 |
| --- | --- | --- |
| FCFS | 到达最早 | **J1**（t=0，比 J2、J3 都早） |
| SJF | 运行时间最短 | **J3**（2 < 3、3） |

## 2026-08-29｜21｜互斥锁的解锁权归属（2.3）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | D |
| 我的选择 | C |
| 错误类型 | 概念不清 |

**原题：下列关于互斥锁的说法中，正确的是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 互斥锁只能用于多线程之间，不能用于多进程之间 |
| B | 互斥锁只能用于多进程之间，不能用于多线程之间 |
| C | 互斥锁可用于多线程或多进程之间，但只能由创建它的线程或进程来加锁和解锁 |
| D | 互斥锁可用于多线程或多进程之间，但只能由对它加锁的线程或进程来解锁 |

错误原因：<span style="color: red;">把「创建者」当成了锁的所有者。锁的归属是动态的，由**当前谁加了锁**决定，跟谁创建的没关系。</span>

复盘结论：C 和 D 的前半句完全一样，差别只在后半句，所以这题只考一件事——**解锁权归谁**。

| | C 的说法 | D 的说法（正确） |
| --- | --- | --- |
| 谁能加锁 | 只有创建者 | 任何线程/进程 |
| 谁能解锁 | 只有创建者 | 当前持有锁的那个 |

按 C 的说法，锁只能被创建者用，那它就不叫互斥锁了——**互斥锁存在的意义就是让多个执行流去争它**，只有一个能用的锁没有任何互斥价值。这个反推能当场毙掉 C。

规则的实质是**所有权（ownership）**：谁 `acquire()` 谁就是主人，只有主人能 `release()`。别人试着解一个不属于自己的锁会返回错误码。这也是互斥锁和信号量最大的区别之一——**信号量的 V 谁都能做**（同步问题里 V 和 P 本来就在两个不同进程），互斥锁的解锁必须原主人来。

判据：**看到互斥锁的加解锁权，答「加锁的那个」，不是「创建的那个」。** 顺带把 22 题一起记住：同一线程对同一锁连加两次是**自死锁**（该题答 C 是因为问的是「两个线程」的循环等待）。

```c
    z = y;                          if (x <= 1) t = t + 2;
}                                   u = t;
                                }
                            }
```

| 选项 | 内容 |
| --- | --- |
| A | 程序能正确运行，结果唯一 |
| B | 程序不能正确运行，可能有两种结果 |
| C | 程序不能正确运行，结果不确定 |
| D | 程序不能正确运行，可能死锁 |

错误原因：<span style="color: red;">数了一下 z 只能取 0 或 1，就选了「可能有两种结果」。把不确定性数字化了——x 是无互斥保护的共享变量，`if (x >= 1)` 的成败取决于 P2 何时把 x 改成 0，这是竞态：结果不可预知、不可重现，且 P2 在循环里反复改 x，程序没有稳定的最终状态。</span>

复盘结论：判据一句话——**共享变量没有互斥保护，且「判断」和「使用」分成两条语句写，结果就是「不确定」。**

- z 的取值范围确实是 {0, 1}，这个观察不错，但题目问的是「程序运行的结果」，指的是每次运行的整体表现是否可预知，不是可能值的个数。
- 选项里出现「可能有两种结果」这类把竞态量化成固定几种的说法，基本是干扰项；只有当所有相关语句都是原子操作、能穷举全部交错时才成立。
- A 排除：没有互斥保护就谈不上「正确运行」。
- D 排除：全程只有共享变量读写，没有任何资源的请求与保持，四个必要条件一条都不满足（KP79），谈不上死锁。

判据：看到「两个并发进程 + 共享变量 + if 判断」，先找**判断与赋值之间有没有可能被别人插进来**。能插进来就是竞态 → 结果不确定。

## 2026-08-29｜27｜死锁定理的归属（2.4）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | A |
| 错误类型 | 概念不清 |

**原题：死锁定理是用于处理死锁的（）方法。**

| 选项 | 内容 |
| --- | --- |
| A | 预防死锁 |
| B | 避免死锁 |
| C | 检测死锁 |
| D | 解除死锁 |

错误原因：<span style="color: red;">看到「定理」就觉得是事前用来防的规则，选了预防。死锁定理拿的是当前的资源分配图，回答的是「现在有没有死锁」，是事后判断。</span>

复盘结论：死锁定理 = **系统处于死锁状态 ⟺ 资源分配图不可完全简化**（KP95）。输入是「当前的分配与请求状态」，输出是「是否已死锁」，正是死锁检测的定义（KP94：只判当前时刻，不需预知未来需求）。

四种方法的**标志物**表，做题时先归位再读句子：

| 策略 | 标志物 |
| --- | --- |
| **预防** | 一次性（静态）分配、资源有序分配、允许剥夺——都是静态规则 |
| **避免** | 银行家算法、安全性算法、安全状态、安全序列 |
| **检测** | 资源分配图化简、**死锁定理** |
| **解除** | 资源剥夺法、撤销进程法、进程回退法 |

判据：**按标志物归类，不按字面语感。**「定理」听着像预防、「银行家」听着像检测，全是错觉。

## 2026-08-29｜30｜银行家算法允许分配的判据（2.4）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | D |
| 错误类型 | 概念不清 |

**原题：用银行家算法避免死锁时，检测到（）时才分配资源。**

| 选项 | 内容 |
| --- | --- |
| A | 进程首次申请资源时对资源的最大需求量超过系统现存的资源量 |
| B | 进程已占有的资源数与本次申请的资源数之和超过对资源的最大需求量 |
| C | 进程已占有的资源数与本次申请的资源数之和不超过对资源的最大需求量，且现存资源量能满足尚需的最大资源量 |
| D | 进程已占有的资源数与本次申请的资源数之和不超过对资源的最大需求量，且现存资源量能满足本次申请量，但不能满足尚需的最大资源量 |

错误原因：<span style="color: red;">只走到银行家算法的第 ② 步（本次申请 ≤ Available）就判定可以分配。D 的后半句「不能满足尚需的最大资源量」恰恰说明分配后这个进程跑不完，正是不安全的写法，我把它当成了通过条件。</span>

复盘结论：银行家算法永远是**两道关**（KP90）：

| 关 | 判据 | 对应选项里的哪半句 |
| --- | --- | --- |
| **合法性** | `Allocation + Request ≤ Max`，即 `Request ≤ Need` | 「之和不超过最大需求量」 |
| **安全性** | 剩余资源足以让它补齐 Need、跑完并归还全部资源 | 「现存资源量能满足尚需的最大资源量」 |

C 两关都过；D 只过了「够本次申请」，卡在安全性 → **撤销试探性分配，进程等待**，这就是 KP93 第 ③ 个请求（P0 要 (0,2,0)）的情形。

A、B 排除：

- A 错：Max 只要求不超过**系统资源总量**，不要求不超过当前 Available；首次申请时 Max 大于现存量很正常。
- B 错：`Allocation + Request > Max` 是**非法请求**（超过声明），直接报错，不是分配条件。

补一句严格性（考试不必写）：安全性算法允许「别的进程先跑完再腾资源给它」，所以并非只有 C 这一种情形才安全；但四个选项里只有 C 描述了**能构成安全序列**的充分情形，而 D 把这种可能明确否定了。

判据：**「够本次申请」只是入场券，不是结论。** 银行家算法的结论只来自安全性检查。

## 2026-08-29｜39｜死锁避免与死锁检测的区分【2015 统考真题】（2.4）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | B |
| 我的选择 | D |
| 错误类型 | 概念不清 |

**原题：若系统 S1 采用死锁避免方法，S2 采用死锁检测方法。下列叙述中，正确的是（）。**

| 编号 | 叙述 |
| --- | --- |
| I | S1 会限制用户申请资源的顺序，而 S2 不会 |
| II | S1 需要进程运行所需的资源总量信息，而 S2 不需要 |
| III | S1 不会给可能导致死锁的进程分配资源，而 S2 会 |

| 选项 | 内容 |
| --- | --- |
| A | 仅 I、II |
| B | 仅 II、III |
| C | 仅 I、III |
| D | I、II、III |

错误原因：<span style="color: red;">三条全选。把 I 的「限制申请资源的顺序」当成了死锁避免的手段——资源有序分配是死锁**预防**（破坏循环等待，KP86），银行家算法不限制申请顺序，只在每次分配前算一次安全性。</span>

复盘结论：逐条判——

- **I 错**：限制申请顺序 = 预防（资源有序分配法）。避免对「按什么顺序申请」完全不管。
- **II 对**：避免需要预知 Max，检测只看当前分配与请求（KP94 原句）。
- **III 对**：避免会拒绝导致不安全状态的分配；检测放开分配，事后化简资源分配图再收拾。

三者对照，这张表能同时解掉 27 和 39：

| | 预防 | 避免 | 检测 |
| --- | --- | --- | --- |
| 限制申请顺序 | **✓**（有序分配） | ✗ | ✗ |
| 需预知最大需求 Max | ✗ | **✓** | ✗ |
| 拒绝可能致死锁的分配 | 靠静态规则事先挡掉 | **✓ 每次算安全性** | ✗ 先给再说 |
| 运行时开销 | 无须检测 | 每次分配都算 | 定期检测 + 解除 |

**为什么「不安全就不分配」不算限制申请顺序**（这是 I 最容易被绕进去的地方）：

| | 限制什么 | 谁受约束 | 不通过的后果 |
| --- | --- | --- | --- |
| 资源有序分配（**预防**） | 你**可以怎么提**：按编号递增，同类一次提完 | 程序员，写代码时就得守 | 这种提法**不合规**，程序不允许这么写 |
| 银行家算法（**避免**） | 系统**怎么答**：这次给不给 | OS，运行时逐次判断 | 请求**仍然有效**，进程阻塞等待，状态安全了就给 |

反证：一个「先申请 R3、再申请 R1」的进程，在有序分配法下**根本不合规**；在银行家算法下**完全合法**，只是某次申请可能被推迟。所以银行家限制的是**分配时机**，不是**申请顺序**。

另外，「资源不够就让你等」是任何分配策略的共性，连不管死锁的系统也这样，那不叫限制；银行家的特色是**够也可能不给**（Available 满足但状态不安全）。而它真正施加的约束，题目已经写在 II 里了——**必须预先声明 Max**。

判据（补充）：预防的规则**与当前状态无关**（编号固定，什么时候看都一样）；避免的决定**完全取决于当前状态**（同一请求此刻拒、等别人还了资源再提就批）。「不管现在什么样都不许这么提」= 预防；「看情况给不给」= 避免。

判据：**「限制顺序 / 一次性申请 / 允许剥夺」是预防的三件套**，看到它们出现在「避免」的描述里，直接判错。

## 2026-08-29 · 2.4 六题共同错因

五道（02、05、27、30、39）是同一个毛病：**把手段挂到了错的策略、或把限定条件放宽了**。

| 题 | 我用的映射 | 正确映射 |
| --- | --- | --- |
| 02 | 同时取筷 → 会饥饿 | 限制人数 → 破坏循环等待 |
| 05 | 死锁原因 → 资源不足 | 死锁原因 → 分配不当 / 顺序非法 |
| 27 | 死锁定理 → 预防 | 死锁定理 → 检测 |
| 39 | 限制申请顺序 → 避免 | 限制申请顺序 → 预防 |
| 30 | 够本次申请 → 可分配 | 能补齐 Need（安全）→ 可分配 |

前几章的主线接上了：第 1 章归属边界 → 2.1 量词 → 2.2 映射方向 → 2.3 精度 → **2.4 归属**。2.4 几乎不考计算，考的全是「某个名词属于哪种策略、破坏哪个条件」。

对策，做 2.4 选择题的固定动作：

1. **先把选项里的名词归位**，用 27 那张标志物表（预防三件套 / 避免=银行家、安全序列 / 检测=图化简、死锁定理 / 解除=剥夺、撤销、回退）。
2. **看到「破坏了 X 条件」，先只验 X**：互斥永远破坏不了；有序分配和奇偶分序都破坏循环等待；一次性分配和「两个一起拿」都破坏请求并保持。
3. **看到「原因」二字，只答质不答量**：分配不当、顺序非法，别答资源少。
4. **银行家算法两道关都过才分配**，只过「够本次申请」的一律等待。

24 是唯一的例外，不属于死锁归属，属于并发正确性：**共享变量无互斥保护 + 判断与使用分写 ⇒ 结果不确定**，别去数可能值的个数。

复查重点：02 的三办法对应条件表、27 的标志物表、39 的预防/避免/检测三列对照。
