## 2026-08-16｜03｜操作系统的职责边界

| 题型 | 单项选择题 |
| 正确答案 | D |
| 我的选择 | B |
| 错误类型 | 概念不清 |

**原题：下列选项中，（）不是操作系统关心的问题。**

| 选项 | 内容 |
| --- | --- |
| A | 管理计算机裸机 |
| B | 设计、提供用户程序与硬件系统的界面 |
| C | 管理计算机系统资源 |
| D | 高级程序设计语言的编译器 |

错误原因：<span style="color: red;">把「界面」读成了图形界面，误以为是应用程序的事；根子上是没把「系统软件」和「操作系统」切开。</span>

复盘结论：这里的「界面」是 interface（接口），指程序接口和用户接口，正是 OS 的核心角色之一。编译器是系统软件但不是 OS——它怎么做语法分析、怎么生成目标代码，OS 一概不管。注意别反向踩：OS 关心「程序的链接与装入」（1.3 节），但那是把目标文件装进内存运行，跟「编译器本身怎么实现」是两件事。

| 选项 | 内容 |
| --- | --- |
| A | 直接通过键盘交互方式使用 |

| 正确答案 | C |
| 我的选择 | A |
| 错误类型 | 概念不清 |

**原题：操作系统提供给编程人员的接口是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 库函数 |
| B | 高级语言 |
| C | 系统调用 |
| D | 子程序 |

错误原因：<span style="color: red;">知道「库函数只是封装」这个结论，但被「编程人员」的措辞诱导，按「谁常用」而不是「谁提供」来选。</span>

复盘结论：判据是**谁提供**，不是**谁常用**。库函数由 C 标准库提供，属语言/编译系统；OS 提供的是系统调用。反证：`strlen`、`sqrt` 压根不进内核，如果库函数是 OS 接口，它们算哪门子接口。B 高级语言是编程语言不是接口，D 子程序是程序结构概念。

## 2026-08-16 三题共同错因

三道全是**边界题**：编译器不属于 OS 管的范围、系统调用不属于命令接口、库函数不属于 OS 提供的东西。

对概念本身的理解没问题，问题出在概念的**归属和外延**。

下次遇到同类题第一步：先问「这东西属于哪一层、是谁提供/谁负责的」，再看选项说得对不对，而不是凭「这句话听起来对不对」来选。

## 2026-08-19｜01｜提高资源利用率的关键技术

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | D |
| 我的选择 | A |
| 错误类型 | 概念不清 |

**原题：提高单机资源利用率的关键技术是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 脱机技术 |
| B | 虚拟技术 |
| C | 交换技术 |
| D | 多道程序设计技术 |

错误原因：<span style="color: red;">把脱机技术的收益记大了。脱机只是让 I/O 不占 CPU，但内存里仍只有一道程序，CPU 空出来的时间没有第二个程序可用，还是闲着。</span>

复盘结论：判据是「CPU 等 I/O 的时候有没有活干」。脱机技术解决的是**人机速度不匹配**（省掉人工装带），多道程序设计解决的是 **CPU 与 I/O 速度不匹配**（等待期间切去跑别的程序），后者才是利用率的关键。B 虚拟、C 交换都建立在多道程序设计之上，是它的产物不是前提。
## 2026-08-19｜18｜多道程序系统的优点（2017 统考真题）

| 我的选择 | A |

**原题：【2017 统考真题】与单道程序系统相比，多道程序系统的优点是（）。**

I. CPU 的利用率高　II. 系统开销小　III. 系统吞吐量大　IV. I/O 设备利用率高

| 选项 | 内容 |
| --- | --- |
| A | 仅 I、III |
| B | 仅 I、IV |
| C | 仅 II、III |
| D | 仅 I、III、IV |

错误原因：<span style="color: red;">只算了 CPU 那一侧的收益，漏掉 IV。多道程序的并发是 CPU 与 I/O 双向重叠，两边的利用率都提高。</span>

复盘结论：I、III、IV 全对，唯一的错项是 II——多道程序需要额外的进程调度、上下文切换、内存保护，**系统开销比单道更大**，这是它的代价不是优点。记法：多道程序用「开销换利用率」，凡是选项说它开销小，直接否。

I. 具有并发和并行的特点　II. 需要实现对共享资源的保护　III. 需要运行在多 CPU 的硬件平台上

复盘结论：I 对，因为并行不限于进程级——这正是 KP6 里那条容易漏的硬件并行。III 错在「**需要**」：多 CPU 能让进程级并行，但不是多任务的前提，Windows XP 在单核上就是多任务系统。遇到「必须 / 只能 / 需要运行在」这类措辞，先找反例再判断。

## 2026-08-19 三题共同错因

三道都围绕**多道程序设计**，各偏了一个方向：01 把收益记到脱机技术头上（阶段错位），18 只数了 CPU 一侧的收益（范围漏算），19 把前提条件想严了（条件加码）。

下次遇到同类题第一步：先定位这项技术解决的是**哪一对速度矛盾**——脱机是人机不匹配，多道是 CPU 与 I/O 不匹配。定位准了，收益范围和前提条件基本就跟着对了。

## 2026-08-19｜04｜OS 必须提供的功能（1.3）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | B |
| 错误类型 | 概念不清 |

**原题：（）是操作系统必须提供的功能。**

| 选项 | 内容 |
| --- | --- |
| A | 图形用户界面（GUI） |
| B | 为进程提供系统调用命令 |
| C | 中断处理 |
| D | 编译源程序 |

错误原因：<span style="color: red;">B 和 C 都像「必须」，没找到区分两者的判据——漏掉了系统调用**建立在中断异常机制之上**这层依赖关系。</span>

复盘结论：判据是**依赖关系，谁更底层**。系统调用靠陷入指令实现，陷入指令属异常（KP27 自陷），所以没有中断异常机制，系统调用根本无法实现——C 是 B 的前提。另一条理由：中断处理属内核的**支撑功能**（KP19），OS 靠它才能从用户程序手里夺回 CPU，没有中断连多道程序和抢占式调度都不存在。A 错在 GUI 非必需（服务器 OS、嵌入式 OS 都可以没有），D 错在编译器不是 OS 的事（呼应 2026-08-16 的 03 题）。

## 2026-08-19｜06｜中断处理程序的归属（1.3）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | D |
| 错误类型 | 概念不清 |

**原题：在中断发生后，中断处理的程序属于（）。**

| 选项 | 内容 |
| --- | --- |
| A | 用户程序 |
| B | 可能是用户程序，也可能是 OS 程序 |
| C | 操作系统程序 |
| D | 单独的程序，既不是用户程序也不是 OS 程序 |

错误原因：<span style="color: red;">把中断**响应**由硬件完成的印象延伸到了中断**处理**上，于是觉得它是游离在 OS 之外的独立存在。</span>

复盘结论：中断处理程序就是内核代码——KP19 里「与硬件紧密相关的模块」第一个列的就是它。要切开两个阶段：**中断响应**由硬件完成（保存 PC/PSW、查向量表、置模式位 0）；**中断处理**由 OS 完成（服务程序本体），且必须在内核态执行。设备驱动程序同理，也是内核的一部分。2011 真题考「时钟中断处理程序在哪个态」，答内核态，同一个点。

## 2026-08-19 · 1.3 两题共同错因

两道都是**归属题**，和 2026-08-16 那批（编译器归谁管、系统调用属哪类接口、库函数谁提供）是同一类——第三次栽在这上面。

这次多了一个**硬件维度**：04 要判断「中断处理和系统调用谁更底层」，06 要判断「中断处理程序归硬件还是归 OS」。

下次遇到同类题第一步：**先画依赖链，再判归属。**

`硬件 → 中断/异常机制 → 系统调用 → 库函数`

箭头指向的一方是前提。问「哪个是必须的」就往链条左边找，问「归谁提供」就看它落在链条哪一段。

## 2026-08-20｜03｜模块化 OS 的特点（1.4）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | B |
| 我的选择 | C |
| 错误类型 | 概念不清 |

**原题：下列选项中，（）不属于模块化操作系统的特点。**

| 选项 | 内容 |
| --- | --- |
| A | 很多模块化的操作系统，可以支持动态加载新模块到内核，适应性强 |
| B | 内核中的某个功能模块出错不会导致整个系统崩溃，可靠性高 |
| C | 内核中的各个模块可以相互调用，无须通过消息传递进行通信，效率高 |
| D | 各模块间相互依赖，相比于分层式操作系统，模块化操作系统更难调试和验证 |

错误原因：<span style="color: red;">觉得 C「直接调用、效率高」是宏内核的说法而非模块化的，没意识到模块化就是宏内核的组织方式；同时漏掉 B 把微内核的可靠性搬给了模块化。</span>

复盘结论：模块化 OS 的所有模块都在**内核态、共享同一地址空间**，由此同时得出两件事：① 模块之间能直接函数调用，不必消息传递，所以效率高（C 对）；② 任一模块出错整个内核崩溃（B 错）。这是同一个前提的两面，抓住前提就不会挑错项。B 的正确版本是「**微内核** OS 中，内核**外**的功能模块出错不会导致系统崩溃」——王道解析管这叫「移花接木」。A 是 Linux 可加载内核模块（LKM），D 对应 KP35 缺点②「找不到可靠的决定顺序」。

## 2026-08-20｜06｜微内核应包含的功能（1.4）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | B |
| 错误类型 | 概念不清 |

**原题：对于以下五种服务，在采用微内核结构的操作系统中，（）不宜放在微内核中。**

I. 进程间通信机制　II. 低级 I/O　III. 低级进程管理和调度　IV. 中断和陷入处理　V. 文件系统服务

| 选项  | 内容         |
| --- | ---------- |
| A   | I、II 和 III |
| B   | II 和 V     |
| C   | 仅 V        |
| D   | IV 和 V     |

错误原因：<span style="color: red;">把「低级 I/O」判成不宜放进微内核，多选了 II。</span>

复盘结论：判据一句话——**凡带「低级」二字的全在微内核里**。低级 I/O、低级进程管理与调度、低级存储器管理（页表映射），「低级」＝贴硬件的**机制**部分，正是微内核的定义域；再加进程间通信（微内核最频繁使用的功能）和中断/陷入的**捕获与分发**，基本就是微内核的全部内容。以「**服务**」结尾的（文件系统服务）一律在微内核外的服务器里。

附带反省：这道题正好戳中 KP37 笔记里「微内核管抽象的、服务器管具体的」那个说法——低级 I/O 是最具体的东西，却必须在内核。判据要换成 **机制（怎么做到）在内核、策略（挑哪个、用什么算法）在服务器**。

## 2026-08-20｜08｜操作系统结构的综合判断（1.4）

| 项目 | 内容 |
| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | D |
| 错误类型 | 审题错 |

**原题：下列关于操作系统结构的说法中，正确的是（）。**

I. 当前广泛使用的 Windows 操作系统，采用的是分层式 OS 结构
II. 模块化的 OS 结构设计的基本原则是，每一层都仅使用其底层所提供的功能和服务，这样就使系统的调试和验证都变得容易
III. 因为微内核结构能有效支持多处理机运行，所以非常适合于分布式系统环境
IV. 采用微内核结构设计和实现操作系统具有诸多好处，如添加系统服务时不必修改内核，使系统更高效

| 选项 | 内容 |
| --- | --- |
| A | I 和 II |
| B | I 和 III |
| C | III |
| D | III 和 IV |

错误原因：<span style="color: red;">判 IV 为对。IV 前半句「添加系统服务时不必修改内核」确实正确，但句尾还挂着「使系统更高效」——没读到句尾就下了判断。</span>

复盘结论：同一份卷子的 07 题里「使系统更高效」这个错项刚判对过，08 换成复合句就漏了，说明**知识没问题，缺的是审题动作**。两条硬规则：

1. **「微内核 + 高效 / 性能好」= 必错**，无论前面铺垫了多少正确内容。性能是微内核唯一的缺点，出题人反复拿它当句尾的尾巴。
2. 判断题的每个罗马数字要**读到句号**。凡是中间用逗号或「所以 / 因此 / 这样就」连接的长句，后半句就是陷阱位。

另外 I、II 都是移花接木：Windows 是**混合内核**不是分层式；「每层仅使用底层功能」是**分层式**的原则不是模块化的。III 对——微内核靠消息传递通信，天生适配多处理机与分布式环境。

## 2026-08-20｜10｜外核的职责边界（1.4）

| --- | --- |
| 题型 | 单项选择题 |
| 正确答案 | C |
| 我的选择 | B |
| 错误类型 | 概念不清 |

**原题：下列关于操作系统外核（exokernel）的说法中，错误的是（）。**

| 选项 | 内容 |
| --- | --- |
| A | 外核可以给用户进程分配未经抽象的硬件资源 |
| B | 用户进程通过调用「库」请求操作系统外核的服务 |
| C | 外核负责完成进程调度 |
| D | 外核可以减少虚拟硬件资源的「映射」开销，提升系统效率 |

错误原因：<span style="color: red;">怀疑 B「通过调用库请求外核服务」。这是把 2026-08-16 第 07 题的结论（库函数不是 OS 提供的接口）跨架构迁移了，可外核架构的设计恰恰就是让用户通过库操作系统拿资源。</span>

复盘结论：C 错在**职责越界**——外核只做三件事：**分配、回收、保护**（KP39），功能实现全在用户空间的**库操作系统**里，进程调度属于「实现」，不归外核。注意「库」在三种架构里地位完全不同：宏内核、微内核下库函数只是对系统调用的封装（不是 OS 接口）；外核下**库 OS 就是干活的 OS 本体**。已学过的规则不能跨架构照搬，这是这次错的真正教训。

## 2026-08-20 · 1.4 四题共同错因

四道题，出题人只用了两种手法。

**一、移花接木（03、08）**——把某架构的特点挂到另一个架构名下。03 把微内核的「单模块崩溃不影响系统」安给模块化；08-I 把混合内核的 Windows 说成分层式；08-II 把分层式的「只调用紧邻下层」说成模块化的原则。王道解析里「移花接木」四个字就是明说。

**二、职责越界（06、10）**——什么该在微内核里、什么归外核管。这是**第四次**栽在归属题上（08-16 的 03/06/07、08-19 的 04/06、这次的 06/10）。

对策一：做 1.4 的题，先问「**这句话是谁家的**」，用这张表对号入座。

| 说法 | 只属于 |
| --- | --- |
| 每层仅调用紧邻下层、便于调试验证、有可靠的决定顺序 | 分层式 |
| 模块间直接调用无须消息传递、效率高、可动态加载模块 | 模块化 / 宏内核 |
| 一崩全崩、占内存空间大、可扩展性差、不便移植 | 宏内核 / 模块化 |
| 单模块崩溃不影响系统、可靠性与安全性高、加服务不改内核、可移植性好、适合分布式 | 微内核 |
| 不做抽象、直接给物理资源、只负责分配回收与保护 | 外核 |
| **效率高 / 性能好** | 宏内核、模块化——**永远不是微内核** |

对策二：08 那种复合句读到句尾再判，尾巴常常是唯一的错处。
