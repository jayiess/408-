# 2.1 进程与线程

## KP1 进程的定义与进程实体

**核心结论**：并发性破坏了程序的**封闭性**，使执行呈现**间断性**、结果可能**不可再现**，为描述和控制并发行为才引入进程，用来支撑 OS 的两大基本特性——**并发性与共享性**。

正式定义（背这条）：**进程是进程实体的运行过程，是系统进行==资源分配和调度==的一个独立单位**。

==**进程实体（也称进程映像）= 程序段 + 相关数据段 + PCB==**==

| 操作   | 本质            |
| ---- | ------------- |
| 创建进程 | 创建其 **PCB**   |
| 撤销进程 | 释放该 PCB 及相关资源 |

三种常见表述：① 正在执行的程序实例；② 程序及其数据从外存加载到内存后在 CPU 上运行的过程；③ 具有独立功能的程序在一个特定数据集合上的执行活动。

**易错点**：这里的「系统资源」不只是内存、I/O 设备==，**还包括 CPU 的使用权**（==通过时间片分配实现）。

**易错点**：==正因为进程是资源分配与调度的基本单位，它必然是**动态的、有生命周期的**==，不是静态的程序。==「程序 = 进程」是最常见的错。==

## KP2 进程的四大特征

| 特征  | 含义                                                        |
| --- | --------------------------------------------------------- |
| 动态性 | 程序的一次执行实例，有创建/就绪/运行/阻塞/终止的生命周期。==**动态性==是进程最根本的特征**       |
| 并发性 | 多个进程可同时驻留内存、交替或并行执行。==**引入进程的根本目的就是支持并发执行**==             |
| 独立性 | ==能独立运行、独立获取资源、作为调度基本单位参与 CPU 竞争。**未建立 PCB 的程序不能被调度执行**== |
| 异步性 | 相互制约，==以不可预知的速度推进，可能导致结果不可再现==，需 OS 提供协调机制                |

**易错点**：问「最根本的特征」答**动态性**（对比第 1 章：OS 最基本的特征是并发与共享，两个问题别混）。

**易错点**：==独立性的判据是**有没有 PCB**，不是「有没有代码」。==

## KP3 PCB：内容与组织方式

**核心结论**：==PCB 是**进程存在的唯一标志**，**常驻内存**==，可随时被系统访问，进程终止时回收。系统唯有通过它才能感知并管理进程。

PCB 四类信息：

| 类别                   | 内容                                       |
| -------------------- | ---------------------------------------- |
| 进程==标识信息==           | PID（唯一编号）、PPID（父进程）、UID（所属用户，供资源共享与安全保护） |
| 进程==调度信息==           | 当前状态、优先级、CPU 占用时间、等待时间、进入内存时间、**阻塞原因**   |
| 资源和内存信息              | 代码段/数据段/堆栈段指针、**文件描述符列表**、I/O 资源清单       |
| 处理机状态信息（**CPU 上下文**） | 通用寄存器值、程序计数器、**PSW**、栈指针 SP              |

PCB 的组织方式两种：

| 方式   | 做法                                                        |
| ---- | --------------------------------------------------------- |
| 链接方式 | 相同状态的 PCB 用指针链成==队列==（就绪队列、阻塞队列）；阻塞进程还可按阻塞原因分成多个**阻塞子队列** |
| 索引方式 | 每种状态建一张索引表（就绪索引表、阻塞索引表），表项指向对应 PCB                        |

**易错点**：==进程切换时 CPU 上下文是**保存回 PCB**==，恢复时从 PCB 取。所有对进程的操作都绕不开访问和更新 PCB。

**易错点**：==阻塞队列可以有**多个**（按阻塞原因分）==，==就绪队列通常一个。==

## KP4 程序段与数据段：共享还是私有

|     | 是否可共享            | 说明                                                         |
| --- | ---------------- | ---------------------------------------------------------- |
| 程序段 | ==**可被多个进程共享**== | 程序本身是静态的。多个用户跑同一个文本编辑器，==内存里只留**一份代码副本**==，各进程用自己的 PCB 指向它 |
| 数据段 | ==**每个进程私有**==   | 即使多个进程跑同一程序，==数据段也彼此隔离==，保障独立性与安全性                         |

**易错点**：这一条是「程序 ≠ 进程」的直接体现——==同一份代码可以对应多个进程，因为每个进程有自己的 PCB 和数据段。==

## KP5 进程的内存映像（真题）

**真题**：2025 考过进程虚拟地址空间中各区域的存放内容。

**核心结论**：==程序加载运行时 OS 为它建立**虚拟地址空间**==，其逻辑布局就是内存映像。与磁盘上的静态可执行文件不同，内存映像是**动态的**——虚拟内存机制下地址空间无须全部驻留物理内存，实际访问某部分时才通过**缺页中断**从磁盘调入。

按地址**从高到低**排（这个顺序必须记牢）：

| 区域        | 内容                                                            | 增长方向          |
| --------- | ------------------------------------------------------------- | ------------- |
| 用户栈       | ==局部变量==、函数参数、返回地址，**LIFO**，系统自动管理                            | **高地址 → 低地址** |
| 共享库的存储映射区 | ==公共函数代码（如 `printf`），运行时动态映射，只读、可共享==                         | —             |
| 堆         | ==`malloc()` 动态申请==，`free()` 释放，适合生命周期不确定的数据                  | **低地址 → 高地址** |
| 读/写数据段    | `.data` 已初始化的全局/静态变量（`int x = 5;`）；`.bss` ==未初始化==的（`int y;`） | 加载时确定         |
| 只读代码段     | `.init` 启动初始化代码；`.text` 主程序指令；`.rodata` 只读数据（字符串常量）           | 加载时确定         |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-2-1.jpg]]（图 2.1 一个典型进程在内存中的映像）

**核心结论（易错重点）**：==**PCB 不属于进程的虚拟地址空间**。它由内核维护，存放在**系统内核区**，对用户进程不可见。==

**易错点**：==**代码段和数据段的大小在程序加载时就已确定**==；==只有**堆和栈**能在运行中动态扩展收缩。==

**易错点**：==`.data` 和 `.bss` 的分界是**有没有显式赋初值**==，不是「是不是全局变量」。静态局部变量（`static`）也在数据段，不在栈上。

**易错点**：堆向上长、栈向下长，两者**相向而行**，中间是未使用的空隙。别记反。

> <span style="color: red;">答：栈向下、堆向上，是为了共用中间那块空闲区，免得加载时给两者划死边界。</span>

## KP6 进程的五种状态（真题）

**真题**：2023 考过执行中断处理程序时进程的状态。

前三种是**基本状态**：

| 状态       | 含义                                                                |
| -------- | ----------------------------------------------------------------- |
| 运行态      | 正在 CPU 上执行。==**单 CPU 下任一时刻最多一个**进程处于运行态==                         |
| 就绪态      | 已获得**除 CPU 外**的所有必要资源，==一拿到 CPU 就能跑==。组织成**就绪队列**                 |
| 阻塞态（等待态） | 因等待某事件（资源可用、I/O 完成）暂停。==**即使 CPU 空闲也无法执行**。组织成阻塞队列，可按原因再分子队列==    |
| 创建态      | 正在创建中，尚未就绪。步骤：==申请空白 PCB → 填信息 → 分配资源 → 转就绪态并插入就绪队列。**短暂的中间状态**== |
| 终止态      | 已完成执行（正常或被强制），等待系统回收资源。==**不再参与调度==**，但 PCB 等信息可能暂时保留             |

**核心结论（就绪 vs 阻塞的本质）**：就绪态**只缺 CPU**；阻塞态**缺 CPU 以外的资源或在等事件**。

为什么要把 CPU 和其他资源分开看：时间片只有几毫秒，进程在**运行态↔就绪态之间切换非常频繁**；而外设分配、I/O 完成往往耗时很长，**进入阻塞态的频率远低于就绪态**。两者代表性质完全不同的等待。

**易错点（2023 那道的核心）**：==执行**中断处理程序**时，被中断的那个进程**不是阻塞态**——中断处理是内核代表当前进程在跑，进程本身仍算运行态。别一看到「中断」就往阻塞态填。==

> [!note] 我的笔记
> **单处理机下是「最多一个」进程处于运行态，不是「只有一个」。** 「最多」允许 0 个：发生死锁时所有进程都阻塞，运行态进程数就是 0。选项里写「任何时刻都只有一个进程处于运行态」直接判错（2.1 习题 06 就这么栽的）。
> 
> **闲逛进程不算作运行的进程。** 王道在计数时不把它算进去，所以照样说「CPU 空闲」。它和 KP10 那条笔记分工如下：问**运行态进程的数量**，答可以是 0；问**调度程序会不会没得选**，答不会，闲逛进程兜底。两个问题，两个答案。

## KP7 状态转换：主动与被动（真题超高频）

**真题**：2014、2015、2018、2023、2025 都考过引起进程状态转换的事件。

三种基本状态之间的四条转换：

| 转换        | 触发事件                                               | 性质                     |
| --------- | -------------------------------------------------- | ---------------------- |
| 就绪态 → 运行态 | 被调度程序选中，获得 CPU 使用权（分到时间片）                          | 由**调度程序**决定            |
| 运行态 → 就绪态 | ① **时间片用完**，主动让出 CPU；② 可剥夺式调度下，**更高优先级进程就绪**，被强制切换 | —                      |
| 运行态 → 阻塞态 | 通过**系统调用**请求服务（如发起 I/O），请求无法立即满足                   | ==**主动行为**（自身发起）==     |
| 阻塞态 → 就绪态 | 等待的事件发生（I/O 完成），由**中断处理程序**改状态并插回就绪队列              | **被动行为**（靠外部事件或其他进程协助） |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-2-2.jpg]]（图 2.2 5 种进程状态的转换）

**易错点（考得最多的一条）**：==**没有「阻塞态 → 运行态」和「就绪态 → 阻塞态」**这两条转换。阻塞进程被唤醒只能先回就绪态排队。==

**易错点**：==**并非所有系统调用都会导致阻塞**==，只有需要等待外部事件的才会。`getpid()` 这种查一下就返回的不阻塞。

**易错点**：运行→阻塞是**主动**，阻塞→就绪是**被动**。这对不对称关系是判断题的常考点，和第 1 章「用户态↔内核态两个方向不对称」是同一种考法。

## KP8 进程的创建（真题高频）

**真题**：2010 考过导致创建进程的操作；2021 考过创建新进程时的操作；2020、2024 考过父进程与子进程的关系和特点。

**核心结论**：==进程控制操作都以**原语**形式实现——执行期间**不允许被中断**，不可分割，保证原子性和一致性。==

**父子进程关系**：

| 项目            | 说明                                  |
| ------------- | ----------------------------------- |
| 子进程**复制**父进程的 | ==程序代码、数据段、堆栈内容、**打开的文件描述符**、环境变量== |
| 子进程**独立拥有**   | 各自的 **PCB** 和**虚拟地址空间**             |

引起创建进程的事件：**==终端用户登录系统、作业调度启动批处理任务、系统提供服务、用户程序发起应用请求。==**

创建原语四步：

| 步   | 做什么                                                                 |
| --- | ------------------------------------------------------------------- |
| ①   | 分配唯一 **PID**，从系统 PCB 池申请一个**空白 PCB**。==PCB 耗尽则创建失败返回错误==            |
| ②   | 分配运行所需资源（内存、文件、I/O 设备），记录在 PCB 中。==资源**或从 OS 获得，或从父进程继承**==         |
| ③   | **初始化 PCB**：标识信息、处理机状态信息、调度与控制信息、内存与资源信息。==通常设为**最低优先级**==，除非用户显式要求 |
| ④   | 若允许参与调度，把 PCB **插入就绪队列**                                            |

**易错点**：子进程「复制」父进程状态，但==**不共享地址空间**==——各有独立的虚拟地址空间。这和线程共享地址空间形成对照（见 KP16）。

**易错点**：==新进程默认是**最低优先级**==，不是继承父进程优先级，也不是最高。

**易错点**：创建失败的典型原因是 **PCB 池耗尽**，不是内存不够（内存在第 ② 步才分配）。

> [!note] 我的笔记
> 父子进程本质是两个独立的进程，只是子进程可以拷贝父进程的内容且父子进程的关闭有一定的牵连

## KP9 进程的终止与级联终止（真题）

**真题**：2024 考过终止进程时的操作。

引起终止的三类事件：

| 类别   | 说明                                             |
| ---- | ---------------------------------------------- |
| 正常结束 | 完成预定任务后主动退出                                    |
| 异常结束 | 存储区越界、非法指令、特权指令违规、算术运算错误、I/O 故障、运行超时           |
| 外界干预 | ==操作员强制终止、OS 因资源不足或安全策略终止、**父进程通过系统调用终止子进程**== |

终止原语五步：

| 步   | 做什么                                      |
| --- | ---------------------------------------- |
| ①   | 按标识符**检索 PCB**，读取当前状态                    |
| ②   | 若正处于**运行态**，立即**剥夺 CPU**，并触发调度程序选下一个就绪进程 |
| ③   | **释放**其占用的所有系统资源，归还 OS                   |
| ④   | ==若支持**级联终止**，递归终止所有**子孙**进程；否则子孙继续运行==  |
| ⑤   | 把 PCB 从所在队列（或链表）中**移除**                  |

**核心结论**：==**级联终止**＝一个进程终止时其所有子孙进程也随之终止。但**并非所有 OS 都采用**这一策略。==

**Linux 的做法（常考对比）**：父进程终止时子进程**不会**被自动终止，而是由 **init 进程（PID = 1）收养**，继续正常运行。

**易错点**：==第 ② 步要先剥夺 CPU 再调度——「终止一个运行态进程会引起进程调度」是对的。==

**易错点**：==级联终止不是默认行为==。看到「父进程终止后子进程一定终止」要警惕，Linux 就是反例。

## KP10 阻塞原语与唤醒原语（真题高频）

**真题**：2018、2022、2023 考过进程阻塞的事件与分析；2014、2019 考过进程唤醒的事件与分析。

**核心结论**：**阻塞是进程的==主动行为**==，==所以**只有处于运行态的进程才能执行阻塞操作**。==

常见等待事件：请求系统资源暂时不可用、等待 I/O 完成、等待接收数据、等待信号量。

| Block（阻塞原语）三步                              | Wakeup（唤醒原语）三步               |
| ------------------------------------------ | ---------------------------- |
| ① 保存当前 CPU 现场（PC、状态寄存器）到其 **PCB**          | ① 在指定事件的**等待队列**中找到目标进程的 PCB |
| ② PCB 状态字段改为**阻塞态**，把 PCB 插入**所等待事件的等待队列** | ② 从等待队列**移出**，状态置为**就绪态**    |
| ③ 调用**调度程序**，从就绪队列另选一个进程投入运行               | ③ 把 PCB **插入就绪队列**，等调度程序选中   |

谁来唤醒：由内核的**中断处理程序**或**合作进程**调用 Wakeup。

**核心结论**：Block 与 Wakeup 是一对**作用相反的原语，==必须成对使用**==。==只 Block 而无人 Wakeup，该进程将**永久停留在阻塞态**，再也无法被调度。==

**易错点**：阻塞由**自己**调用（主动），唤醒由**别人**调用（被动）——一个进程不可能自己唤醒自己，因为它已经不在运行了。

**易错点**：阻塞原语第 ③ 步会**引起进程调度**。「进程阻塞自己后 CPU 空转」是错的。

> [!note] 我的笔记
> cpu永远不可能空转，实在没有进程了系统会给一个闲逛进程

## KP11 进程通信的分类与共享存储

**核心结论**：进程通信（IPC）＝进程之间的信息交换。

| 类别   | 用途                | 代表                |
| ---- | ----------------- | ----------------- |
| 低级通信 | 传递**控制信息**（同步、互斥） | **PV 操作**（2.3 节）  |
| 高级通信 | 高效传输**大量数据**      | 共享存储、消息传递、管道通信、信号 |

**共享存储**：进程地址空间本来相互隔离，==通过特殊的**系统调用**创建一段独立内存区域，**映射到多个进程的虚拟地址空间**，各进程直接读/写该区域来交换信息。==

教材图示：[[王道教材/27 王道操作系统/pictures/fig-2-3.jpg]]（图 2.3 共享存储）

**核心结论（这是共享存储最常考的一条）**：==OS **只负责分配共享内存区并完成地址映射，不自动提供同步保护**。读/写逻辑与同步控制（如信号量 P、V 操作）**必须由用户程序自己设计实现**。==

**记忆锚**：甲乙之间放一个公共大布袋，甲放进去、乙取出来。谁也不能直接伸手拿对方手里的东西，交换必须经过这个公共区域。

**易错点**：共享存储是**速度最快**的 IPC（直接读写内存，无内核拷贝），代价就是**同步得自己管**。看到「操作系统自动保证共享内存的互斥访问」直接判错。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 共享存储的内存区域就是进程映像里栈和堆夹在中间的那一块吗
> <span style="color: red;">答：位置猜对了，性质要改——它不是那块「空隙」本身（空隙是尚未建立映射的虚拟地址空间），而是 OS 通过系统调用在空隙里划出一段并建立映射，落在 KP5 表中「共享库的存储映射区」那一层。更要紧的是：共享发生在物理内存层面，各进程的虚拟地址可以完全不同，但页表指向同一组物理页帧。</span>

## KP12 消息传递

**核心结论**：没有共享内存、或出于安全考虑不便用共享存储时，用消息传递。数据交换以**格式化的消息**为单位，==通过 OS 提供的**发送原语和接收原语**进行==。底层细节封装在内核中，**对用户透明**。

两种基本模式：

| 模式   | 做法                                                   |
| ---- | ---------------------------------------------------- |
| 直接通信 | 发送进程**指定接收进程**；内核把消息从发送方复制到**接收方的内核缓冲队列**；接收进程用接收原语取 |
| 间接通信 | 双方**不直接指定对方**，通过中间实体**信箱**交换。发送方投递到信箱，接收方从信箱取        |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-2-4.jpg]]（图 2.4 消息传递）

**核心结论**：消息传递是目前**应用最广泛**的 IPC 机制。**微内核 OS 中微内核与服务器之间的交互就是基于消息传递**（呼应第 1 章 KP37）。它还很好地支持**多处理器系统、分布式系统和计算机网络**，是这些环境的主流通信方式。

**记忆锚**：甲写信交给邮差。直接通信＝邮差把信直接交到乙手里；间接通信＝乙家门口有邮箱，邮差投进去，乙自己来取。两种方式的投递都由邮差（内核）完成。

**易错点**：消息传递**要经过内核拷贝**，所以比共享存储慢，但**同步由内核负责**，用户不用自己加锁——和共享存储正好是一组权衡。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 如果信箱方式通信不指定对方那接收方怎么知道是发给自己的？
> <span style="color: red;">答：不指定的是「进程」，指定的是「信箱」——接收方主动 receive(信箱ID) 去取，路由靠信箱标识而不是 PID，所以双方可以互不相识、甚至生命周期不重叠（发完就退出，接收方过一会儿再来取）。这就是「间接」的全部含义：把收发双方的身份解耦了。</span>
> 
> 所有的进程共用一个信箱？
> <span style="color: red;">答：不是，信箱可建任意多个，分私用信箱（创建者独享读权限，一对一）、公用信箱（OS 创建，所有获权进程可读写，多对多）、共享信箱（创建者指定谁能共享）。由此通信关系有一对一 / 一对多 / 多对一 / 多对多四种，多对一就是客户-服务器模型。常考点：多个进程同时从同一信箱 receive 时，消息给谁是不确定的。</span>

## KP13 管道通信（真题）

**真题**：2014 考过管道通信的特点。

**核心结论**：管道基于==**先进先出**==原则，常用于**有亲缘关系的进程**（如父子进程）之间，==按**生产者-消费者**模式交换数据。==

| 视角 | 管道是什么 |
| --- | --- |
| 编程接口上看 | 一种**特殊的共享文件**，支持标准的 `read()` 和 `write()` |
| 实现上看 | **不是磁盘文件**，而是内核维护的一块**固定大小的内存缓冲区** |

管道必须提供的三方面协调能力：

| 能力     | 内容                                                 |
| ------ | -------------------------------------------------- |
| 互斥     | 任一时刻只允许一个进程对管道读或写                                  |
| 同步     | **管道满时写进程阻塞**，直到读进程取走部分数据；**管道空时读进程阻塞**，直到写进程写入新数据 |
| 写端关闭检测 | 写端关闭后，读端 `read()` **返回 0**，表明无数据可读                 |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-2-5.jpg]]（图 2.5 管道通信）

Linux 中管道的特点：

1. **固定缓冲区大小**——==内核中的**环形缓冲区**（如 64KB）==，不会像普通文件那样无限增长。缓冲区满时 `write()` 被阻塞。
2. **自动阻塞与唤醒**——读快于写时数据被读空，`read()` 被阻塞等写入。

管道由父进程通过 `pipe()` 系统调用创建。子进程创建时**继承父进程的文件描述符表**，所以能通过这些描述符访问同一管道。

**核心结论（两条必背）**：

- ==从管道读数据是**一次性操作**，数据一旦被读出，缓冲区空间即被释放供后续写入。==
- ==**普通管道只支持单向通信**，要双向必须**建两个管道**。==

**易错点**：管道的同步互斥是**内核自动提供**的（这点和共享存储相反，别混）。

**易错点**：「管道是文件所以存在磁盘上」是错的——它只是**接口像文件**，实体是内存缓冲区。

**易错点**：亲缘关系是因为要**继承文件描述符**，无亲缘关系的进程用普通管道通信不了（要用命名管道 FIFO）。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 跟信箱的区别？
> <span style="color: red;">答：管道是无边界的字节流，信箱是按条投递的有边界消息——这是唯一会考的差别。相同点反而更多：都用内核缓冲区、都由内核自动提供同步互斥、数据都是读走即消失，所以有些教材把管道视为消息传递的特例。其余差异：普通管道单向（双向要建两个）且要求亲缘关系（靠继承 fd），信箱天然多对多、只需知道 ID。</span>

## KP14 信号

**核心结论**：==信号（Signal）用来**通知进程某个事件已发生**==。不同系统事件对应不同信号类型，每类信号有一个序号。Linux 内核实现约 **30 种**信号，编号 1～30。

PCB 里用**两个 n 位向量**管信号（Linux 用 32 位整型）：

| 向量         | 作用                                    |
| ---------- | ------------------------------------- |
| 待处理信号向量    | 发送信号时内核把对应位**置 1**；信号被成功处理后对应位**清 0** |
| 阻塞（屏蔽）信号向量 | 某位为 1 表示该信号**不被立即处理**，而是暂存起来，直到解除阻塞   |

发送方式两种：

| 方式   | 说明                                                   |
| ---- | ---------------------------------------------------- |
| 内核发送 | 内核检测到特定系统事件时发。如进程执行**非法指令** → 发 **SIGILL**（序号 4）     |
| 进程发送 | 调用 `kill()` 请求内核向指定进程发（需提供目标 PID 和信号序号）。**也可以向自身发送** |

**核心结论（检查时机，常考）**：==OS **从内核态返回用户态时**（如系统调用结束）检查当前进程是否有**未被阻塞的待处理信号**==。若有，立即处理其中一个，**通常优先处理序号较小的**。

处理方式两种：

| 方式        | 说明                                            |
| --------- | --------------------------------------------- |
| 默认信号处理程序  | OS 为每类信号预设操作。如收到 SIGILL 默认**终止进程**            |
| 自定义信号处理程序 | 进程可自己定义处理函数，如收到 SIGILL 时输出 `hello world` 而不终止 |

信号处理程序执行结束后，**返回原程序被中断的位置**继续执行后续指令。

**易错点**：信号的检查点是**内核态返回用户态那一刻**，不是「随时立即处理」。这条呼应第 1 章的态切换机制。

**易错点**：信号可以被**屏蔽**（暂存不处理），但屏蔽不等于丢弃。

**易错点**：信号是**低数据量的通知机制**，不能用来传大量数据——它只传「发生了什么」，不传内容。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 为什么要放在内核态返回用户态的时候检查信号呢？
> <span style="color: red;">答：根本原因是信号处理程序是用户态代码，内核态下没法直接跳去执行它——只能在返回用户态那一刻修改即将恢复的上下文，把返回地址指向 handler，让进程回去先跑 handler，跑完再回原断点。另两个理由：① 返回时本来就要恢复上下文、访问 PCB，顺手比两个位向量几乎零成本，若要求「随时立即处理」就得在任意指令边界插检查，代价极大；② 此刻内核已放锁、原语已走完，状态干净，不会被用户代码破坏（呼应 KP8「原语不允许被中断」）。这和「中断只在指令边界才被响应」是同一种设计思路。补：纯用户态死循环也不会漏收信号，时钟中断会把它带进内核，中断返回时即处理，延迟上限一个时间片。</span>

## KP15 线程的基本概念与五个属性（真题）

**真题**：2011、2019、2024 考过线程的特点。

**核心结论（两个目的要分清）**：

| 引入什么 | 目的 |
| --- | --- |
| 引入**进程** | 让多道程序能并发执行，提高资源利用率和系统吞吐量 |
| 引入**线程** | 进一步**降低程序并发执行的时空开销**，提升并发性能 |

==线程＝「**轻量级进程**」，是程序执行流的最小单元，也是**处理器调度的基本单位**。==

**核心结论**：多线程 OS 中，==**进程不再是基本的执行实体**==，但仍保留与执行相关的状态。所谓进程处于「执行」状态，实际是指**该进程中的某个线程正在运行**。

五个属性：

| 属性      | 内容                                                                              |
| ------- | ------------------------------------------------------------------------------- |
| 轻量级执行实体 | ==**不拥有独立系统资源**（==地址空间、打开的文件），但有私有数据结构==：**线程 ID、程序计数器、寄存器集合、栈**，以及一个 **TCB**== |
| 共享代码段   | ==同进程内多线程可并发执行相同代码。如 Web 服务器进程开多个线程各服务不同用户请求==                                  |
| 资源共享    | 同进程内==所有线程共享**代码段、数据段、堆、文件描述符**==。通信和数据共享高效，**无须复杂的 IPC**                       |
| 独立调度单位  | 单 CPU 下靠时间片轮转轮流用 CPU；多 CPU 下可**并行运行于多个核心**，缩短进程整体处理时间                           |
| 生命周期    | 创建 → 就绪、运行、阻塞 → 终止                                                              |

**核心结论（引入线程后的分工，必背）**：==**进程成为除 CPU 外的系统资源分配单位，线程成为 CPU 调度和执行的基本单位。**==

**易错点**：同进程内的线程切换**不需要切换地址空间**，==所以开销远小于进程切换==。这是线程「轻」的根本原因。

> [!note] 我的笔记
> 线程共享堆但不共享栈

> [!question] 我的问题
> 在没有引入线程的os里，进程也是cpu调度和执行的基本单位吧？
> <span style="color: red;">答：对。未引入线程时进程既是资源分配单位、又是调度和执行单位；引入线程后拆开，进程只留资源分配，调度和执行归线程。答这类题先确认有没有「引入线程」这个前提。</span>

## KP16 线程与进程的比较：六个维度（真题）

**真题**：2012 考过进程和线程的比较。

| 维度     | 进程                                               | 线程                                                     |
| ------ | ------------------------------------------------ | ------------------------------------------------------ |
| 调度     | 传统 OS 中既是资源拥有者也是独立调度单位，每次调度需完整上下文切换，开销大          | **独立调度的基本单位**。同进程内线程切换**不引起进程切换**；跨进程的线程切换**仍会引起进程切换** |
| 并发性    | 进程之间可并发                                          | 进程间可并发 + **同进程内多线程可并发** + 不同进程的线程也能并发                  |
| 拥有资源   | **系统资源分配的基本单位**                                  | **不拥有独立系统资源**，只有必需的私有数据结构；共享所属进程的地址空间及资源               |
| 独立性    | 各有完全独立的地址空间，默认其他进程无法访问                           | 一个进程中的线程**对其他进程完全不可见**；同进程内线程共享地址空间、紧密协作               |
| 系统开销   | 创建/撤销需分配回收 PCB、地址空间、I/O 资源，开销显著；切换涉及整个地址空间和资源上下文 | 创建/撤销仅需分配栈和少量内核对象，开销很小；切换**只需保存恢复寄存器状态**。同步与通信非常容易     |
| 支持多处理器 | 单线程进程任一时刻**只能在一个 CPU 上执行**                       | 多线程进程可把多个线程**同时调度到多个 CPU 并行执行**                        |

**易错点（这条最常考）**：==「线程切换一定不引起进程切换」是错的。判据是**切换前后的线程是否属于同一进程**。==

**易错点**：线程「不拥有资源」指的是**不拥有独立的系统资源**，==不是「什么都没有」——它有 ID、PC、寄存器、栈这些私有数据结构。==

## KP17 线程的状态与生命周期

**核心结论**：==线程之间共享资源、存在同步互斥制约，执行过程有明显**间断性**==。三种基本状态：

| 状态  | 含义                           |
| --- | ---------------------------- |
| 运行态 | 已获得 CPU，正在执行                 |
| 就绪态 | 已具备所有运行条件，只需获得 CPU 即可执行      |
| 阻塞态 | 因等待某事件（I/O 完成、**锁释放**）暂时无法继续 |

这三种状态之间的转换与**进程基本状态的转换类似**（对照 KP7）。

生命周期：

| 阶段   | 说明                                                                                        |
| ---- | ----------------------------------------------------------------------------------------- |
| 创建   | 用户程序启动时通常**只有一个初始线程**，其主要任务是创建其他线程。==创建时传入**线程主函数入口地址、堆栈大小、调度优先级**等参数，成功后返回唯一的**线程标识符**== |
| 调度执行 | 调度器按优先级和调度策略决定谁获得 CPU；被调度后进入运行态，执行其主函数代码                                                  |
| 终止   | 正常执行完主函数、发生未处理异常被迫退出、主动调用终止函数、被其他线程通过**取消机制**强制终止                                         |

**核心结论（终止后的资源回收，容易漏）**：==大多数 OS 中线程终止后**不会立即释放资源**。只有当进程中的**其他线程执行了相应的分离操作**后，被终止的线程才与资源分离，资源才被回收。==

**已被终止但尚未释放资源的线程仍可被其他线程调用，以使其重新恢复运行。**

**易错点**：线程只有**三种**基本状态（==没有创建态、终止态的独立提法==），进程有五种。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 创建进程是由os进行的吧？那创建线程是由进程运行创建还是os创建？
> <span style="color: red;">答：进程一律由 OS 创建。线程看类型：用户级线程由进程内的线程库在用户态创建，内核不知道、不需要系统调用；内核级线程由 OS 创建，TCB 在内核区。</span>
> 
> 线程中止释放的是栈和TCB之类的资源吗？
> <span style="color: red;">答：是，释放的就是私有资源——TCB、私有栈、寄存器现场。共享的一概不动：堆、全局变量、代码段、文件描述符属于进程，所以线程 malloc 的内存不随它结束而释放。</span>
> 
> 线程执行分离操作是什么意思？
> <span style="color: red;">答：线程默认可结合（joinable），终止后要留着 TCB 等人来取；分离（pthread_detach）就是声明「不用等我，一结束就自动回收」。既不 join 也不 detach 就成僵尸线程，和进程不 wait() 完全对称。</span>

## KP18 TCB 与线程的私有资源（真题）

**真题**：2024 考过线程的私有资源。

TCB 通常包含六项：

| 项   | 内容                                  |
| --- | ----------------------------------- |
| ①   | 线程标识符 Thread ID                     |
| ②   | **寄存器集合**：程序计数器、状态寄存器、通用寄存器         |
| ③   | 线程当前状态                              |
| ④   | 调度优先级                               |
| ⑤   | **线程局部存储区**，保存线程私有数据                |
| ⑥   | **堆栈指针**，指向该线程的私有栈（过程调用时存局部变量、返回地址） |

**核心结论（私有 vs 共享，这是 2024 那道的核心）**：

| 线程**私有**                              | 线程**共享**（属于所在进程）                  |
| ------------------------------------- | --------------------------------- |
| 线程 ID、程序计数器、寄存器集合、**私有栈**、线程局部存储区、TCB | 地址空间、**全局变量**、代码段、数据段、**堆**、文件描述符 |

**易错点（关键细节）**：每个线程有独立的私有栈，但**这些栈位于进程的地址空间内**——所以技术上**一个线程可以访问另一个线程的栈内容**。但这严重违反编程规范，破坏封装性和正确性，实际开发中应严格避免。

==**易错点**：**栈是私有的，堆是共享的**。这一组对比几乎每年都以某种形式出现。==

## KP19 用户级线程 ULT（真题）

**真题**：2019 考过两种线程的特点与比较。

**核心结论**：==所有线程管理工作（创建、切换、撤销）均由**应用程序在用户空间（用户态）完成**==，无须 OS 介入，==**内核完全感知不到这些线程的存在**。==应用程序只需==引入**线程库**即可开发为多线程程序。==

教材图示：[[王道教材/27 王道操作系统/pictures/fig-2-6.jpg]]（图 2.6 用户级线程和内核级线程）

**调度不公平性（教材专门举例，容易考）**：==ULT 下**调度仍以进程为单位**，调度器只看得见进程，只给整个进程分一个时间片。==

| 假设每进程每次得 100ms    | 结果                              |
| ----------------- | ------------------------------- |
| 进程 A 有 1 个用户级线程   | 该线程独占全部 **100ms**               |
| 进程 B 有 100 个用户级线程 | 100ms 在 100 个线程间分配，每个平均 **1ms** |

A 中线程拿到的 CPU 时间是 B 中各线程的 **100 倍**，系统层面体现出明显的==**调度不公平性**。==

|     | 内容                                                                               |
| --- | -------------------------------------------------------------------------------- |
| 优点① | 线程切换**在用户空间完成，无须切换到内核态**，==避免模式切换开销==                                            |
| 优点② | ==**调度策略可由应用程序定制**，不同进程可用不同的线程调度算法==                                             |
| 优点③ | ==实现**与操作系统无关**，==线程管理代码属于用户程序的一部分，==**可移植性好**==                                 |
| 缺点① | **系统调用的阻塞问题**：某个线程执行阻塞型系统调用时，==**整个进程被内核挂起，进程内所有线程都被阻塞**==                       |
| 缺点② | **无法发挥多处理器并行优势**：内核只把该进程调度到一个 CPU 上，同进程的多个用户级线程**不能在不同 CPU 上并行**，只能在单个 CPU 上交替执行 |

**易错点**：缺点①的根源是**内核不知道线程存在**，它只能整个进程一起挂起。这一条是 ULT 所有缺点的总根源。

> [!note] 我的笔记
> 因为用户级线程阻塞的时候，内核看不到线程，这种情况下没有内核级线程所以进程是调度的基本单位，os认为整个进程都被阻塞，于是都被挂起。

## KP20 内核级线程 KLT

**核心结论**：线程管理**完全由 OS 内核负责**，所有线程操作均在**内核空间（内核态）**完成。OS 为每个内核级线程维护一个 **TCB**，内核通过 TCB 感知线程的存在并控制它。

| | 内容 |
| --- | --- |
| 优点① | **能发挥多处理器并行优势**：内核可把同进程的多个线程同时调度到不同 CPU 核心并行执行 |
| 优点② | **阻塞处理更灵活**：某线程因系统调用阻塞时，内核**仍可调度该进程中的其他线程**运行，或切到其他进程的线程 |
| 优点③ | **内核自身可采用多线程技术**，提升系统服务的并发性和整体效率 |
| 缺点 | **线程切换需从用户态陷入内核态**。线程在用户态运行而调度由内核完成，每次切换都涉及模式转换和上下文保存/恢复，**系统开销较大** |

**核心结论（ULT vs KLT 一句话对照）**：

| | ULT | KLT |
| --- | --- | --- |
| 内核是否感知 | **不感知** | **感知** |
| 调度单位 | 进程 | **线程** |
| 切换是否进内核态 | 不需要，快 | **需要，慢** |
| 一个线程阻塞 | **整个进程都阻塞** | 其他线程仍可运行 |
| 能否多核并行 | **不能** | **能** |
| 可移植性 | 好（与 OS 无关） | 差（依赖内核） |

**易错点**：==ULT 和 KLT 的优缺点几乎**处处相反**==，成对记最省力。核心分水岭只有一个：**内核知不知道线程的存在**。

## KP21 三种多线程模型

**核心结论**：**组合方式（混合模型）**——内核支持多个内核级线程的创建与调度，同时允许用户程序在用户空间管理多个用户级线程。三个好处：多线程可在多 CPU 并行、单线程阻塞不导致整个进程挂起、用户级线程切换在用户空间快速完成。

按用户级线程与内核级线程的**映射关系**分三种模型：

| 模型 | 映射 | 特点 |
| --- | --- | --- |
| 多对一 | 多个 ULT → **1 个** KLT | 调度和管理在用户空间。每进程仅一个 KLT，**仅当用户线程需访问内核时才映射，且每次只允许一个线程映射** |
| 一对一 | 每个 ULT → **一个独立** KLT | 一一对应，**调度由内核完成，需切换到内核态** |
| 多对多 | **n 个 ULT → m 个 KLT，要求 n ≥ m** | ULT 由应用程序在用户空间调度，KLT 由内核调度到多个 CPU 执行 |

各自优缺点：

| 模型 | 优点 | 缺点 |
| --- | --- | --- |
| 多对一 | 线程管理在用户空间，**无须切换到内核态，切换效率高** | 任一 ULT 执行阻塞型系统调用时**整个进程被挂起**；任何时刻**最多一个线程与内核交互**，无法多处理器并行 |
| 一对一 | 某线程阻塞时内核可调度同进程其他线程，**支持真正的并发，可多 CPU 并行** | 每创建一个用户线程就必须创建一个对应内核线程，**开销大**（内核 TCB 占内存、调度负担增加），**限制了可支持的最大线程数** |
| 多对多 | 既克服多对一并发度低，又避免一对一开销过大；**ULT 切换高效 + 支持多核并行 + 阻塞隔离** | — |

教材图示（图 2.7 多线程模型，教材里拆成三张）：[[王道教材/27 王道操作系统/pictures/2-1-image-007.jpg]]（多对一）、[[王道教材/27 王道操作系统/pictures/image-008.jpg]]（一对一）、[[王道教材/27 王道操作系统/pictures/image-009.jpg]]（多对多）

**易错点**：多对一模型本质就是纯 ULT，一对一本质就是纯 KLT，所以它们的优缺点分别照抄 KP19、KP20，不用另记一套。

**易错点**：==多对多的约束是 **n ≥ m**（用户级线程数不少于内核级线程数），反过来写就错了。==

> n如果小于m，总有一个内核级进程是空的，所以没这个必要

## KP22 线程库

**核心结论**：程序员通过线程库提供的 **API** 创建和管理线程。实现有两种方式：

| 实现方式    | 说明                                                     | 对应模型      |
| ------- | ------------------------------------------------------ | --------- |
| 纯用户空间实现 | 线程库完全位于用户空间，代码和数据结构均在用户态。==调用库函数**仅触发本地过程调用，无须陷入内核**== | **用户级线程** |
| 内核支持实现  | 线程库底层依赖内核，==API 调用通常**会触发系统调用**，由内核完成实际线程操作==          | **内核级线程** |

三种主流线程库：

| 线程库 | 归属 |
| --- | --- |
| **POSIX Pthreads** | POSIX 标准定义的线程 API，**具体实现可基于用户级或内核级** |
| **Windows 线程 API** | 直接构建于 Windows 内核之上，属**内核级线程**实现 |
| **Java 线程 API** | JVM 运行于宿主 OS 之上，通常**调用宿主系统的线程库**：Windows 上用 Windows API，类 UNIX 上用 Pthreads |

**易错点**：Pthreads 是**标准（API 规范）**，不是某一种实现——所以它既可以是用户级也可以是内核级。问「Pthreads 属于哪种线程」不能一口答定。

## KP23 本节小结：引入进程解决了什么

**核心结论**：引入进程解决了多道程序并发执行的**三大问题**——正好对应第 1 章讲的并发带来的三个破坏：

| 问题 | 进程怎么解决 |
| --- | --- |
| 失去封闭性 | 通过**地址空间隔离**，为每个程序提供独立、受保护的执行环境 |
| 执行过程的间断性 | 利用 **PCB 保存和恢复执行上下文**，确保中断后能准确连续地继续执行 |
| 结果不可再现性 | **进程的隔离机制 + OS 的调度策略**共同保障执行的可控性与结果可再现性 |

**记忆锚（教材的类比）**：进程 = 人的生命历程。生命历程是动态的过程而非静态描述；主体是「人」对应**进程映像**（程序段 + 数据段 + PCB）；**PCB 就是身份标识**。人从「充满斗志」（就绪）到「发奋图强」（运行），遇挫折陷入「失落」（阻塞），受鼓励重回「充满斗志」（就绪）——正是就绪→运行→阻塞→就绪的迁移。

**易错点**：这三大问题的表述和第 1 章 KP10（异步性）是同一条线索——**只要正确使用同步机制，结果的可再现性是有保障的**，不是「并发就一定不可再现」。

# 2.2 CPU 调度

## KP24 CPU 调度的基本概念

**核心结论**：CPU 调度指按一定算法（兼顾**公平性与效率**），从**就绪队列**中选出一个进程，把 CPU 分配给它运行，从而实现多个进程的并发执行。

- 前提：多道程序系统里进程数远多于 CPU 数，争用 CPU 不可避免。
- 地位：==CPU 调度是**多道程序操作系统的基础**==，也是 OS 设计的核心问题之一。

**易错点**：==调度的候选集合是**就绪队列**==，不是「所有进程」。阻塞态进程不参与 CPU 调度，得先被唤醒进就绪队列。

## ==KP25 调度的三个层次==

教材图示（图 2.8 CPU 的三级调度）：[[王道教材/27 王道操作系统/pictures/fig-2-8.jpg]]

**核心结论**：一个作业从提交到完成要经历三级调度。

| 层次   | 别名       | 做什么                                               | 调度范围       | 频率           | 是否必备              |
| ---- | -------- | ------------------------------------------------- | ---------- | ------------ | ----------------- |
| 高级调度 | **作业调度** | 从外存后备队列挑作业，==分配内存/IO 设备，**创建进程**，使其获得竞争 CPU 的资格== | 外存 ↔ 内存    | 最低           | 批处理系统配备，分时/实时一般不设 |
| 中级调度 | **内存调度** | ==把暂时不能运行的进程换出外存（**挂起态**），条件满足再换入（恢复为就绪态）==       | 内存 ↔ 外存    | 中            | 选择性配置             |
| 低级调度 | **进程调度** | 按算法从就绪队列选进程，把 CPU 分给它                             | 就绪队列 → CPU | 最高（几十 ms 一次） | **所有 OS 必须有**     |

- 作业调度：每个作业在整个生命周期中**仅被调入一次、调出一次**。==分时/实时系统里用户进程由交互式命令直接创建，所以一般不设独立的作业调度模块。==
- 中级调度：本质就是**存储管理中的对换（swap）功能**，目的是提高内存利用率和系统吞吐量。
- ==三级配合：作业调度做**准备**（拿到参与调度的资格）→ 中级调度做**调节**（动态调整内存中活跃进程数）→ 进程调度**驱动执行**（并发的核心机制）。==
- 频率排序：**进程调度 > 中级调度 > 作业调度**。

**易错点**：
- ==只有**进程调度不可或缺**==，作业调度、中级调度都是按系统类型选配。
- 「只调入一次、调出一次」说的是**每个作业**，不是整个系统只调度一次。
- 挂起态是**中级调度**换出产生的，别和阻塞态混为一谈（阻塞在内存，挂起在外存）。

## KP26 进程调度的三项任务

**核心结论**：

1. **保存 CPU 现场信息**。==把当前进程的 CPU 状态（PC、通用寄存器等）完整保存到它的 **PCB** 中，保证以后能从断点恢复。==
2. **选取待运行进程**。按算法（时间片轮转、优先级等）从就绪队列挑一个，状态由**就绪态改为运行态**。
3. **完成 CPU 分配**。由**分派程序**把选中进程 PCB 里保存的 CPU 现场**装回处理器寄存器**，交出 CPU 控制权，从断点继续执行。

**易错点**：注意分工——「选谁」是调度程序做的决策，「把现场装回寄存器、真正交出 CPU」是**分派程序**做的执行。

## KP27 调度程序的三个组成部分

教材图示（图 2.9 调度程序的结构）：[[王道教材/27 王道操作系统/pictures/fig-2-9.jpg]]

**核心结论**：实现 CPU 调度与分派的软件叫调度程序，由三部分组成。

| 部件         | 职责                                                      |
| ---------- | ------------------------------------------------------- |
| **排队器**    | ==把所有就绪进程按策略组织成一个或多个**就绪队列**==；每当有进程转为就绪态就把它插入相应队列      |
| **分派器**    | 执行实际的 CPU 分配：==从就绪队列**移出**目标进程、**触发上下文切换**、交出 CPU 控制权== |
| **上下文切换器** | ==完成现场的保存与装入==                                          |

**两对上下文切换**（易考）：

1. ==第一对：把**当前进程**的上下文保存到它的 PCB，再装入**分派程序**的上下文，让分派程序能跑。==
2. ==第二对：移出**分派程序**的上下文，把**新选进程**的 CPU 现场装入 CPU 各寄存器。==

- 开销来源：==上下文切换要执行**大量 load / store 指令**保存和恢复寄存器，开销大。==
- 硬件优化：==设**两组寄存器**（一组内核用、一组用户用），切换时只改指针指向当前所需的寄存器组，不必真搬数据。==

**易错点**：一次进程切换里发生的是==**两对**（四次）上下文装卸==，中间要过一趟分派程序，不是「保存旧的、装入新的」两步就完。

> 上下文切换器的作用在哪？之前不是提到由硬件保存pc和psw，os保存别的，这个切换器就是统筹这些工具？
> <span style="color: red;">答：两件事不同层次。硬件保存 PC/PSW 是中断隐指令、服务模式切换（这两个寄存器软件来不及救）；上下文切换器只管换人时把通用寄存器、内存管理信息、进程状态 load/store 进 PCB——它不是统筹者，它本身就是那串 load/store。分派器发起，切换器搬运。</span>

## KP28 可以进行调度与切换的时机

**真题**：可以进行 CPU 调度的事件或时机（2012、2021）

**核心结论**：==调度程序是**内核程序**==，只有请求调度的事件发生后才运行；调度出新进程之后才进行切换。理论上「请求 → 调度 → 切换」顺序执行，但实际内核里满足条件也不一定能立刻调度。

需要调度与切换的典型情形：

1. **创建新进程后**——父子进程都是就绪态，调度程序可合法地选其中任一个先运行。
2. **进程正常结束或异常终止后**——必须从就绪队列另选一个；若无就绪进程，就运行**闲逛进程**。
3. **进程主动阻塞时**——因 I/O 请求、信号量操作等原因阻塞，必须调度其他进程。
4. **I/O 完成发出中断后**——等待 I/O 的进程由阻塞态转就绪态，此时要决定是让它上 CPU 还是让被中断的进程接着跑。

==抢占式系统额外两条：**更高优先级进程进入就绪队列**、**当前进程时间片用完**。==

进程切换的动作：把原进程上下文（PC、寄存器状态等）保存到它的 **PCB 或内核栈**；从新进程的 PCB 或内核栈加载上下文，更新地址空间信息（如页表基址），重置 PC，开始执行。

**易错点**：
- 情形 1、4 是「**可以**调度」，不是「必须切换」——父/子、被中断者/新就绪者都合法，取决于算法。
- ==情形 2 是「**必须**从就绪队列选一个」。==
- ==非抢占系统里==，「更高优先级进程到来」和「时间片用完」==都**不**触发调度。==

## KP29 不能进行调度与切换的时机

**核心结论**：三种情况下**不能**调度和切换。

1. ==**处理中断的过程中**==。理由两条：① 中断处理逻辑复杂，实现上难以安全切换；② ==中断处理属内核工作，**逻辑上不隶属于任何用户进程**，不应被剥夺 CPU。==
2. **进程处于操作系统内核程序临界区中**。这类临界区访问的是**内核数据结构**（就绪队列、PCB 链表等）。根本原因是**自指**：调度本身就要读写这些结构，若此刻切换，调度程序会读到被改到一半的链表；而且内核临界区通常靠**加锁 + 屏蔽中断**进出，连时钟中断都进不来，物理上也无法调度。
3. ==**执行原子操作的过程中**==。如加锁/解锁、中断现场的保护与恢复，==这类操作要**屏蔽中断**来保证原子性==——连中断都禁了，更不能调度切换。

**内核程序临界区 vs 普通临界区**（这是本节 06 题、2.2 节 41 题的唯一考点）：

| 临界区类型 | 访问什么 | 能否调度 |
| --- | --- | --- |
| **内核程序**临界区 | 内核数据结构（就绪队列、PCB 链表） | **不能**。调度自身要用这些结构，期间通常屏蔽中断 |
| 普通临界区 | 普通临界资源（打印机等） | **能**。占用时间可能很长，禁止调度会严重降低系统效率；还可能因申请不到资源而主动阻塞 |

补充机制：若在不可调度期间发生了调度条件，==系统会**置一个调度请求标志**，等临界区或中断处理结束后再按标志执行调度与切换。==

**易错点**：不是「发生了调度事件就一定立刻调度」。禁止期只是==**延迟**==调度（靠标志位记账），不是丢弃这次调度请求。另一个高频错项是把「内核程序临界区」写成「临界区」——**见到「临界区 → 不能调度」，先找「内核程序」这四个字，没有就是错项。**

## KP30 两种进程调度方式

**核心结论**：调度方式回答的是「进程正在跑，来了更紧迫的进程，CPU 给谁」。

| 方式      | 别名    | 行为                        | 让出 CPU 的时机                                             | 优缺点 / 适用                                          |
| ------- | ----- | ------------------------- | ------------------------------------------------------ | ------------------------------------------------- |
| **非抢占** | 非剥夺方式 | 当前进程继续跑，==高优先级进程只能等==     | ==运行完成（正常结束/异常终止），或**主动**因事件进入阻塞态（等 I/O、执行 Block 原语）== | ==实现简单、开销小==；无法满足分时和大多数实时系统的及时响应要求。==适用于早期批处理系统== |
| **抢占**  | 剥夺方式  | 调度程序可暂停当前进程，把 CPU 给更紧迫的进程 | 上述情形 + **被剥夺**                                         | ==提高吞吐率和响应效率；开销大==                                |

抢占必须遵循的原则：==**优先级原则、短进程优先原则、时间片原则**。==

**易错点**：
- 非抢占方式下进程让出 CPU 一定是**自身原因**（跑完或自己阻塞），外部事件动不了它。
- 抢占不是「随意打断」，必须依据上述三类原则之一。

## KP31 闲逛进程

**核心结论**：进程切换时若系统中**没有就绪进程**，OS 就调度**闲逛进程（Idle）**运行。

- **PID = 0**。
- 优先级**最低**，只在无其他就绪进程时运行；一旦有新进程进就绪队列，**立即让出 CPU**。
- 主要任务：在空闲循环里**不断检测中断请求**。
- 不占用除 CPU 外的任何系统资源，**也不会因等待事件而被阻塞**。

**易错点**：闲逛进程永远不阻塞（它不等任何事件），所以它只在「运行 ↔ 就绪」之间来回，永远不会进阻塞态。

## KP32 两种线程的调度

**核心结论**：

|          | **用户级线程 ULT**                 | **内核级线程 KLT**                                           |
| -------- | ----------------------------- | ------------------------------------------------------- |
| 内核调度的对象  | **进程**（内核不知道线程存在），CPU 时间给整个进程 | **线程**本身                                                |
| 谁决定跑哪个线程 | ==进程内部的**用户级线程库**==           | **内核**                                                  |
| 时间片      | ==整个进程共用一个时间片，库在内部再分==        | **每个线程可单独被赋予时间片**                                       |
| 切换开销     | 同进程内完成，只保存少量寄存器，**开销极小**      | 完整上下文切换 + 地址空间更新（跨进程时）+ 可能的 TLB 刷新和 Cache 失效，**开销高出数倍** |
| 阻塞影响     | 一个线程阻塞（如 I/O），**整个进程被阻塞**     | 只有该线程被挂起，同进程其他线程可继续                                     |

**易错点**：==ULT 里线程切换**不需要内核介入**==，所以不发生模式切换；==KLT 的线程切换必须陷入内核态==。「线程数多就一定快」在 ULT 里不成立——==一次阻塞全员停摆。==

## KP33 调度的目标（评价指标与公式）

**真题**：作业执行的相关计算（2012、2016、2018、2019、2023、2024）

**核心结论**：五类衡量标准。

1. **CPU 利用率**

$$\text{CPU 利用率} = \frac{\text{CPU 有效工作时间}}{\text{CPU 有效工作时间} + \text{CPU 空闲等待时间}}$$

2. **系统吞吐量**：单位时间内完成的作业数。==长作业占 CPU 多，拉低吞吐量；短作业提升吞吐量。==

3. **周转时间**：从**作业提交**到**作业完成**的总时间，含等待、就绪排队、CPU 执行、I/O 的全部时间。

$$\text{周转时间} = \text{完成时间} - \text{提交时间}$$
$$\text{平均周转时间} = \frac{\sum \text{各作业周转时间}}{n}$$
$$\text{带权周转时间} = \frac{\text{周转时间}}{\text{实际运行时间}}$$
$$\text{平均带权周转时间} = \frac{\sum \text{各作业带权周转时间}}{n}$$

4. **等待时间**：==进程在**就绪队列中**等待 CPU 的总时间==。调度算法**不影响**作业的实际执行时间和 I/O 时间，**只影响它在就绪队列里等多久**——所以等待时间是评价调度算法的核心指标。

5. **响应时间**：从提交请求到系统==**首次产生响应**的时间==。交互式系统里比周转时间更有实际意义。

结论性判断：==**不存在**同时满足所有用户需求和系统目标的调度算法==。设计时要兼顾特定场景要求、系统整体效率、以及**调度算法自身的实现开销**。

**易错点**：
- ==算作业完成时间时，**CPU 与 I/O 设备之间、不同 I/O 设备之间可以并行**——这是画时间轴的关键，别串行硬加。==
- ==带权周转时间的分母是**实际运行时间**（服务时间）==，不是周转时间；==带权周转时间**恒 ≥ 1**。==
- 等待时间只算**就绪队列里的等待**，==等 I/O 的阻塞时间不计入。==

## KP34 进程切换与上下文切换流程

**真题**：进程调度前后 CPU 模式的变化（2023）；进程的上下文切换（2024、2025）

**核心结论**：进程的创建、撤销、请求 I/O 都要==通过系统调用进内核完成==，==**进程切换同样在内核支持下实现**——任何进程都是在内核支持下运行的。==

**上下文切换**：把 CPU 从一个进程切到另一个进程，需保存当前进程状态、恢复另一进程状态。进程上下文由其 **PCB** 表示，包括 **CPU 寄存器的值、进程状态、内存管理信息**。

五步流程：

1. **挂起**当前进程，把它的 CPU 上下文**保存到其 PCB** 中。
2. 把该进程的 **PCB 移入相应队列**（就绪队列，或因等待事件进入的阻塞队列）。
3. **选择另一个进程**执行，更新其 PCB 中的相关信息。
4. **恢复**新进程的 CPU 上下文。
5. **跳转**到新进程 PCB 中程序计数器所指的位置，开始执行。

开销：单次切换只有微秒量级，但高负载下每秒几十上百次，累积消耗可观。==优化手段是**多组寄存器 + 切换寄存器组指针**==，但大多数通用处理器仍需完整保存恢复。

**易错点**：==上下文切换**只能由内核完成**，整个过程运行在**内核态**==（因为要访问和修改 PCB 这类内核数据结构）。

> [!question] 我的问题
> 切换寄存器组指针具体是怎么实现优化上下文切换开销的，举个简单一点的例子？
> <span style="color: red;">答：设两组寄存器 Bank0/Bank1 加一个当前组指针 CRP，指令里写的 R0 经 CRP 映射到某一组；切进程只改 CRP，一条指令，旧值原封不动留在原组，零次数据搬运。本质是把「搬数据」换成「改映射」。局限：组数固定（2 组、8 组），进程数远多于组数，用完照样往内存搬。</span>

## KP35 上下文切换 vs 模式切换，调度 vs 切换

**核心结论**：两组极易混的概念。

| | **模式切换** | **上下文切换** |
| --- | --- | --- |
| 发生范围 | **同一进程内部**（用户态 ↔ 内核态） | **两个进程之间** |
| 当前进程是否改变 | **不变** | **改变** |
| 典型场景 | 系统调用、中断进内核，完成后返回用户态继续执行**该进程** | 进程调度后真正换人 |
| 是否涉及 PCB 存取 | 不涉及换人的 PCB 操作 | 必须保存旧 PCB、恢复新 PCB |

推论：==**模式切换不一定引起上下文切换**==（系统调用返回后还是原进程）；==但**上下文切换必然发生在内核态**，必然伴随模式切换。==

|     | **调度**                 | **切换**                  |
| --- | ---------------------- | ----------------------- |
| 性质  | **决策**行为：决定把 CPU 给哪个进程 | **执行**行为：实际完成 CPU 控制权转移 |
| 顺序  | 先调度做决策                 | 后触发上下文切换实现决策            |

**易错点**：一次中断/系统调用发生了模式切换，但如果返回后还是原进程，那**没有**上下文切换、也**没有**进程切换。「进入内核态 = 换进程」是典型错判。

> [!note] 我的笔记
> 系统调用只保证模式切换，**阻塞了才换人**：「系统调用一定引起进程切换」错，「可能引起」对。内核态代码不是另一个进程，是同一个进程的另一副面孔（用的还是它自己的内核栈，CPU 时间还记在它头上）。

> [!question] 我的问题
> 这里的进程是相对于用户进程而言？如果进入内核态一般都是要执行系统调用例程，这种os程序不算这上面讲的进程？
> <span style="color: red;">答：这里的「进程」就是有 PCB 的执行实体，内核自己的进程也算，不是只指用户进程。系统调用服务例程不算进程，它是原进程借内核态身份在跑——当前进程不变、用它自己的内核栈、CPU 时间记它头上，所以只是模式切换。</span>

## KP36 先来先服务 FCFS

**真题**：各种调度算法的特点与对比（2009、2011、2014）；FCFS 调度算法的思想（2017）；批处理系统中作业完成时间的分析（2012、2016）

**核心结论**：选**最早进入队列**的那个。**作业调度、进程调度都能用**。

- 作业调度：从后备作业队列选最早进入的作业调入内存、分配资源、建进程、进就绪队列。
- 进程调度：从就绪队列选最早进入的进程，运行**直到完成或阻塞**才交出 CPU。
- ==属**非抢占式**。==

教材例（提交 8.0 / 8.4 / 8.8 / 9.0，运行 2 / 1 / 0.5 / 0.2）：

| 作业 | 提交 | 运行 | 开始 | 等待 | 完成 | 周转 | 带权周转 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 8 | 2 | 8 | 0 | 10 | 2 | 1 |
| 2 | 8.4 | 1 | 10 | 1.6 | 11 | 2.6 | 2.6 |
| 3 | 8.8 | 0.5 | 11 | 2.2 | 11.5 | 2.7 | 5.4 |
| 4 | 9 | 0.2 | 11.5 | 2.5 | 11.7 | 2.7 | 13.5 |

平均等待 1.575，平均周转 2.5，平均带权周转 5.625。

特点小结：

- 实现简单，但效率低。看似公平，实际**长作业先到会让大量短作业久等**，不适合作分时/实时系统的主调度策略。
- **有利于长作业，不利于短作业**（相对 SJF、高响应比）。
- ==**有利于 CPU 繁忙型作业，不利于 I/O 繁忙型作业**：I/O 型本可频繁让出 CPU 提高并发，但排在长作业后面就发挥不出来。==
- 常作为**辅助规则**嵌进其他策略：优先级相同的多个进程按 FCFS 排。

**易错点**：FCFS 排序依据是「**进入队列的时刻**」而不是「作业提交时刻」——作业调度里两者一致，进程调度里一个进程可能多次进出就绪队列。

## KP37 短作业优先 SJF / 短进程优先 SPF

**真题**：SJF 调度算法的思想（2017）；饥饿现象的含义（2016）

**核心结论**：按**预计运行时间**最短者优先。作业调度里叫 SJF，进程调度里叫 **SPF（短进程优先）**。

同一组作业改用 SJF：

| 作业 | 提交 | 运行 | 开始 | 等待 | 完成 | 周转 | 带权周转 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 8 | 2 | 8 | 0 | 10 | 2 | 1 |
| 2 | 8.4 | 1 | 10.7 | 2.3 | 11.7 | 3.3 | 3.3 |
| 3 | 8.8 | 0.5 | 10.2 | 1.4 | 10.7 | 1.9 | 3.8 |
| 4 | 9 | 0.2 | 10 | 1 | 10.2 | 1.2 | 6 |

平均等待 1.175，平均周转 2.1，平均带权周转 3.525——三项都优于 FCFS。

三个缺点：

1. ==**对长作业不利**，甚至产生**饥饿**：后备队列里的长作业，只要短作业不断到达，就一直排不上。==
2. **未考虑紧迫程度**，只看运行时间长短，无法保证紧迫作业及时处理。
3. 「长短」靠**用户估计值**，用户可能故意低报来抢调度优势，算法目标被架空。

抢占版本：SPF 默认**非抢占**；抢占式版本叫**最短剩余时间优先（SRTN）**——==新进程到达时，若其估计运行时间 < 当前进程**剩余**执行时间，则立即抢占。==

**核心结论（最优性）**：==当**所有作业同时到达且运行时间已知**时，SJF 的平均等待时间和平均周转时间**最优**。==

**易错点**：
- **饥饿**是「调度策略导致的无限期等待」，和死锁的**环形等待**有本质区别——饥饿的进程不持有资源阻塞别人。
- 最优性有**前提**（同时到达 + 时间已知），去掉前提就不能说 SJF 平均周转时间最短。
- 抢占版比较的是「新到达者的估计运行时间」vs「当前进程的**剩余**时间」，不是两者的总运行时间。

> [!note] 我的笔记
> 抢占式的是看剩余时间决定是否要抢占

> [!question] 我的问题
> 最优性是否跟哈夫曼树有关？
> <span style="color: red;">答：不是同一个定理，但目标函数同形——都是「大系数配小数值」的乘积和（每个作业的运行时间要被排在它后面的所有作业各等一遍）。SJF 的最优性用交换论证证：相邻两个把长的换到后面，其余不受影响而总等待时间必减少。408 不考两者联系，要记的是前提：同时到达＋运行时间已知，到达时间不同时最优的是 SRTN。</span>

## ==KP38 高响应比优先调度算法==

**核心结论**：主要用于**作业调度**，是 FCFS 与 SJF 的**综合平衡**——同时考虑等待时间和估计运行时间。每次调度时算出后备队列中每个作业的响应比，==选**响应比最高**的调入执行。==

$$\text{响应比} = \frac{\text{等待时间} + \text{估计运行时间}}{\text{估计运行时间}}$$

三条推论：

1. **等待时间相同**时，运行时间越短响应比越高 → 有利于短作业，像 SJF。
2. **估计运行时间相同**时，等待时间越长响应比越高 → 体现 FCFS 的公平性。
3. 长作业的响应比**随等待时间不断提高**，等够久就能被调度 → **有效避免饥饿**。

**易错点**：
- 响应比 = (等待 + 运行)/运行 = 1 + 等待/运行，所以**恒 ≥ 1**，形式上等于「带权周转时间」的预测值。
- ==缺点是**每次调度都要重算所有作业的响应比，开销大**。==
- ==它是**非抢占**的。==

> [!note] 我的笔记
> 

> [!question] 我的问题
> 为啥这响应比不能直接写成等待/运行，还非要加个1？
> <span style="color: red;">答：排序上完全等价（只差一个常数），加 1 是定义需要——响应比就是带权周转时间的预测值（周转/运行），分子必须是「提交到完成」的完整时间，才有恒 ≥ 1；否则刚到达的作业算出 0，含义就反了。考试写原式，写成 等待/运行 判错；手算可以只比 等待/运行 再统一加 1。</span>

## KP39 优先级调度算法（抢占/非抢占、静态/动态）

**真题**：优先级调度算法的应用分析（2025）；非抢占式优先级调度（2018）；抢占式优先级调度（2022、2023）；静态优先级和动态优先级的分析（2016）；调整进程优先级的合理时机（2010）

**核心结论**：给每个作业/进程一个优先级反映紧迫程度，作业调度选后备队列中优先级最高的，进程调度选就绪队列中优先级最高的。

按是否允许抢占分两类：

| 类型 | 高优先级进程到来时 | 何时换人 |
| --- | --- | --- |
| **非抢占式优先级** | 当前进程**继续执行** | 当前进程因**自身原因**（完成或等待事件）让出 CPU 时，才选就绪队列中优先级最高的 |
| **抢占式优先级** | **立即暂停**当前进程 | 马上把 CPU 交给更高优先级进程 |

按创建后是否可变分两类：

| 类型 | 定义 | 依据 / 特点 |
| --- | --- | --- |
| **静态优先级** | 创建时确定，**整个运行期间不变** | 依据：进程类型、资源需求、用户指定。优点实现简单、开销小；缺点不灵活，**可能饥饿** |
| **动态优先级** | 创建时给初值，随进程推进或**等待时间增加**而动态调整 | 等待越久优先级越高，初始低的进程等够久也能获得 CPU，**可防饥饿** |

**易错点**：静态优先级会饿死低优先级进程；==要防饥饿必须用**动态优先级**（随等待时间提升==）。别把「抢占/非抢占」和「静态/动态」这两个维度混成一个。

## KP40 优先级设置的三条原则

**真题**：进程优先级的设置：I/O 型和计算型（2013）

**核心结论**：实际系统中优先级高低遵循三条：

1. ==**系统进程 > 用户进程**。==系统进程管核心资源和服务。
2. ==**交互型进程 > 非交互型进程**==（前台 > 后台）。==交互型要快速响应用户输入。==
3. ==**I/O 型进程 > 计算型进程**。==

第 3 条的理由要会说：I/O 设备（如打印机）比 CPU 慢得多。==把 I/O 型进程优先级提高，它能**尽快拿到 CPU 并启动 I/O 操作**，让慢速 I/O 设备**尽早开始工作**，从而与 CPU 并行，**提高系统整体吞吐量**。==

**易错点**：I/O 型优先不是因为它「更重要」，==而是因为它**只需很短的 CPU 时间就能去驱动慢设备干活**==，是拿小成本换设备并行度。反过来把计算型排前面，I/O 设备就一直闲着。

## KP41 时间片轮转 RR

**真题**：时间片轮转调度算法的原理（2021、2024）；时间片轮转调度算法的特点（2017）

**核心结论**：主要用于**分时系统**，==最大特点是**公平性**==。所有就绪进程按 **FCFS** 组织成一个就绪队列；每隔一个固定时间片（如 30 ms）产生一次**时钟中断**，激活调度程序，把 CPU 分给队首进程执行一个时间片。时间片用完即使没跑完也**必须被剥夺 CPU**，重新插入就绪队列**末尾**。

两个调度时机：

1. 进程在时间片结束**前已完成** → 立即激活调度程序做进程切换。
2. **时间片用尽** → 由**时钟中断处理程序**触发调度程序，完成上下文切换。

时间片大小的影响：

| 时间片 | 后果 |
| --- | --- |
| **过大** | 大到每个进程都能在一个时间片内跑完时，**RR 退化为 FCFS**，无法满足短作业和交互用户的快速响应 |
| **过小** | 频繁调度和上下文切换，**系统开销剧增**，真正执行用户程序的 CPU 时间反而减少 |

取值依据：系统期望响应时间、就绪队列中进程数量、系统处理能力。交互式系统以「**典型交互**」为基准（输入一个字符、按一次回车，几十到上百毫秒），==合理的时间片应**略长于一次典型交互所需时间**。==

**易错点**：RR 是**抢占式**的，==抢占依据是**时间片原则**（靠时钟中断）==，不是优先级。「时间片用完 → 时钟中断 → 调度」这条链子要能完整说出来。

## KP42 多级队列调度算法

**核心结论**：前述算法只有一个就绪队列、单一固定策略，满足不了不同类型进程的差异需求（交互型要响应快，批处理要吞吐高）。==多级队列把就绪进程**划分成多个独立的就绪队列**==，每类进程一个队列（系统进程、交互型、批处理……）。

两个要点：

1. **每个队列可独立采用适合自己的调度算法**。交互型队列用 RR 保响应，批处理队列用 FCFS 或 SJF 提吞吐。
2. **各队列本身有不同优先级**。调度时总是优先调度高优先级队列的进程，**只有所有高优先级队列都空**，才轮到低优先级队列。

**易错点**：多级队列的进程**固定在自己的队列里**，不会因为跑得久而降级——「队列间移动」是**多级反馈队列**的特性，两者别混。

## KP43 多级反馈队列调度算法

教材图示（图 2.10 多级反馈队列调度算法）：[[王道教材/27 王道操作系统/pictures/fig-2-10.jpg]]

**真题**：多级反馈队列调度算法的应用分析（2019）；实现思想（2020）

**核心结论**：**时间片轮转 + 优先级调度**的综合与发展，融合前几种算法的优点。

实现机制三条：

1. **设多个就绪队列**，第 1 级优先级最高，依次降低。==**优先级越高的队列，时间片越小**==；第 *i*+1 级的时间片通常是第 *i* 级的 **2 倍**。
2. **每个队列内部用 RR**。==新进程先进**第 1 级队尾**；在时间片内完成就退出系统，**时间片用完还没完成就降到下一级队尾**==，逐级下沉直到某级完成。最低级（第 *n* 级）时间片最长、行为接近 FCFS，但仍用 RR 保公平。
3. **按队列优先级调度**。仅当第 1 级空才调第 2 级；仅当 1 ~ *i*−1 级全空才调第 *i* 级。由于新进程总进第 1 级，**若当前运行的是低优先级队列的进程，新进程到来会立即抢占它**，被抢占者放回原队列末尾。

三类用户都受益：

| 用户类型     | 为什么好                                                  |
| -------- | ----------------------------------------------------- |
| 交互型（终端型） | ==进程短、频繁 I/O，能在高优先级队列快速完成==                           |
| 短批处理作业   | 优先级高、时间片小，==迅速执行完，周转时间短==                             |
| 长批处理作业   | ==虽最终降到低优先级队列，但**已在高优先级队列拿到过部分 CPU 时间**，不会饥饿，最终仍能完成== |

优势总结：既有利于短进程（提高吞吐、缩短平均周转），又有利于 I/O 型进程（提升设备利用率和响应速度），==而且**无须事先知道进程的运行时间**。==

**易错点**：
- 时间片和优先级是**反向**的：级别越低、优先级越低、时间片越大。
- 被抢占的进程放回**原队列末尾**，不是降级——只有「时间片用完」才降级。
- 「无须预知运行时间」是它相对 SJF 的关键优势，常作为选项考点。

> [!note] 我的笔记
> 需不需要预先知道（估计）运行时间，两阵营记死：**需要**的只有 SJF / SPF / SRTN 和高响应比优先；**不需要**的是 FCFS、优先级、RR、多级队列、多级反馈队列。多级反馈队列用「降级」替代「预知」——跑不完就沉一级，拿行为反推长短。

> [!question] 我的问题
> 无需知道进程的运行时间算什么优势？
> <span style="color: red;">答：是可实现性优势，不是性能优势——SJF 性能更好但要求预知运行时间，而运行时间 OS 无法预知、用户还会故意低报（KP37 缺点第 3 条）。多级反馈队列改用行为反推（跑不完就降级），零先验信息就逼近了 SJF 的效果。</span>

## KP44 基于公平原则的调度算法

**核心结论**：前面的算法都以响应时间/吞吐量/周转时间为目标，==这两种以**公平性**为核心目标。==

**（1）保证调度算法**：不追求「优先运行」，==而是给每个进程**可量化的 CPU 时间保证**==。n 个并发进程，每个应得约 **1/n** 的 CPU 时间。实现需要四步：

1. 跟踪每个进程**自创建以来已获得**的 CPU 时间。
2. 计算每个进程**应获得**的 CPU 时间 = 自进程创建以来的时间 / n。
3. 计算**公平比率** = 实际获得 / 应获得。< 1 表示未达应得份额，> 1 表示超额占用。
4. ==选择**比率最小**的进程运行，一直跑到它的比率**超过最接近它的那个进程的比率**为止。==

**（2）公平分享调度算法**：==保证调度对**进程**公平，但对**用户**未必公平==。用户 1 开 4 个进程、用户 2 开 1 个，RR 之下用户 1 拿 80% CPU、用户 2 只有 20%。==公平分享算法保证**每个用户**获得相同（或按要求比例）的 CPU 时间，不论他开多少进程。==

- 两用户各半（用户 1 有 A、B、C、D，用户 2 有 E）：`AEBECEDEAEBECEDE...`
- 用户 1 拿用户 2 的两倍：`ABECDEABECDE...`

**易错点**：==保证调度的公平单位是**进程**，公平分享的公平单位是**用户**——考点就在这个「对谁公平」的差别。==

## KP46 ==多处理机调度==：AMP vs SMP，亲和性与负载平衡

**核心结论**：多处理机调度策略与系统结构有关，按处理机之间的协作方式分两类。

|      | **非对称多处理机 AMP**                                    | ==**对称==多处理机 SMP**         |
| ---- | -------------------------------------------------- | -------------------------- |
| 结构   | **主从式**：==一个主 CPU 负责全部调度决策和系统管理，从 CPU 只执行任务不参与调度== | ==所有 CPU **地位对等**，均可参与调度== |
| 内核位置 | 一般只运行在主 CPU 上                                      | 任意 CPU                     |
| 就绪队列 | 主 CPU 维护一个**全局就绪队列**，从 CPU 空闲时向主 CPU 发进程请求信号       | 可把任意就绪进程分给任意空闲 CPU         |
| 评价   | ==实现简单，但主 CPU 承担全部调度开销，**高负载下成为性能瓶颈**==            | 408 讨论的主要对象                |

SMP 调度的两个核心矛盾：

1. **处理器亲和性**：进程从一个 CPU 迁到另一个 CPU 时，==要**把第一个 CPU 的缓存置为无效、再重新填充第二个 CPU 的缓存**，代价高。所以应尽量让一个进程始终在同一个 CPU 上运行。==
2. **负载平衡（负载均衡）**：==应把负载平均分到所有 CPU，否则会出现「一些 CPU 空闲、另一些高负载且有进程在等」的浪费。==

**两者互相抵消**：保持亲和性的好处是能用上该 CPU 的缓存，而负载平衡要迁移进程，迁移就丢了这个好处。==因此有些系统**只有当不平衡达到一定程度才触发进程迁移**。==

**易错点**：==亲和性的代价来自**Cache 失效**（还有 TLB）==，不是「进程数据要搬家」——进程的内存不动，动的是它在哪颗核上跑。

## KP47 多处理机调度的两种方案

**核心结论**：区别就在就绪队列是共享还是私有，两者的优缺点正好互补。

|      | **公共就绪队列**                 | **私有就绪队列**       |
| ---- | -------------------------- | ---------------- |
| 结构   | 全系统仅一个就绪队列，所有 CPU 共享       | 每个 CPU 一个私有就绪队列  |
| 取进程  | CPU 一空闲就立刻从公共队列取一个跑        | CPU 空闲时从自己的私有队列取 |
| 优点   | **负载平衡好**                  | **处理器亲和性好**      |
| 缺点   | 进程可能频繁在不同 CPU 间切换，**亲和性差** | 必须额外做**负载平衡**    |
| 配套手段 | 软亲和 / 硬亲和                  | 推迁移 / 拉迁移        |

提升亲和性的两种方式：

- **软亲和**：==由**调度程序**尽量把进程保持在某个 CPU 上，但仍**可以**迁移。==
- **硬亲和**：==由**用户进程通过系统调用**主动请求把自己**绑定到固定 CPU**。==
- Linux 实现了软亲和，同时也支持硬亲和的系统调用。

平衡负载的两种方式：

- **推迁移**：==由特定**系统程序周期性检查**各 CPU 负载，发现不平衡就从超载 CPU 的队列「推」出部分进程给空闲 CPU。==
- **拉迁移**：==某个 CPU **负载很低时主动**从超载 CPU 的队列「拉」进程到自己队列。==
- ==实际系统中推迁移和拉迁移**常结合使用**==。

**易错点**：推是**超载方被动、系统程序发起**，拉是**空闲方主动发起**——方向和发起者都要记准。软/硬亲和的分水岭是「谁决定绑定」：调度程序尽力 vs 用户显式系统调用。

## KP48 本节小结：为什么调度、哪些算法配哪种系统

**核心结论一：为什么要进行 CPU 调度？**

没有调度，就得等当前进程跑完下一个才能上 CPU。但进程经常要等外部设备输入，而外设速度远低于 CPU，让 CPU 干等 I/O 是极大浪费。引入调度后，运行中的进程因等 I/O 阻塞时，可把 CPU 分给其他就绪进程，**显著提高 CPU 利用率**。归结起来：调度的目的是**高效、合理地管理和分配软硬件资源**。

**核心结论二：哪些算法适合分时系统、哪些适合实时系统？**

| 算法 | 适配 | 理由 |
| --- | --- | --- |
| FCFS、SJF | **都不适合** | 无法保证在限定时间内响应用户请求，既不满足分时的交互性，也不满足实时的及时性与可预测性 |
| 优先级调度 | **实时系统** | 按紧急程度赋优先级，优先服务高优先级任务；通常需**配合抢占机制**确保关键任务及时执行 |
| 高响应比优先、时间片轮转、多级反馈队列 | **分时系统** | 都能保证每个就绪进程在一定时间内拿到 CPU 时间片，轮转共享 CPU，公平 |

**贯穿全书的主线**：只要对某类资源的请求超过其可用数量，就需要调度。后面还会遇到**内存调度、磁盘调度、I/O 调度**，设计思想与 CPU 调度异曲同工。

**易错点**：实时系统答「优先级 + 抢占」，分时系统答「时间片轮转 / 多级反馈队列」。别把 SJF 答成「适合分时」——它连响应时间上界都给不出。

# 2.3 同步与互斥

## KP49 临界资源与临界区

**真题**：同步与互斥的相关分析（2016、2021、2023）；临界区和临界资源的分析（2024）

**核心结论**：

- **临界资源**：同一时刻**仅允许一个进程访问**的资源。例：打印机等物理设备，以及被多个进程共享的变量、数据结构。
- **临界区**：==**每个进程中访问临界资源的那段代码**。注意临界区是**代码段**，不是资源本身。==

访问临界资源的四段结构：

| 段       | 做什么                                 |
| ------- | ----------------------------------- |
| **进入区** | 检查当前是否允许进入；允许就设置「正在访问临界区」的标志，阻止别人进来 |
| **临界区** | 实际访问临界资源的代码（也叫临界段）                  |
| **退出区** | 清除「正在访问」标志，表示已释放资源                  |
| **剩余区** | 除上述三部分之外的其余代码                       |

```c
while (true) {
    entry section;      // 进入区
    critical section;   // 临界区
    exit section;       // 退出区
    remainder section;  // 剩余区
}
```

**易错点**：临界区是**代码**，临界资源是**资源**——「进程处于临界区」= 它正在执行那段访问代码。不同进程访问同一临界资源的代码段，各自都是临界区。

## KP50 同步（直接制约）与互斥（间接制约）

**核心结论**：两种制约关系，考点在「直接/间接」的对应。

|     | **同步**                                                          | **互斥**                                                |
| --- | --------------------------------------------------------------- | ----------------------------------------------------- |
| 别名  | **直接制约关系**                                                      | **间接制约关系**                                            |
| 来源  | ==进程之间的**相互合作**==                                               | ==进程之间**竞争同一临界资源**==                                  |
| 含义  | 为完成某任务而建立的多个进程，需协调彼此**运行次序**，产生等待或传递信息的制约                       | 一个进程在临界区用资源时，其他想访问的进程必须等待，直到它退出临界区                    |
| 例子  | 输入进程 A 通过单缓冲向 B 供数据：缓冲区空则 B 阻塞，A 送入数据后唤醒 B；缓冲区满则 A 阻塞，B 取走后唤醒 A | 系统只有一台打印机，A 要打印但打印机已给 B，A 阻塞；B 打完释放，系统唤醒 A（阻塞态 → 就绪态） |

引入进程同步概念的动因（教材例）：算 $1+2\times3$，若拆成乘法进程和加法进程，加法必须等乘法完成。但 OS 有**异步性**，不加约束加法可能先跑，结果就错了。

**易错点**：
- 同步 = 直接制约，互斥 = 间接制约。这组对应关系反着记就全错。
- 互斥是「竞争关系」，同步是「协作关系」；同步问题里往往**同时含互斥**（如生产者-消费者），别只看到一半。

## KP51 同步机制应遵循的四准则

**真题**：临界区同步与互斥的设计准则（2020）

**核心结论**：为防止多个进程同时进入临界区，同步机制应遵循四条准则。

| 准则           | 含义                               | 违背它的后果                   |
| ------------ | -------------------------------- | ------------------------ |
| ==**空闲让进**== | 临界区空闲时，应允许一个请求进入的进程**立即进入**      | 资源明明空着却进不去，利用率低          |
| ==**忙则等待**== | 已有进程在临界区内时，其他进程**必须等待**          | 两个进程同时进临界区，破坏互斥          |
| ==**有限等待**== | 任何请求进程应在**有限时间内**能进入临界区          | 无限期等待，产生饥饿               |
| ==**让权等待**== | 进不去时应**主动放弃 CPU** 转阻塞态，而不是原地循环测试 | 忙等待（busy waiting），浪费 CPU |

**核心结论**：前三条是**必须**遵循的，==**让权等待是「原则上应遵循但非必须」**==——很多正确的互斥算法都不满足它。

**易错点**：
- 判断某算法违背了哪条准则，是最常见的题型。==记住对应关系：**同时进入 → 违背忙则等待；空闲进不去 → 违背空闲让进；永远等不到 → 违背有限等待；忙等 → 违背让权等待**。==
- 「不满足让权等待」不等于「算法错误」。Peterson、TS、Swap、自旋锁都不满足让权等待，但都能正确实现互斥。

## KP52 软件实现（一）：单标志法

**真题**：实现互斥的软/硬件方法的特点（2018）

**核心结论**：设一个公用整型变量 `turn` 指示**当前允许进入**临界区的进程号。进程退出临界区时把 `turn` 让给对方。

```c
// P0:                        // P1:
while (turn != 0);            while (turn != 1);      // 进入区
critical section;             critical section;       // 临界区
turn = 1;                     turn = 0;               // 退出区
remainder section;            remainder section;      // 剩余区
```

- **优点**：能保证每次只有一个进程进入临界区（互斥正确）。
- **缺点**：==两个进程**必须交替进入**。若某进程不再请求进入，另一个也无法再次进入——**违背「空闲让进」**。==
- 教材例子：P0 用完临界区，`turn = 1`，但 P1 根本不想进；此时临界区空闲，P0 却再也进不去了。

**易错点**：单标志法的问题**不是互斥失效**，而是「必须轮流、资源利用不充分」。它违背的是**空闲让进**，同时也属于**忙等待**（不满足让权等待）。

## KP53 软件实现（二）：双标志先检查法

**核心结论**：设布尔数组 `flag[2]`，`flag[i] = true` 表示 Pi 想进临界区。**先检查对方，再设置自己**。

```c
// P0:                        // P1:
while (flag[1]);      // ①    while (flag[0]);      // ②   先检查对方
flag[0] = true;       // ③    flag[1] = true;       // ④   再设置自己
critical section;             critical section;
flag[0] = false;              flag[1] = false;
remainder section;            remainder section;
```

- **优点**：无须交替进入，允许**连续使用**临界区（解决了单标志法的问题）。
- **缺点**：==按 ①②③④ 的顺序执行时，两个进程都先检查到对方 `flag` 为 `false`，然后各自设置自己的标志，结果**同时进入临界区**——**违背「忙则等待」**。==
- **根因**：「检查对方标志」和「设置自己标志」这**两个操作不是原子的**，中间可能发生进程切换。

**易错点**：这是四个软件算法里**唯一互斥失效**的一个。记法：**先检查后设置 → 会一起进去**。

## KP54 软件实现（三）：双标志后检查法

**核心结论**：针对算法二的毛病，改成**先设置自己，再检查对方**。

```c
// P0:                        // P1:
flag[0] = true;       // ①    flag[1] = true;       // ②   先设置自己
while (flag[1]);      // ③    while (flag[0]);      // ④   再检查对方
critical section;             critical section;
flag[0] = false;              flag[1] = false;
remainder section;            remainder section;
```

- **优点**：解决了「同时进入」，**互斥是正确的**。
- **缺点**：按 ①②③④ 顺序执行时，两个进程都先举了手，再互相一看对方也想进，==于是**彼此等待，谁也进不去**。==临界区空闲却没人能进——==**违背「空闲让进」**==；==进程可能长期甚至永远拿不到访问权——**违背「有限等待」**，导致**饥饿**。==

**易错点**：算法三违背**两条**准则（空闲让进 + 有限等待），是四个算法里违背最多的。记法：**先设置后检查 → 谁都进不去**。注意它这个「互相等待」形态上很像死锁，但教材归类为违背准则、产生饥饿。

## KP55 软件实现（四）：Peterson 算法

**真题**：Peterson 算法的原理（2010、2018）

**核心结论**：**结合算法一和算法三**——用 `flag[]` 解决互斥访问，用 `turn` 解决饥饿。关键动作是**主动「谦让」**：设置自己想进后，把 `turn` 让给对方。

```c
// P0:                                  // P1:
flag[0] = true;                         flag[1] = true;               // 我想进
turn = 1;                               turn = 0;                     // 谦让给对方
while (flag[1] && turn == 1);           while (flag[0] && turn == 0); // 等待
critical section;                       critical section;
flag[0] = false;                        flag[1] = false;
remainder section;                      remainder section;
```

正确性论证（要会说）：

- **只有一个进程请求**：如 P0 单独进，`flag[1] == false`，while 条件不成立，直接进入。
- **两个进程同时请求**：P0 置 `turn = 1`，P1 置 `turn = 0`，两次赋值**依次完成**，`turn` 的最终值由**后赋值的那个进程**决定。==而 while 的等待条件是「对方想进 **且** turn 指向对方」，所以**总有一个进程的等待条件不成立**，它就能进去。==

准则达成情况：

| 准则           | 是否满足                     |
| ------------ | ------------------------ |
| 空闲让进         | ✔                        |
| 忙则等待         | ✔                        |
| 有限等待         | ✔                        |
| ==**让权等待**== | ==**✘**（进入区循环测试，仍是忙等待）== |

**核心结论**：Peterson 算法是**纯软件互斥算法中，==在满足前三条准则方面最完善的方案**。==

**易错点**：`turn` 是**谦让**语义（我把机会让给你），不是「我要进」。写成 `turn = i` 就错了。另外别答「Peterson 满足四条准则」——它不满足让权等待。

## ==KP56 硬件实现（一）：中断屏蔽方法==

**真题**：中断屏蔽实现互斥的原理与分析（2021）

**核心结论**：**关中断**是实现互斥最简单的方法。临界区前关中断，临界区后开中断。

```c
关中断;
临界区;
开中断;
```

原理：==**CPU 仅在响应中断时才可能发生进程/线程切换**，所以关中断期间当前进程不会被抢占，临界区代码能不受干扰地连续执行。==

三个缺点：

1. **限制 CPU 的并发能力**，显著降低系统效率。
2. **不能把关中断权限开放给用户进程**。内核在更新关键变量的几条指令期间关中断是可行的，==但用户进程关了中断不及时开，可能导致**系统死锁或崩溃**。==
3. ==**不适用于多处理器系统**——在某一 CPU 上关中断，**无法阻止其他 CPU 上的进程**并发访问同一临界区。==

**易错点**：这条「只适合单处理器、只适合内核」是常考点。理解锚：==关中断只影响**本 CPU** 的切换，管不了别的核。==

## KP57 硬件实现（二）：TestAndSet 指令

**真题**：TestAndSet 指令实现互斥的原理与特点（2016、2018）

**「锁」的抽象（先理解这个）**：把共享标志看成一把锁，「锁开」表示允许进入，「锁关」表示需等待，初始为开。每个想进临界区的进程先测试锁：锁关则等，**一发现锁开就立即上锁**。若多个进程几乎同时检测到「锁开」，就会同时进入——所以**「测试」与「上锁」必须构成一个原子操作**。现代计算机提供了能以原子方式检测并修改一个字、或交换两个字的硬件指令，正是为此。

**核心结论**：TS（TestAndSet）指令==**由硬件保证原子性**==，功能是「读旧值 + 置 true + 返回旧值」。

```c
boolean TestAndSet(boolean *lock) {
    boolean old;
    old = *lock;      // old 存放 lock 的旧值
    *lock = true;     // 无条件把 lock 置为 true
    return old;       // 返回旧值
}
```

用法：为每个临界资源设一个共享布尔变量 `lock`（**初值 false**）。`lock = true` 表示已被占用（已加锁），`false` 表示空闲。

```c
while (TestAndSet(&lock));   // 尝试获取锁（忙等待）
临界区代码段;
lock = false;                // 解锁
其他代码;
```

- 返回 `false` → `lock` 原为 false，无人在临界区，**本进程获得锁**（此时 lock 已被指令置为 true，挡住别人）。
- 返回 `true` → `lock` 原为 true，已有进程在临界区，**循环等待**，直到持锁者退出并置 `lock = false`。

优缺点：

- 相比软件方法：由**硬件**保证「检查锁」与「加锁」的原子性，不会像双标志先检查法那样被切换打断。
- 相比关中断方法：`lock` 是**共享变量**，所以**适用于多处理器系统**。
- ==缺点：等待进程持续执行 TS 指令，**忙等待**，无法实现「让权等待」，浪费 CPU。==

**易错点**：TS 是**无条件写入** true 的——不管原来是什么值都置 true。正是「返回旧值」这一点让调用者知道自己是否抢到了锁。

## KP58 硬件实现（三）：Swap 指令与硬件方法总评

**真题**：Swap 指令实现互斥的原理与分析（2018、2023）

**核心结论**：==Swap 指令**原子地交换两个变量的值**。==

```c
void Swap(boolean *a, boolean *b) {
    boolean temp = *a;
    *a = *b;
    *b = temp;
}
```

用法：共享布尔变量 `lock`（初值 false）+ 每个进程一个**局部**布尔变量 `key`（每次进入前初始化为 true）。

```c
boolean key = true;
while (key != false)
    Swap(&lock, &key);
临界区代码段;
lock = false;
其他代码;
```

原理与 TS **本质相同**：一次原子操作既取到锁的当前状态（存进 `key`），又把锁置为占用（`key` 的 true 换给了 `lock`）。`key == false` 说明此前无人持锁 → 获得访问权；==`key == true` 说明锁已被占用 → 继续循环。**进入临界区的条件是 `key` 变为 false**。==

硬件指令方法（TS / Swap）**总优点**：

1. **实现简单**，正确性易于验证。
2. **支持任意数量的进程**，适用于**多处理器系统**。
3. 系统中可存在**多个临界区**，只需为每个临界区分配独立的 `lock` 变量。

**总缺点**：

1. **忙等待**，无法实现「让权等待」，浪费 CPU。
2. ==**锁的获取顺序不确定**，可能导致某些进程长期拿不到访问机会，产生**饥饿**。==

**说明**：TS 和 Swap 的代码只是**功能示意**，实际由硬件逻辑实现、不会被中断；它们也不是真实的编程接口，而是描述同步互斥的**抽象模型**。真实 OS 里这些底层机制已被封装进**信号量、互斥锁**等高级同步原语，用户无须自己写忙等待循环。

==**易错点**：`key` 必须是**局部变量**（每个进程各一份），`lock` 才是共享的。把 key 写成共享的整套逻辑就崩了。==

## KP59 互斥锁与自旋锁

**核心结论**：解决临界区问题**最简单的工具是互斥锁（mutex lock）**。进临界区前调 `acquire()` 拿锁，出临界区调 `release()` 放锁。每个互斥锁含一个布尔变量 `available` 表示锁是否可用。

```c
acquire() {
    while (!available)
        ;                 // 忙等待
    available = false;    // 获得锁
}
release() {
    available = true;     // 释放锁
}
```

- `acquire()` 和 `release()` 的执行**必须是原子操作**，因此互斥锁**通常采用硬件机制实现**。
- 上述互斥锁也叫**自旋锁（spin lock）**，==主要缺点是**忙等待**==：有进程在临界区时，其他进程必须连续循环调用 `acquire()`。同类的还有**单标志法、TS 指令、Swap 指令**。

自旋锁的适用场景与优点：

| 方面 | 内容 |
| --- | --- |
| 不适合 | 多个进程**共享同一 CPU** 时，连续循环白白浪费 CPU 周期 |
| 适合 | **多处理器系统**——一个线程在一个处理器上「旋转」，不影响其他线程执行 |
| 优点 | 等待期间**没有上下文切换**；若**持有锁的时间较短**，等待代价很低 |

**易错点**：==自旋锁的价值就在「省掉上下文切换」。所以判断该不该用自旋锁，看两点：**是不是多处理器** + **临界区是不是很短**。临界区很长还自旋，就是纯浪费。==

## ==KP60 信号量机制与整型信号量==

**真题**：信号量的含义（2010）

**核心结论**：信号量机制**既能解决互斥问题，也能处理同步问题**。它**仅能通过两个标准原语访问**：`wait()` 和 `signal()`，也就是 **P 操作和 V 操作**。

**原语**：完成特定功能、**执行过程中不可被中断**的操作序列，通常由硬件实现（如 TS、Swap 指令）。单 CPU 系统中也可通过**屏蔽中断**保证原子性。之所以要求不可中断：若其对共享变量的操作被中途打断，可能与其他进程的操作交织，**破坏临界区的互斥性**。

**整型信号量**：用一个整型变量 S 表示某类资源的**可用数量**。与普通整型变量不同，对它的操作**仅限三种：初始化、wait、signal**。

```c
wait(S) {          // 相当于进入区（原子操作）
    while (S <= 0);   // 资源不够就一直循环等待
    S = S - 1;        // 资源够则占用一个
}
signal(S) {        // 相当于退出区（原子操作）
    S = S + 1;        // 用完释放一个
}
```

**缺陷**：当 S ≤ 0 时进程**持续循环测试**，处于**忙等待**，**未遵循「让权等待」**，浪费 CPU 时间，在单 CPU 系统中尤其低效。

**易错点**：整型信号量的 S **永远不会为负**（`while` 卡在那里，减不下去）——这是它和记录型信号量最好用的区分点。

## ==KP61 记录型信号量（重点）==

**真题**：wait() 操作导致线程状态的变化（2023）；遵循「让权等待」的互斥方法（2018）

==**核心结论**：**Dijkstra 提出**，用**阻塞机制**克服忙等待，**实现了「让权等待」**==。采用结构化数据：整型 `value`（当前可用资源数）+ 进程链表 `L`（等待队列，链接所有因请求该资源而阻塞的进程）。

```c
typedef struct {
    int value;
    struct process *L;
} semaphore;
```

```c
void wait(semaphore S) {        // 申请资源
    S.value--;
    if (S.value < 0) {
        add this process to S.L;
        block(S.L);             // 自我阻塞，让权等待
    }
}
void signal(semaphore S) {      // 释放资源
    S.value++;
    if (S.value <= 0) {
        remove a process P from S.L;
        wakeup(P);              // 唤醒一个等待进程
    }
}
```

- `wait(S)`：**先减 1**，若减后 `S.value < 0`，说明资源已分配完，调 **block 原语自我阻塞**、主动放弃 CPU，加入等待队列 S.L。
- `signal(S)`：**先加 1**，若加后 `S.value ≤ 0`，说明**仍有进程在等待**，调 **wakeup 原语**从 S.L 移出一个进程唤醒它。

**核心结论（数值语义，必须会读）**：

| `S.value` | 含义 |
| --- | --- |
| > 0 | 当前**可用资源数** |
| = 0 | 资源刚好分完，无等待进程 |
| < 0 | **其绝对值 = 等待队列中被阻塞的进程数** |

**易错点**：
- 减/加**在判断之前**执行，所以 value 会变成负数——这正是它和整型信号量的本质区别。
- `signal` 里判断条件是 **≤ 0**（不是 < 0）：加 1 后仍 ≤ 0 说明还有人在等。
- 2023 那道的落点：执行 `wait()` 若资源不足，线程从**运行态转为阻塞态**（不是就绪态）。

## KP62 用信号量实现互斥

**真题**：利用信号量实现互斥的实现（2024）

**核心结论**：为临界资源设一个**互斥信号量 S，初值为 1**（可用资源数为 1），把各进程的**临界区夹在 P(S) 与 V(S) 之间**。

```c
semaphore S = 1;        // 互斥信号量，初值 1
P1() {
    ...
    P(S);               // 申请临界资源，加锁
    进程 P1 的临界区;
    V(S);               // 释放临界资源，解锁
    ...
}
P2() {
    ...
    P(S);
    进程 P2 的临界区;
    V(S);
    ...
}
```

**两个进程竞争时 S 的取值只有 1、0、−1**（这是常考的判断题）：

| S | 含义 |
| --- | --- |
| **1** | 两个进程都没进临界区 |
| **0** | 有**一个**进程正在临界区中 |
| **−1** | 一个在临界区，**另一个已阻塞在等待队列**，需等前者 V(S) 后被唤醒 |

三条注意事项：

1. **不同的临界资源应配置独立的互斥信号量**，避免相互干扰。
2. **P(S) 与 V(S) 必须严格成对出现**：缺 P(S) 无法保证互斥；缺 V(S) 导致资源永不释放，等待进程**永久阻塞**。
3. 若系统中有**多个同类资源**，信号量**初值设为资源总数**，申请时 P(S)、释放时 V(S)。

**易错点**：互斥用法里 P、V 必须**紧夹**临界区，中间不能插入无关代码（插了就延长了临界区、降低并发甚至引发死锁）。这一点和同步用法的摆放规则不同，见 KP63。

## KP63 用信号量实现同步

**真题**：利用信号量实现同步（2024）

**核心结论**：同步源于**协作需求**。并发进程有异步性、推进次序不确定；若 P2 的语句 y 要用 P1 的语句 x 的结果，就必须保证 **y 在 x 之后执行**。做法：设同步信号量 S，**初值为 0**（理解为「P2 需要的资源还没被生产出来，而它只能由 P1 产生」）。

```c
semaphore S = 0;      // 同步信号量，初值 0
P1() {
    x;                // 执行语句 x
    V(S);             // 通知 P2：x 已完成
}
P2() {
    P(S);             // 等待 x 完成
    y;                // 使用 x 的结果
}
```

两种执行顺序都正确：

| 情况 | 过程 |
| --- | --- |
| P1 先 V(S) | S 由 0 → 1；P2 再 P(S)，S-- 后为 0，**不调 block**，直接执行 y |
| P2 先 P(S) | S 由 0 → -1，无可用资源，**调 block 阻塞 P2**；P1 执行 x 后 V(S)，S 由 -1 → 0，**调 wakeup 唤醒 P2**，P2 继续执行 y |

**PV 操作用法总结（必背）**：

- **同步问题**：某行为**提供**某资源 → 在该行为**之后 V** 这种资源；某行为**需要**某资源 → 在该行为**之前 P** 这种资源。
- **互斥问题**：P、V 必须**紧夹**使用临界资源的那个行为，中间不得插入任何无关代码。

**易错点**：

- 同步信号量初值 **0**，互斥信号量初值 **1**，多个同类资源初值 = **资源总数**。三者不要混。
- 同步里 V 在前驱之后、P 在后继之前，**P 和 V 分处两个不同进程**；互斥里 P、V 在**同一个进程**内成对出现。这是判断一个信号量是同步用还是互斥用的最快判据。

## KP64 用信号量实现前驱关系（真题应用题）

**真题**：信号量实现前驱关系的应用题（2020、2022）

教材图示（图 2.11 前驱关系举例）：[[王道教材/27 王道操作系统/pictures/fig-2-11.jpg]]

**核心结论**：每一条前驱边就是**一个独立的同步问题**（后继必须等前驱完成）。所以：

1. **为每条边**设一个同步信号量，**初值全为 0**；命名习惯 `aij` 表示协调 Si → Sj。
2. 前驱段执行**完毕后**，对它的**每条出边**执行 V，通知所有直接后继。
3. 后继段开始执行**之前**，对它的**每条入边**执行 P，等待所有直接前驱。

图 2.11 的约束是 S1→S2、S1→S3、S2→S4、S2→S5、S3→S6、S4→S6、S5→S6：

```c
semaphore a12=0, a13=0, a24=0, a25=0, a36=0, a46=0, a56=0;
S1() { ...;            V(a12); V(a13); }          // 出边 2 条
S2() { P(a12);   ...;  V(a24); V(a25); }
S3() { P(a13);   ...;  V(a36); }
S4() { P(a24);   ...;  V(a46); }
S5() { P(a25);   ...;  V(a56); }
S6() { P(a36); P(a46); P(a56); ...; }              // 入边 3 条
```

**记忆锚**：**信号量个数 = 图中边数**；每个程序段里 **P 的个数 = 入度，V 的个数 = 出度**。写完对着图数一遍度数就能自查。

**易错点**：

- 不要试图用一个信号量代表「S1 完成」去通知两个后继——一次 V 只能唤醒一个进程，S1→S2 和 S1→S3 必须是两个信号量、两次 V。
- P 全部写在段首、V 全部写在段尾，顺序不能反；同一段里多个 P 之间顺序无所谓（都是初值 0 的同步量，不构成死锁）。

## KP65 分析同步互斥问题的三步法

**核心结论**：拿到 PV 应用题，按固定三步走：

1. **关系分析**：找出参与并发的进程，厘清它们之间是哪种关系——
   - **互斥关系**：多个进程竞争同一临界资源；
   - **同步关系**：某进程需等待另一进程的执行结果；
   - **前驱关系**：存在明确的执行顺序约束。
2. **思路梳理**：根据各进程的操作流程确定**关键同步点**，初步规划 P、V 的位置；主动类比典型场景（生产者-消费者、读者-写者、前驱图）。
3. **信号量设置**：定义信号量，明确**语义与初值**，把 P、V 嵌入适当位置，确保逻辑正确、**避免死锁与饥饿**、满足所有约束。

**易错点**：第 1 步最容易漏的是「既互斥又同步」——缓冲区类题目一定是两种关系并存，只看出一种就会少设信号量。

## ==KP66 生产者-消费者问题（真题超高频）==

**真题**：PV 操作的应用题（2009、2011、2013、2014、2015、2017、2019、2025）

**问题描述**：一组生产者、一组消费者共享一个**初始为空、容量为 n** 的缓冲区。约束：缓冲区未满生产者才能放，否则等待；缓冲区非空消费者才能取，否则等待；==**缓冲区是临界资源，必须互斥访问**。==

**三步分析**：

1. 关系：缓冲区共享 → 生产者与消费者**互斥**；消费者必须等生产者产出 → 二者又**同步**。
2. 思路：一个互斥量管缓冲区，两个计数量分别记空位数和产品数，并**严格控制 P 操作的顺序**以避免死锁。
3. 信号量：

| 信号量     | 语义      | 初值  |
| ------- | ------- | --- |
| `mutex` | 互斥访问缓冲区 | 1   |
| `empty` | 空缓冲区数量  | n   |
| `full`  | 满缓冲区数量  | 0   |

```c
semaphore mutex = 1, empty = n, full = 0;
producer() {
    while (1) {
        生产一个产品;
        P(empty);      // 要用什么，P 一下：申请一个空缓冲区
        P(mutex);      // 互斥夹紧：进入临界区
        将产品放入缓冲区;
        V(mutex);      // 互斥夹紧：退出临界区
        V(full);       // 提供什么，V 一下：满缓冲区数 +1
    }
}
consumer() {
    while (1) {
        P(full);       // 申请一个满缓冲区
        P(mutex);
        从缓冲区取出一个产品;
        V(mutex);
        V(empty);      // 空缓冲区数 +1
        消费产品;
    }
}
```

**记忆锚**：**要用什么就 P 什么，提供什么就 V 什么；mutex 紧夹存取动作。** 「生产一个产品」和「消费产品」都在临界区**外**，因为它们不碰缓冲区。

**易错点**：

- `empty` 和 `full` 是一对，**总和恒为 n**；`V(full)` 的对面是 `P(empty)`，别配错。
- 生产者是 `P(empty)…V(full)`，消费者是 `P(full)…V(empty)`——**P 自己需要的、V 对方需要的**。

## KP67 为什么 P(empty) 必须在 P(mutex) 之前（死锁分析）

**核心结论**：对 `empty`／`full` 的 P 操作**必须置于对 `mutex` 的 P 操作之前**，顺序颠倒会死锁。

反例推演（缓冲区已满，empty = 0）：

1. 生产者先 `P(mutex)` 成功，**持有 mutex**；
2. 生产者再 `P(empty)`，因 empty = 0 而**阻塞，且没有释放 mutex**；
3. 消费者想取产品，执行 `P(mutex)` 时因 mutex 被生产者持有而**阻塞**，进不去临界区，也就无法执行 `P(full)` 和取走产品；
4. 生产者等消费者腾出空位，消费者等生产者释放 mutex → **互相阻塞，死锁**。

缓冲区为空（full = 0）时同理：消费者先拿 mutex 再 `P(full)` 阻塞，生产者也进不来放产品。

**通用判据**：**绝不能「持有互斥锁的同时去等待资源」**。所以顺序永远是**先申请资源状态（empty/full），再申请互斥权（mutex）**。

**易错点**：

- 两个 **V 操作的顺序可以互换**，不会死锁（V 从不阻塞）；只有**两个 P 的顺序**是死的。
- 这条不是「习惯写法」而是正确性要求，考试改错题最常挖这个坑。

## KP68 进阶：吃水果问题（容量为 1 的多产品缓冲区）

**问题描述**：桌上一个盘子，**最多容纳一个水果**。爸爸只放苹果，妈妈只放橘子；女儿只吃苹果，儿子只吃橘子。盘子空时爸爸或妈妈才能放；盘中有自己要的水果时儿子或女儿才能取。

**三步分析**：

1. 关系：爸爸和妈妈**互斥**（争同一个盘子）；爸爸↔女儿、妈妈↔儿子分别**同步**；儿子和女儿之间**既无互斥也无同步**（各等各的水果）。
2. ==思路：两个生产者、两个消费者，共享容量 1 的缓冲区。**不同产品要由不同消费者取走，所以不能只用一个 `full`**，必须为每种产品设独立的同步信号量。==
3. 信号量：`plate` 初值 1（盘子可用）、`apple` 初值 0、`orange` 初值 0。

```c
semaphore plate = 1, apple = 0, orange = 0;
dad()      { while(1){ 准备苹果; P(plate); 把苹果放入盘子; V(apple);  } }
mom()      { while(1){ 准备橘子; P(plate); 把橘子放入盘子; V(orange); } }
son()      { while(1){ P(orange); 取出橘子; V(plate); 吃掉橘子; } }
daughter() { while(1){ P(apple);  取出苹果; V(plate); 吃掉苹果; } }
```

教材图示（图 2.12 进程之间的关系）：[[王道教材/27 王道操作系统/pictures/fig-2-12.jpg]]

**核心结论**：`dad()` 与 `daughter()`、`mom()` 与 `son()` **必须成对执行**。只有水果被取走后才执行 `V(plate)`，盘子才重新可用。

**易错点（本题的真正考点）**：

- `plate` 这里**不是纯互斥锁**，它同时承担「盘子有空位」这个**同步条件**——所以 `P(plate)` 在放水果的进程里，而 `V(plate)` 在**取水果的进程里**，P、V 分处不同进程。对比 KP66 的 `mutex`（同进程内紧夹），这是最容易写错的地方。
- 因为容量只有 1，`apple`／`orange` 本身已经保证了盘子内容不会被混淆，不需要再额外加一个互斥量。
- 不能把 `V(plate)` 写在爸爸放完水果之后——那样盘子会被立刻重复占用，苹果被覆盖。

## KP69 读者-写者问题（读者优先）

**问题描述**：读者和写者共享一个文件。**多个读者可同时读**；写者与任何其他进程（读者或写者）同时访问都会破坏一致性。要求：① 允许多个读者同时读；② 任一时刻只允许一个写者写；③ 写者写完前不允许其他任何进程访问；④ 写者开始写前必须等所有已进入的读者和写者退出。

**三步分析**：

1. 关系：**读者↔写者互斥**、**写者↔写者互斥**、**读者↔读者不互斥**（可并发）。
2. ==思路：写者简单，与所有人互斥，一个互斥量即可。读者复杂：既要允许别的读者并发，又要挡住写者。引入计数器 `count` 记录当前正在读的读者数——**第一个读者进入时挡住写者，最后一个读者离开时放开写者**；而多个读者改 `count` 本身又必须互斥。==
3. 信号量：`count = 0`（当前读者数，普通变量）、`mutex = 1`（保护 count）、`rw = 1`（保护文件）。

```c
int count = 0;
semaphore mutex = 1, rw = 1;
writer() {
    while (1) { P(rw);  写文件;  V(rw); }
}
reader() {
    while (1) {
        P(mutex);
        if (count == 0) P(rw);   // 第一个读者：挡住写者
        count++;
        V(mutex);
        读文件;
        P(mutex);
        count--;
        if (count == 0) V(rw);   // 最后一个读者：放开写者
        V(mutex);
    }
}
```

**核心结论**：这是**读者优先**策略——只要已有读者在读，后来的读者可立即进入，写者必须等所有读者退出，因此**可能造成写者饥饿**（读者源源不断时写者被无限推迟）。

**易错点**：

- `P(rw)` / `V(rw)` 在读者里是**由第一个和最后一个读者代表全体执行的**，不是每个读者都执行；也正因为如此，`if` 判断必须放在 `mutex` 的保护之内。
- `count` 是**普通整型变量**，不是信号量；`mutex` 保护的是 count，`rw` 保护的是文件，两者职责别混。
- 读者内部有**两段**临界区（进入时改 count、退出时改 count），漏写第二段是常见错误。

## KP70 读者-写者问题（写者优先）

**核心结论**：目标是**一旦有写者请求，就禁止新读者进入**，当前读者全退出后立刻让写者写。==做法：加一个互斥信号量 `w`，充当进入「准备访问文件」阶段的**门卫**。==

```c
int count = 0;
semaphore mutex = 1, rw = 1, w = 1;   // w 是实现写者优先的关键
writer() {
    while (1) { P(w); P(rw); 写文件; V(rw); V(w); }
}
reader() {
    while (1) {
        P(w);                        // 若有写者持有或在等 w，读者被挡住
        P(mutex);
        if (count == 0) P(rw);
        count++;
        V(mutex);
        V(w);                        // 更新完 count 立刻放开 w
        读文件;
        P(mutex);
        count--;
        if (count == 0) V(rw);
        V(mutex);
    }
}
```

**为什么读者要「立刻 V(w)」**：只要存在活跃读者（count > 0），写者已经被 `rw` 挡住了，提前释放 `w` 不会破坏优先级，却能避免不必要地阻塞其他进程。

==**关键结论：这只是「相对优先」，不是绝对优先。**== `w` 能阻止新读者在写者等待时插队，但若读者和写者**同时**阻塞在 `w` 上，系统通常按 **FCFS 唤醒**，先到的读者仍可能排在后到的写者之前。所以它的本质是**在防止写者饥饿的前提下给写者有限优先**。

**通用解题启示**：读者-写者的关键是**用受互斥保护的计数器动态判断资源状态**。遇到复杂同步互斥题，主动想想能不能引入这样一个计数器。

**易错点**：写者是 `P(w); P(rw); … V(rw); V(w);`——`w` 在最外层包住整个写操作；读者的 `w` 只包住「登记 count」这一小段。范围写错就退化成读者优先或者直接串行化。

## KP71 哲学家进餐问题

**问题描述**：圆桌旁 5 名哲学家，相邻两人之间放 1 根筷子共 5 根，每人面前一碗饭。哲学家交替思考与进餐：思考互不影响；饥饿时**必须同时持有左右两根筷子**才能进餐，且**筷子要逐根拿起**；所需筷子被占则等待；进餐完毕立即放下两根筷子。

教材图示（图 2.13 5 名哲学家进餐）：[[王道教材/27 王道操作系统/pictures/fig-2-13.jpg]]

**三步分析**：

1. 关系：每根筷子被两侧哲学家共享，对**同一根筷子的访问必须互斥**。
2. 思路：5 个并发进程，关键是**如何安全地拿到左右两根筷子，避免死锁或饥饿**。
3. 信号量：`chopstick[5]` 全部初值 1。哲学家编号 0~4，哲学家 i 的**左筷编号 i，右筷编号 (i+1)%5**。

**直观实现（有死锁风险）**：

```c
semaphore chopstick[5] = {1,1,1,1,1};
Pi() {
    do {
        P(chopstick[i]);           // 拿左筷
        P(chopstick[(i+1)%5]);     // 拿右筷
        进餐;
        V(chopstick[i]);
        V(chopstick[(i+1)%5]);
        思考;
    } while(1);
}
```

**死锁场景**：5 人同时饥饿、几乎同时执行完 `P(chopstick[i])`，各持一根左筷、都在等右筷 → **循环等待，全体阻塞，死锁**。

**三种防死锁办法（必背）**：

| 办法       | 做法                                          | 破坏了什么                  |
| -------- | ------------------------------------------- | ---------------------- |
| ==① 限制人数==   | ==最多允许 **4 人**同时尝试进餐==                          | ==保证至少一人能拿到两根，用完释放后带动其他人== |
| ==② 奇偶分序==   | ==**奇数号先拿左后拿右，偶数号相反**==                         | ==破坏**循环等待**条件==           |
| ==③ 整体互斥取筷== | ==仅当左右两根都空闲时才允许拿起（用一个 `mutex` 把「取两根筷子」整个过程互斥）== | ==使「持有一根等另一根」的中间状态不再对外可见== |

第 ③ 种的实现：

```c
semaphore chopstick[5] = {1,1,1,1,1};
semaphore mutex = 1;               // 取筷子这一整段的互斥量
Pi() {
    do {
        P(mutex);                  // 申请取筷子
        P(chopstick[i]);
        P(chopstick[(i+1)%5]);
        V(mutex);                  // 两根都到手才释放
        进餐;
        V(chopstick[i]);
        V(chopstick[(i+1)%5]);
        思考;
    } while(1);
}
```

**教材小坑**：教材原文写「假设采用第二种方法」，但紧接着的描述（左右筷子都可用才拿）和给出的代码实现的其实是**第 ③ 种**（用 mutex 把取筷过程整体互斥），并不是第 ② 种奇偶分序。看代码判断，别被那句话带偏。

**易错点**：

- ==`V(mutex)` 必须放在**两个 P(chopstick) 都完成之后**；放在中间就等于没做整体互斥。==
- 放筷子的两个 V **不需要** mutex 保护（V 不阻塞，不会造成死锁）。
- 本质是**预防循环等待**。真题里 PV 大题多考生产者-消费者和读者-写者，但哲学家的三种防死锁法是选择题常客。

## KP72 管程的定义与四个组成部分

**真题**：管程的特点（2016）

**为什么要引入管程**：信号量机制中，每个访问临界资源的进程都要**自己编写 P/V**。同步代码分散 → 编程复杂、极易因**操作顺序不当而死锁**。管程是更高层的抽象：==把**共享资源及其操作封装在一起**，**自动保证互斥访问**，程序员无须显式写互斥代码；再通过**条件变量**实现灵活同步，降低死锁风险。==

**核心结论**：管程（monitor）用一个**共享数据结构**表示系统中的共享资源，并把对该数据结构的所有操作封装成**一组过程**。进程对资源的申请、释放都必须**通过调用这些过程**完成；过程根据资源当前状态决定是否放行（满足则处理，否则阻塞该进程），从而保证**任一时刻至多一个进程使用该共享资源**。

**四个组成部分（必背）**：

1. 管程的**名称**；
2. 局部于管程内部的**共享数据结构说明**；
3. 对该数据结构进行操作的**一组过程（函数）**；
4. 对共享数据进行**初始化的语句**。

```c
monitor Demo {                 // ① 管程名称
    共享数据结构 S;             // ② 局部共享数据
    init_code() { S = 5; }     // ④ 初始化语句
    take_away() {              // ③ 过程 1：申请资源
        对 S 的一系列处理;  S--;
    }
    give_back() {              // ③ 过程 2：归还资源
        对 S 的一系列处理;  S++;
    }
}
```

**两个基本特性**：

- ==**封装性**：内部共享数据结构**只能被管程自身的过程访问**，外部进程必须调用过程才能访问资源。==
- ==**互斥性**：**任一时刻仅允许一个进程执行管程内的过程**。这个互斥由**编译器／管程机制自动保证**，不需要程序员写 P/V。==

**易错点**：管程的互斥是==**自动的、由机制提供的**==，这是它相对信号量最大的优势；==说「管程内也要程序员写 P、V 来保证互斥」是错的。==

> [!note] 我的笔记
> 任何时候只有一个进程执行管程
> 
> 只有管程内的进程才能访问和调用管程内数据结构

## KP73 管程与进程的六点区别

**核心结论**：

| #   | 进程                  | 管程                       |
| --- | ------------------- | ------------------------ |
| ①   | 拥有**私有**数据结构（如 PCB） | 管理**公共**数据结构（如缓冲区）       |
| ②   | 执行**通用计算**任务        | 专注**同步控制与资源管理**          |
| ③   | 引入是为了实现**并发**       | ==引入是为了解决共享资源的**互斥访问**== |
| ④   | **主动**执行的实体         | **被动**调用的模块（由进程调用其过程）    |
| ⑤   | 多个进程可**并发执行**       | 对同一管程的多个调用是**互斥的**       |
| ⑥   | 有**动态**生命周期（创建到撤销）  | 是操作系统中的**静态**资源管理模块      |

**记忆锚**：私有 vs 公共、计算 vs 管理、并发 vs 互斥、主动 vs 被动、可并行 vs 只能一个、动态 vs 静态。

**易错点**：==管程**不是进程**，不会被调度、没有状态转换、没有 PCB；它只是一段供进程调用的代码模块。==

## KP74 条件变量

**核心结论**：==进程进入管程后若因条件不满足要等待，**必须释放对管程的占用**，否则别人进不来、系统停滞。==为此管程引入**条件变量（condition）**，把**不同的阻塞原因**分别抽象为独立的条件变量。一个进程可能因多种条件阻塞，所以管程中可设置**多个**条件变量，**每个条件变量维护一个等待队列**。

只支持两种操作：

- **`x.wait()`**：条件 x 不满足时，调用者把自己加入 x 的等待队列，并**自动释放管程**，从而允许其他进程进入。
- **`x.signal()`**：条件 x 可能已满足时，**唤醒一个**阻塞在 x 上的进程。

```c
monitor Demo {
    共享数据结构 S;
    condition x;                              // 定义条件变量 x
    init_code() { ... }
    take_away() {
        if (S <= 0) x.wait();                 // 资源不足，在 x 上阻塞
        等待资源足够，分配资源，做相应处理;
    }
    give_back() {
        归还资源，做相应处理;
        if (有进程在等待) x.signal();          // 唤醒一个阻塞进程
    }
}
```

**条件变量 vs 信号量**：

| | 相同 | 不同 |
| --- | --- | --- |
| — | wait/signal 与 P/V 都能实现进程的**阻塞与唤醒** | 信号量**有整数值**，反映可用资源数量；条件变量**不维护数值**，仅用于排队和通知 |

在管程中，**资源数量由共享变量（如 S）显式记录，条件变量只负责同步**。

**易错点**：

- ==`x.wait()` 会**释放管程**（这是它和「在临界区里死等」的本质区别）。==
- `x.signal()` 在没有进程等待时是**空操作**，不像 `V` 那样把值加 1 攒起来——所以条件变量**没有记忆**，这是与信号量最关键的差别。

## KP75 本节小结：2.3 的三个开篇问题

**1. 为什么要引入进程同步的概念？**

多道程序环境下多个进程并发执行，彼此存在**相互制约关系**。为协调这些关系、确保进程能正确有序地协作或竞争共享资源，OS 引入了进程同步。

**2. 不同进程之间会存在什么关系？**

两种基本制约关系：

- **同步（直接制约）**：为完成共同任务而建立的多个进程，在某些**关键点**上需协调工作次序，通过等待或传递信息形成的**协作**关系。
- **互斥（间接制约）**：一个进程正在访问临界资源（处于临界区）时，其他进程必须等待；只有它退出临界区后其他进程才被允许进入，以保证**独占访问**。

**3. 单纯用本节的方法会遇到什么新问题？**

两个或多个进程各自已占用某些资源，又同时请求对方持有的资源，形成**互相等待**；无外部干预就会**永久阻塞**——这就是**死锁**。成因、必要条件、检测与解决方案是 2.4 节的内容。

**本节骨架回顾**：临界资源与四段结构（KP49）→ 同步/互斥与四准则（KP50–51）→ 软件实现四法（KP52–55）→ 硬件实现三法（KP56–58）→ 互斥锁（KP59）→ 信号量（KP60–64）→ 解题三步法（KP65）→ 三大经典问题（KP66–71）→ 管程（KP72–74）。

**易错点**：软件、硬件、互斥锁、信号量、管程是**逐级改进**的关系，考点常落在「哪一种满足让权等待」上：软件四法和硬件方法都是**忙等**（不满足让权等待），**记录型信号量**和**管程**才实现了让权等待。

# 2.4 死锁

## KP76 死锁的定义

**核心结论**：**多个进程因竞争资源而相互等待**——每个进程都占有一部分资源，同时等待其他进程占有的资源，而这些资源都不会被释放，形成**循环等待链**，导致所有相关进程**永久阻塞**，无外部干预就无法推进。

- 生活类比：单车道窄巷，两车对向驶入、都不肯倒车，互相堵死。
- 系统实例：一台打印机 + 一台扫描仪，P1 占扫描仪要打印机，P2 占打印机要扫描仪，双方都不释放。

**易错点**：

- 死锁的关键不是「资源不够」，==而是**已占有的不释放 + 又去等别人的**==。资源充足也可能死锁（推进顺序不当）。
- 「无外部干预无法解除」是死锁的定语，进程自己等不出结果。

## KP77 死锁与饥饿的区别

**核心结论**：

- **死锁**：==每个进程都在等一个只能由**组内另一进程**触发的事件（通常是释放资源）。==
- **饥饿**：==资源分配策略**不公平**（等待时间无上界）==，某进程长期得不到资源而无法推进。例：打印调度用 SPF，长文件被不断到达的短文件挤掉，永远排不上。

| 维度       | 死锁                     | 饥饿                                       |
| -------- | ---------------------- | ---------------------------------------- |
| **进程数**  | **必须 ≥ 2**，==且存在循环等待== | **可以只有 1 个**                             |
| **进程状态** | ==**必定是阻塞态**==         | ==可能是**就绪态**（如 SPF 下长期抢不到 CPU），也可能是阻塞态== |
| **系统整体** | 相关进程全部卡死               | 系统仍在正常运行，只是个别进程被持续忽略                     |

共同点：相关进程都无法向前推进。

**易错点**：

- 「饥饿进程一定是阻塞态」是错的，就绪态排队排不上也算饥饿。
- 死锁必然涉及**循环等待**，饥饿不需要环。

## KP78 死锁产生的两大原因

**核心结论**：

**（1）系统资源的竞争**——==竞争**不可剥夺资源**（打印机、磁带机等）且分配策略不当。==

- 关键限定：死锁与**不可剥夺资源**密切相关；**只竞争可剥夺资源（如 CPU 时间片）一般不会死锁**，因为 OS 可以强制回收。

**（2）==进程推进顺序非法**——即使资源充足，请求/释放的**顺序**不合理仍会死锁。==

- 例：P1 占 R1、P2 占 R2，随后 P1 申请 R2、P2 申请 R1，双方阻塞且都不放手。
- ==**同步机制使用不当**同样会死锁：A 等 B 的消息、B 等 A 的消息。此时消息通道 / 同步对象可视为一种**逻辑资源**，没有硬件资源也能死锁。==

**易错点**：

- 「死锁一定是资源不足造成的」是错的，第二类原因与资源多少无关。
- 只涉及可剥夺资源不死锁；PV 操作写错顺序（如 P(mutex) 写在 P(empty) 前）也是这里的第二类原因，属于典型考点。

## ==KP79 死锁产生的四个必要条件（必背）==

**核心结论**：四条**必须同时满足**，==**任一条不成立死锁就不会发生==**——这正是「死锁预防」的下手点。

| 条件          | 含义                                                     |
| ----------- | ------------------------------------------------------ |
| ==**互斥条件**==    | 资源要求**排他性使用**，一段时间内只能被一个进程占有，其他进程请求就得等                 |
| ==**不可剥夺条件**==  | 已获得的资源在用完前**不能被强行抢走**，只能由持有者主动释放                       |
| ==**请求并保持条件**== | 进程**已持有至少一个资源**，又提出新请求；新请求得不到就阻塞，但**已占有的死不松手**         |
| ==**循环等待条件**==  | 存在进程集合 {P1, P2, …, Pn}，每个 Pi 等待的资源正被下一个进程占有，**首尾相接成环** |

**苹果类比**（区分中间两条）：

- 手里的苹果别人**不能强行抢走** → **不可剥夺**。
- 手里拿着一个苹果，**又去要第二个，且在拿到之前不肯放下第一个** → **请求并保持**。

**易错点**：

- 「必要条件」不是充分条件——四条全满足也**未必**真死锁（见 KP80）。
- 最容易混的是不可剥夺 vs 请求并保持：前者说的是**别人抢不走**，后者说的是**自己不主动放**。

## KP80 环 ≠ 死锁：资源分配图有环的判定

**核心结论**：循环等待条件与死锁的定义**不等价**。资源分配图中**存在环，并不必然死锁**——当某类资源有**多个实例**时，环外的进程释放实例就能解开等待。

- 教材例：输出设备有 2 个实例，P0 和环外的 Pk 各持一台。Pn 请求一台时，只要 P0 或 Pk 任一释放，Pn 就能拿到，环自行解除。

**判定规则（必背）**：

| 情形             | 环与死锁的关系                                            |
| -------------- | -------------------------------------------------- |
| **每类资源只有一个实例** | ==图中有环 ⟺ 死锁（**充分必要条件**）==                          |
| **某类资源有多个实例**  | ==有环只是**必要条件**（潜在风险），是否死锁要靠**化简资源分配图**判断（见 KP95）== |

**易错点**：

- 「资源分配图中有环 → 系统死锁」只在**每类资源单实例**时成立，多实例时是常见陷阱选项。
- 反过来永远成立：**死锁 → 图中一定有环**（无环必无死锁）。

## KP81 资源数计算题型：不发生死锁的临界条件（真题必考）

**真题**：单类资源竞争时发生死锁的临界条件的分析（2009、2014）；多类资源竞争时发生死锁的临界条件分析（2016、2021）

**核心结论**：思路只有一句——**让每个进程都差一个**，就是最坏情况；**再多给一个**，必有一个进程能跑完并归还全部资源，连锁推进，死锁解除。

**（1）同类资源、每个进程最大需求相同**：$n$ 个进程，每个最多需要 $w$ 个同类资源，资源总数 $m$。

$$\text{最坏情况(全部阻塞)} = n(w-1) \qquad \text{保证不死锁} \iff m \geqslant n(w-1)+1$$

- 反解进程数：$n \leqslant \dfrac{m-1}{w-1}$（向下取整）。
- 例（2009 型）：3 个进程各需 4 个 → 至少 $3\times3+1=10$ 个才保证不死锁。

**（2）同类资源、最大需求各不相同**：进程 $P_i$ 最大需求 $w_i$。

$$\text{保证不死锁} \iff m \geqslant \sum_{i=1}^{n}(w_i-1)+1 = \sum w_i - n + 1$$

**（3）多类资源**：对**每类资源分别**套上式；只要有一类满足不死锁条件，就能靠它推进。

**易错点**：

- 公式里是 $w-1$ 不是 $w$：卡死的临界点是每人手里 $w-1$ 个（各差 1 个），不是 $w$ 个。
- 问「**至少多少个资源保证不死锁**」用 $n(w-1)+1$；问「**最多多少个资源仍可能死锁**」答 $n(w-1)$。两问差 1，看清问法。
- 「保证不死锁」是**充分条件**；资源数少于该值只是**可能**死锁，不是必然。

## KP82 死锁处理的三种策略与对比

**核心结论**：三大类策略，前两类**事前防范**，第三类事后补救；**忽略死锁**（假定不会发生）被 Linux / Windows 等通用 OS 采用。

| 策略          | 做法                                    | 时机  |
| ----------- | ------------------------------------- | --- |
| **死锁预防**    | ==设**严格限制条件**，破坏四个必要条件之一或多个==         | 事前  |
| **死锁避免**    | 资源动态分配时==用算法判断分配后是否仍**安全**，安全才分配==    | 事前  |
| **死锁检测与解除** | 不加限制，自由申请；**定期运行检测算法**，发现死锁就终止进程或剥夺资源 | 事后  |

**三者对比（表 2.5，必背）**：

|        | 分配策略                            | 主要优点                       | 主要缺点                               |
| ------ | ------------------------------- | -------------------------- | ---------------------------------- |
| **预防** | 保守，宁可资源闲置（一次请求全部 / 资源剥夺 / 按序分配） | ==**无须运行时检测**，实现简单==       | 资源利用率低；剥夺可能频繁；==**不适用于动态请求**==     |
| **避免** | ==预防与检测的**折中**，运行时判断是否可能死锁==    | ==**无须资源剥夺**==，资源利用率较高     | ==**须预知最大资源需求**==；进程可能因长期不安全被无限期推迟 |
| **检测** | 宽松，能分配就分配                       | ==**不限制资源申请**==，无启动延迟，分配灵活 | 检测与解除有额外开销；==终止或剥夺可能**丢失已完成工作**==  |

**易错点**：

- 预防 vs 避免：预防是**破坏必要条件**（一刀切、静态），避免是**每次分配前算一次安全性**（动态、限制宽松、性能更好但实现复杂）。
- 「预防死锁的限制条件严格但实现简单，避免死锁限制宽松但实现复杂」——这句对比是选择题原句。

## KP83 破坏互斥条件（不可行）

**真题**：死锁预防的特点（2019）

**核心结论**：把只能互斥使用的资源改成**允许多进程共享访问**，死锁自然消失。

## KP84 破坏不可剥夺条件

**核心结论**：进程**请求新资源而得不到**时，**强制释放它已占有的全部资源**，以后需要再重新申请——资源被临时剥夺。

**代价**：

- 对打印机这类不可剥夺的外设，强制释放会让**已完成的工作失效**，甚至造成设备状态混乱。
- ==频繁申请/释放**显著增加系统开销**，延长周转时间、降低吞吐量。==
- ==结论：**实际系统中极少采用**==。

**易错点**：注意触发时机是「请求新资源**失败时**」才释放已有资源，不是随时被别人抢。

## KP85 破坏请求并保持条件

**核心结论**：要求进程请求新资源时**不得持有任何不可剥夺资源**。两种实现：

| 方法                  | 做法                                                    |
| ------------------- | ----------------------------------------------------- |
| **① 静态资源分配（一次性申请）** | ==进程**运行前一次性申请全部所需资源**；系统满足不了就**暂不投入运行**；运行期间不再提新请求== |
| **② 动态释放后申请**       | 对①的改进：先拿到初期资源就可开始执行，==但运行中**必须先释放所有已用完的资源**，才能申请新资源== |

**方法①的优缺点**：实现**简单**，但

- **资源浪费严重**：运行初期就占全部资源，其中一些可能只在末期用、甚至从未用到，长期闲置。
- ==**易引发饥饿**：某些资源长期被别人占着，等它的进程迟迟无法启动。==

**易错点**：

- 静态分配法既是「破坏请求并保持」的典型手段，==也是 **「预防死锁」列表里的「一次请求所有资源」** ，两处说的是同一件事。==
- ==它导致的是**饥饿**==，不是死锁——别把结论说成「仍可能死锁」。

## KP86 破坏循环等待条件：资源有序分配法

**核心结论**：给每类资源赋**唯一编号**，==规定进程**必须按编号递增的顺序申请**不同类资源==，==**同类资源须一次性申请**。==

- 等价说法：进程只有在**未持有任何资源**、或**仅持有较小编号资源**时，才允许申请更大编号的资源。
- 为什么有效：==**已持有大编号资源的进程不可能再申请小编号资源**，所以资源分配图中**不可能出现环**。==

**缺点**：

1. 资源**编号需相对稳定**，不利于新增设备类型。
2. 实际使用顺序可能与编号次序不一致，导致资源**提前占用、长期闲置**，造成浪费。
3. 强制按固定次序申请，**增加用户编程复杂性**。

==**易错点**：约束的是**不同类资源之间的顺序**；同类资源是「一次性申请」，别混成「同类也要按序一个个申请」。==

## KP87 安全状态与安全序列

**真题**：系统安全状态的分析（2018）

**核心结论**：==死锁避免**不预先破坏必要条件**，而是**每次分配资源前动态判断**这次分配会不会引发死锁，安全才分配，否则让进程等待。约束宽松，所以系统性能较好。==

- **安全序列**：存在进程执行序列 (P1, P2, …, Pn)，使得对序列中每个 Pi，**在它之前的所有进程都执行完并释放资源后**，系统的可用资源足以满足 Pi 的**尚需资源量（Max − Allocation）**，从而保证 Pi 能顺利完成。安全序列**可能有多个**。
- **安全状态**：能找出至少一个安全序列。找不到任何安全序列 → **不安全状态**。

**教材例（表 2.6）**：3 个进程共 12 台磁带机，Max 分别为 10 / 4 / 9，已分配 5 / 2 / 2，可用 3。

| 步骤 | 可用 | 动作 |
| --- | --- | --- |
| 起始 | 3 | P2 尚需 $4-2=2 \leqslant 3$，可满足 |
| P2 完成，还 4 台 | 5 | P1 尚需 $10-5=5 \leqslant 5$，刚好满足 |
| P1 完成，还 10 台 | 10 | P3 尚需 $9-2=7 \leqslant 10$，满足 |

→ 安全序列 (P2, P1, P3)，系统**安全**。

**反例**：若再分 1 台给 P3（已分配变 3，可用降为 2），则**无安全序列**：把 2 台给 P2 → P2 完成还 4 台 → 可用 4，但 P1 尚需 5、P3 尚需 6，都不满足，互相等待成死锁。

**易错点**：

- 比较的是**尚需资源量**，不是 Max，也不是已分配量。
- ==判断安全时**假设进程一旦满足就跑完并归还全部已分配资源**（不是只归还这次给的）。==
- 有多个可选进程时**任选一个**都行，==安全序列不唯一——填答案时按题目要求的顺序规则（一般按下标从小到大找）。==

## KP88 安全、不安全、死锁三者的关系（必背）

**核心结论**：

- ==**安全状态 ⟹ 一定不会发生死锁。**==
- ==**不安全状态 ⟹ 死锁可能发生，但不必然发生。**==
- ==逆推：**发生死锁时系统必定处于不安全状态**，但不安全状态不一定演变为死锁。==

一句话记：**安全 ⊂ 无死锁**，死锁只是不安全状态的一个子集。

**易错点**：

- 「不安全状态就是死锁状态」是错的，这是最高频的判断题陷阱。
- 「进入不安全状态后必须马上解除」也不对——==OS 只是**拒绝会导致不安全的分配**，宁可让进程等，属于保守策略（可能牺牲资源利用率）。==

## KP89 银行家算法的思想与四个数据结构

**真题**：银行家算法的特点（2013、2019）

**核心结论**：把 OS 当**银行家**、系统资源当**资金**、进程请求资源当**用户贷款**。每个进程运行前必须声明对各类资源的**最大需求量**，且

- 该最大需求量**在整个生命周期内不得更改**（否则安全性保证失效）；
- 声明总量**不得超过系统资源总量**。

进程运行中申请资源时：先看**当前是否够**，够则**试探性分配**并检查**分配后系统是否仍安全**，安全才正式分配，否则让它等待。

**四个数据结构**（$n$ 个进程、$m$ 类资源）：

| 结构 | 维度 | 含义 |
| --- | --- | --- |
| **Available** | 长度 $m$ 向量 | 各类资源**当前可用数** |
| **Max** | $n \times m$ | 每个进程对各类资源的**最大需求** |
| **Allocation** | $n \times m$ | **已分配**给每个进程的各类资源数 |
| **Need** | $n \times m$ | 每个进程**尚需**的各类资源数 |

$$\text{Need}[i,j] = \text{Max}[i,j] - \text{Allocation}[i,j]$$

**解题第一步永远是**：题目给 Max 和 Allocation，先算出 **Need 矩阵**。

**易错点**：

- ==银行家算法的前提是**预知最大需求**——这是它与死锁检测的本质区别，也是它在实际系统中难落地的原因。==
- Max 中途可改的话算法失效，选择题会拿这点做干扰项。

## KP90 银行家算法的四个步骤

**核心结论**：设 $\text{Request}_i$ 是 $P_i$ 的请求向量。收到请求后依次检查：

| 步           | 检查                                            | 不通过怎么办                     |
| ----------- | --------------------------------------------- | -------------------------- |
| **① 合法性**   | $\text{Request}_i \leqslant \text{Need}[i]$   | **非法请求**（超过声明的最大需求），报错     |
| **② 可用性**   | $\text{Request}_i \leqslant \text{Available}$ | 资源不足，$P_i$ **等待**          |
| **③ 试探性分配** | 修改三处数据结构                                      | —                          |
| **④ 安全性检查** | 跑安全性算法（KP91）                                  | 不安全就**撤销分配、恢复原值**，$P_i$ 等待 |

第③步的三条更新（必背，方向别记反）：

$$\text{Available} \mathrel{-}= \text{Request}_i \qquad \text{Allocation}[i] \mathrel{+}= \text{Request}_i \qquad \text{Need}[i] \mathrel{-}= \text{Request}_i$$

**易错点**：

- 顺序是**先合法性、再可用性**：请求超过 Need 是**非法**（程序出错），请求超过 Available 只是**要等**，两种结论完全不同。
- 第③步是**试探**，第④步不安全时必须**回滚**，三个数据结构都要恢复。
- 向量比较是**逐分量都 ≤** 才算成立，有一个分量超了就不成立。

## KP91 安全性算法（Work / Finish）

**核心结论**：尝试构造一个能让**所有进程依次跑完**的序列。

**两个向量**：

- **Work**：长度 $m$，当前可用资源，初值 $\text{Work} = \text{Available}$。
- **Finish**：长度 $n$ 布尔向量，初值全 **false**；进程被判定可完成时置 true。

**循环步骤**：

1. 在进程中找一个满足 **Finish[i] = false 且 Need[i] ≤ Work** 的 $P_i$。找到转 2，找不到转 3。
2. 模拟它跑完并释放全部资源：$\text{Work} = \text{Work} + \text{Allocation}[i]$，$\text{Finish}[i] = \text{true}$，回到 1。
3. 若**所有 Finish[i] 都为 true** → **安全状态**（此时序列即安全序列）；否则 → **不安全状态**。

**易错点**：

- 释放时加的是 **Allocation[i]（它手里全部资源）**，不是 Need[i]，也不是这次请求量。
- 判定用 **Need ≤ Work**，不是 Max ≤ Work。
- 只要**有一个** Finish 仍为 false 就是不安全，不需要全部卡住。

## ==KP92 安全性算法完整例题（表 2.7 / 2.8）==

**真题**：银行家算法的安全序列分析（2011、2012、2018、2020、2022）

**题设**：5 个进程 {P0…P4}，3 类资源 {A, B, C}，总量 (10, 5, 7)。$T_0$ 时刻：

| 进程 | Max (A B C) | Allocation (A B C) | **Need = Max − Alloc** |
| --- | --- | --- | --- |
| P0 | 7 5 3 | 0 1 0 | **7 4 3** |
| P1 | 3 2 2 | 2 0 0 | **1 2 2** |
| P2 | 9 0 2 | 3 0 2 | **6 0 0** |
| P3 | 2 2 2 | 2 1 1 | **0 1 1** |
| P4 | 4 3 3 | 0 0 2 | **4 3 1** |

Available = 总量 − 已分配和 = (10,5,7) − (7,2,5) = **(3, 3, 2)**。

**执行过程（表 2.8）**：

| 进程 | Work | Need | Allocation | Work + Alloc | Finish |
| --- | --- | --- | --- | --- | --- |
| P1 | 3 3 2 | 1 2 2 | 2 0 0 | **5 3 2** | true |
| P3 | 5 3 2 | 0 1 1 | 2 1 1 | **7 4 3** | true |
| P4 | 7 4 3 | 4 3 1 | 0 0 2 | **7 4 5** | true |
| P2 | 7 4 5 | 6 0 0 | 3 0 2 | **10 4 7** | true |
| P0 | 10 4 7 | 7 4 3 | 0 1 0 | **10 5 7** | true |

初始 Work=(3,3,2) 时 P1(1,2,2) 与 P3(0,1,1) 都满足，本例选 P1 起头（选 P3 也可）。

→ 安全序列 **{P1, P3, P4, P2, P0}**，$T_0$ 时刻系统**安全**。

**做题模板**：算 Need → 算 Available → 逐行扫 Need ≤ Work → 加 Allocation 更新 Work → 直到全 true。最后 Work 必然回到资源总量 (10,5,7)，可当**自检**。

**易错点**：

- Available 常需自己算：**总量 − 各进程 Allocation 之和**，题目未必直接给。
- 扫描时要**从头重新扫**未完成的进程，别只往后看。
- P0 的 Need 最大所以排最后，直觉上「谁 Need 小谁先上」通常成立，但**必须逐分量验证**，不能只比总量。

## KP93 银行家算法例题：三个请求的三种结局

**接 KP92 的 $T_0$ 状态**，依次处理三个请求。

**① P1 请求 $\text{Request}_1 = (1, 0, 2)$ → 批准**

- 合法性：$(1,0,2) \leqslant \text{Need}_1(1,2,2)$ ✓
- 可用性：$(1,0,2) \leqslant \text{Available}(3,3,2)$ ✓
- 试探分配：Available = **(2,3,0)**，$\text{Alloc}_1$ = **(3,0,2)**，$\text{Need}_1$ = **(0,2,0)**
- 安全性：Work=(2,3,0) 起，得安全序列 **{P1, P3, P4, P0, P2}** → **安全，正式分配**

分配后状态（表 2.10）：Available = (2, 3, 0)

| 进程 | Allocation | Need |
| --- | --- | --- |
| P0 | 0 1 0 | 7 4 3 |
| P1 | 3 0 2 | 0 2 0 |
| P2 | 3 0 2 | 6 0 0 |
| P3 | 2 1 1 | 0 1 1 |
| P4 | 0 0 2 | 4 3 1 |

**② P4 请求 $\text{Request}_4 = (3, 3, 0)$ → 等待**

- 合法性：$(3,3,0) \leqslant \text{Need}_4(4,3,1)$ ✓
- 可用性：$(3,3,0) > \text{Available}(2,3,0)$（A 分量 3 > 2）✗ → **资源不足，P4 等待**，第②步就结束，不必试探分配

**③ P0 请求 $\text{Request}_0 = (0, 2, 0)$ → 拒绝**

- 合法性 ✓；可用性：$(0,2,0) \leqslant (2,3,0)$ ✓
- 试探分配：Available = **(2,1,0)**，$\text{Alloc}_0$ = (0,3,0)，$\text{Need}_0$ = (7,2,3)
- 安全性：Available(2,1,0) **无法满足任何进程的 Need**（P1 缺 B、P3 缺 C、P2/P4/P0 缺 A 或 B）→ **不安全**
- 结论：**拒绝请求，撤销试探性分配，三个数据结构全部恢复原值**

**三种结局对照**：

| 卡在哪一步 | 结论 | 系统动作 |
| --- | --- | --- |
| ① 合法性不过 | **非法请求** | 出错处理（超过声明的最大需求） |
| ② 可用性不过 | 资源暂时不足 | 进程**等待**，无需试探 |
| ④ 安全性不过 | 分配后**不安全** | **回滚**，进程等待 |
| 全过 | 安全 | 正式分配 |

**易错点**：

- 第②步就被挡下时**不要往下算安全性**——考试写多余步骤不得分还容易算错。
- 第④步不安全 ≠ 已死锁，只是系统**保守拒绝**；此时资源其实还够 P0 拿走那 2 个 B，但 OS 不冒这个险。
- ③ 中 P0 的请求分量小、看起来无害，仍被拒——说明**判断依据只有安全性算法，不是请求大小**。

## KP94 死锁避免 vs 死锁检测（真题原句）

**真题**：死锁避免和死锁检测的区分（2015）

**核心结论**：

|             | 死锁避免                               | 死锁检测                   |
| ----------- | ---------------------------------- | ---------------------- |
| **目标**      | 保证系统**始终不进入死锁状态**                  | ==只判断**当前时刻是否已发生死锁**== |
| **是否需预知未来** | **需要**预先知道进程从开始到结束的**全部资源需求（Max）** | **不需要**，只依据当前的分配与请求情况  |
| **时机**      | 每次分配资源**之前**                       | 事后**定期**运行             |
| **手段**      | ==安全性算法 / 银行家算法==                  | ==资源分配图化简==            |

若系统在分配资源时**不采取任何预防或避免措施**，就**必须**提供死锁检测与解除机制。

**易错点**：这条对比的考法就是「哪种方法需要预知最大资源需求」——答**死锁避免（银行家算法）**，检测不需要。

## KP95 资源分配图、化简与死锁定理

**真题**：多类资源竞争时发生死锁的临界条件分析（2016、2021）

**核心结论**——**资源分配图**的画法：

| 图元               | 含义                        |
| ---------------- | ------------------------- |
| ==**圆圈**==           | ==进程==                        |
| ==**矩形框**==          | ==一类资源；框内**圆点数 = 该类资源的实例数**== |
| **请求边**（进程 → 资源） | 该进程申请**一个单位**该类资源         |
| **分配边**（资源 → 进程） | 该类资源的**一个实例**已分配给该进程      |

**化简步骤**：

1. ==找一个**当前可继续执行**的进程 $P_i$：它的**所有请求都能被空闲资源满足**。==
   - **空闲数 = 该类资源总数 − 已分配实例数（= 资源节点的出度）**。
   - 例（图 2.16a）：$R_1$ 总数 3、出度 3 → 空闲 0；$R_2$ 总数 2、出度 1 → 空闲 1。P1 只请求 1 个 $R_2$，可满足 → P1 可执行。
1. ==删除 $P_i$ 的**全部请求边和分配边**，使其成为**孤立结点**；它释放的资源可能让别的阻塞进程转为可执行（P1 释放 $R_1$ 后 P2 的请求得以满足）。==
2. 重复，==若最终能**删除图中所有边** → 该图**可完全简化**。==

**死锁定理**：**系统处于死锁状态 ⟺ 资源分配图不可完全简化。**

**补充（教材注意）**：化简后**仍有边相连的进程就是死锁进程**——死锁解除时挑的就是这些进程。

**易错点**：

- 化简顺序**不影响结论**：能完全简化就是不死锁，与先删谁无关。
- 「有环即死锁」只在每类资源**单实例**时成立（见 KP80），多实例必须化简。
- ==数空闲资源时用**出度（分配边数）**，别把请求边也算进去。==

## KP96 死锁解除的三种方法

**真题**：解除死锁的方式（2019）

**核心结论**：

| 方法        | 做法                                                  | 代价 / 风险                                             |
| --------- | --------------------------------------------------- | --------------------------------------------------- |
| **资源剥夺法** | **挂起**部分死锁进程，抢占其资源重新分配给其他死锁进程，打破死锁环                 | ==被挂起的进程可能长期得不到资源而**饥饿**==                          |
| **撤销进程法** | 强制**终止**部分或全部死锁进程，回收其资源；按**优先级或撤销代价**（如资源占有量）决定终止顺序 | 实现**最简单**，但代价可能很高：接近完成的进程被杀，==**已完成工作全部丢失**，需从头执行== |
| **进程回退法** | 让死锁进程**回退到之前某个足以回避死锁的状态**，回退中**自愿释放**资源             | ==需**记录历史状态、设置还原点**，实现**最复杂**==                     |

**易错点**：

- 三种方法都要先靠检测算法（化简资源分配图）**定位死锁进程**——化简后仍有边的进程。
- 撤销法「简单但代价高」、回退法「无须剥夺但实现复杂」、剥夺法「可能引起饥饿」，各自的关键词别串。

## KP97 本节小结：2.4 的两个开篇问题

**1. 为什么会产生死锁？产生死锁有什么条件？**

死锁是多个进程因**竞争不可剥夺资源**而陷入永久阻塞：每个进程占有部分资源，同时等待其他进程占有的资源，导致全部无法推进。必须**同时满足**四个必要条件：① **互斥**（资源同一时刻只能被一个进程占有）；② **不可剥夺**（已获得的资源用完前不能被强制收回，只能主动释放）；③ **请求并保持**（占有资源的同时申请新资源，得不到就阻塞但不释放已占有的）；④ **循环等待**（多个进程构成循环等待链，每个都在等下一个占有的资源）。

**2. 有什么办法可以解决死锁问题？**

① **死锁预防**：限制资源分配方式，**破坏某个必要条件**，从根本上防止死锁；② **死锁避免**：动态分配时用**安全性算法**判断分配后是否仍安全，安全才批准（银行家算法）；③ **死锁检测与解除**：不加限制，定期**化简资源分配图**检测，发现死锁后剥夺资源、撤销进程或回退进程予以解除。

**本节骨架回顾**：定义与饥饿之别（KP76–77）→ 两大成因（KP78）→ 四个必要条件（KP79）→ 环 ≠ 死锁与资源数计算（KP80–81）→ 三种策略对比（KP82）→ 预防：破坏四条件（KP83–86）→ 避免：安全状态与银行家算法（KP87–93）→ 检测：资源分配图化简与死锁定理（KP94–95）→ 解除三法（KP96）。

**易错点**：预防（静态、一刀切）、避免（动态、需预知 Max）、检测（事后、不需预知）三者的**时机与前提**是本节最核心的区分点，几乎每年都以选择题形式出现。
