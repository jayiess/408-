# 4.1 文件系统基础

## KP1 文件的定义与三要素

**核心结论**：==文件是存储在**持久性存储设备**（硬盘、固态盘）上的信息集合==。进程是系统运行时**资源调度分配**的基本单位，文件是用户进行**输入/输出操作**的基本逻辑对象——两个「基本单位」分管两件事，别混。

任何一个文件都由三部分要素构成（对应图书馆类比）：

| 要素 | 内容 | 图书馆类比 |
| --- | --- | --- |
| 数据本身 | 存储空间里保存的信息 | 书的内容 |
| 分类与索引信息 | 供系统分类、组织、查找 | 书分书库、编号、录入管理系统 |
| 访问控制信息 | 不同用户的权限差异 | 绝版书限高权限读者借阅 |

**跨科关联**：[[知识点/CO-01-计算机系统概述.md]] KP10（存储器的层次划分）——文件所在的外存是层次结构的最底层，容量最大、速度最慢、断电不丢。

**易错点**：==操作系统对文件**并无严格统一的定义**。教材给的「数据项—记录—文件」是一种结构化表述，不是所有系统都这么实现（如 UNIX 把一切当字节流）。==

**易错点**：==文件的基本访问单元**可以是字节，也可以是记录**==，取决于文件是无结构还是有结构，不是固定的。

## KP2 文件系统屏蔽了什么：三层抽象

**核心结论**：==文件系统是操作系统中**专门管理文件资源**的部分==，它对二级存储资源做抽象，屏蔽掉三样东西：

| 屏蔽掉的底层细节    | 用户因此不必关心         |
| ----------- | ---------------- |
| 文件的内部属性     | 文件在内部按什么格式组织字节   |
| 存储介质的物理特性   | 磁盘/固态盘的寻道、扇区、块大小 |
| 文件在设备上的具体位置 | 文件占哪些物理块、是否连续    |

**用户视角关心的 vs 不关心的**（这条常被出成「文件系统对用户提供什么」）：

| 用户关心         | 用户不关心（系统负责） |
| ------------ | ----------- |
| 怎么命名、分类、查找文件 | 文件在外存上如何存储  |
| 数据安全性如何保障    | 外存区域如何分配与回收 |
| 能对文件做哪些操作    | 逻辑块到物理块怎么映射 |

**跨科关联**：[[知识点/OS-01-计算机系统概述.md]] KP3（四大管理功能）——文件管理是 OS 四大管理功能之一，与处理机、存储器、设备管理并列。

**易错点**：==文件系统屏蔽的是**物理细节**==，不是逻辑结构。==文件的逻辑结构（顺序、索引）恰恰是暴露给用户的，用户创建文件时要选。==

## KP3 自底向上的文件结构：数据项 → 记录 → 文件

**核心结论**：三级结构，自底向上：

| 层级    | 定义                        | 说明                 |
| ----- | ------------------------- | ------------------ |
| 基本数据项 | 描述一个对象**某一方面属性的一个值**      | 数据中的**最小逻辑单位**     |
| 组合数据项 | 由多个基本数据项组成                | 与基本数据项同属「数据项」这一级   |
| 记录    | 一组相关数据项的集合                | 描述一个对象**某方面的完整属性** |
| 文件    | 创建者定义的、**有文件名**的一组相关元素的集合 | ==分有结构文件、无结构文件==   |

**易错点**：==**数据项是最低级的组织形式，基本数据项才是最小逻辑单位**==。「数据项」这一级里含基本和组合两种，组合数据项不比记录低一级——它仍是数据项。

**易错点**：==文件必须**有名字**才叫文件（名字是标识符）==；一组无名的相关记录不构成文件。

## KP4 文件的八项属性（元数据）

**核心结论**：文件的数据内容之外，OS 还维护一批附加信息，统称**文件属性**，也叫**文件元数据**（metadata）。八项：

| 属性  | 内容                   | 备注                     |
| --- | -------------------- | ---------------------- |
| 名称  | 文件的标识符               | **同一目录内必须唯一**（不同目录可同名） |
| 类型  | 文件种类                 | 供系统决定如何处理/打开           |
| 创建者 | 创建该文件的用户 ID          | 创建后**不变**              |
| 所有者 | 当前拥有该文件的用户 ID        | **可变**，通常有权改属性和权限      |
| 位置  | 指向文件在外存物理存储位置的**指针** | 不是文件内容本身               |
| 大小  | 当前占用空间（字节/字/块）       |                        |
| 保护  | 访问控制策略（读/写/执行）       |                        |
| 时间  | 创建时间、最后修改时间、最后访问时间   | 用于审计、备份、缓存管理           |

**核心结论（易错重点）**：==**元数据 ≠ 文件数据**。元数据描述文件而不含文件内容，它存在 FCB / 索引节点里（4.2 详述），2009 年真题就考「文件属性信息存在哪」。==

**易错点**：**创建者和所有者是两个属性**。创建者是历史记录，所有者随所有权转移而变，权限判断看所有者。

**易错点**：文件名唯一性只要求**同一目录内**唯一，不是全盘唯一。这正是树形目录能解决重名问题的原因。

## KP5 文件的四种分类方式

**核心结论**：分类标准不同，结果不同，别把标准搞串：

| 分类标准       | 类别                     |
| ---------- | ---------------------- |
| 按性质和用途     | 系统文件、用户文件、库文件          |
| 按数据形式      | 源文件、目标文件（编译中间产物）、可执行文件 |
| 按存取控制属性    | 只读文件、读/写文件、可执行文件       |
| 按组织形式与处理方式 | 普通文件、目录文件、特殊文件（如设备文件）  |

**跨科关联**：[[知识点/CO-01-计算机系统概述.md]] KP23（从源程序到可执行文件的四个阶段）——「源文件→目标文件→可执行文件」这条链就是预处理、编译、汇编、链接的产物序列。

**易错点**：**「可执行文件」在两个标准里都出现**（按数据形式、按存取控制属性），但含义不同：前者指内容是机器码，后者指权限只允许执行。

**易错点**：==**目录本身也是文件**（目录文件），设备也被抽象成文件（特殊文件）。UNIX 「一切皆文件」就是这个思想。==

## KP6 文件系统设计的两个核心问题

**核心结论**：设计一个文件系统要解决两件事，一上一下：

| 方向      | 问题            | 具体内容                     |
| ------- | ------------- | ------------------------ |
| 向上（对用户） | 定义**用户接口**    | 文件及其属性、允许的操作类型、目录结构的组织方式 |
| 向下（对硬件） | 设计**算法与数据结构** | 把逻辑上的文件系统映射到物理外存设备上      |

**易错点**：现代 OS **同时支持多种文件系统**（FAT、NTFS、ext4……），所以「文件系统的层次结构」没有唯一答案，教材图 4.1 只是**一个合理的**层次结构，不是标准。真题里问「层次划分」按王道这一套答。

## KP7 文件系统的四层结构（必背总表）

**核心结论**：自下而上四层，越往下越靠硬件：

```
逻辑文件系统      ← 管元数据、目录结构、FCB、文件保护（认"文件名"）
    ↑
文件组织模块      ← 逻辑块 ⇄ 物理块 映射 + 空闲空间管理（认"逻辑块号"）
    ↑
基本文件系统      ← 发通用命令读写物理块 + 内存缓冲区管理（认"磁盘地址"）
    ↑
I/O 控制         ← 设备驱动程序 + 中断处理程序（认"硬件指令"）
    ↑
       磁盘硬件
```

| 层 | 核心职责 | 认识的地址形式 |
| --- | --- | --- |
| 逻辑文件系统 | 元数据、目录、FCB、文件保护 | 文件名、路径名 |
| 文件组织模块 | 地址转换、空闲空间管理 | 逻辑块号 → 物理块号 |
| 基本文件系统 | 读写物理块、缓冲区管理 | 磁盘物理地址 |
| I/O 控制 | 驱动 + 中断，实际搬数据 | 硬件控制器指令 |

教材图示：[[王道教材/27 王道操作系统/pictures/image-001.jpg]]（图 4.1 文件系统层次结构）

**易错点**：**逻辑文件系统在最上层，I/O 控制在最下层**。名字里带「基本」的不是最底层——最底层是 I/O 控制。

## KP8 I/O 控制层：设备驱动 + 中断处理

**核心结论**：最底层，由**设备驱动程序**和**中断处理程序**组成，负责在**内存与磁盘之间实际传输数据**。设备驱动程序的作用是**把高层命令翻译成硬件能识别的特定指令**，交由硬件控制器执行，并向 I/O 控制器指明「对设备的哪个具体位置执行何种操作」。

**跨科关联**：[[知识点/OS-01-计算机系统概述.md]] KP19（内核装了什么）——设备驱动和中断处理属于内核的**设备管理**部分；[[知识点/OS-01-计算机系统概述.md]] KP21（中断机制）解释了中断处理程序为什么必须在内核态。

**易错点**：设备驱动程序**不做地址转换（逻辑块→物理块）**，那是文件组织模块的活。驱动只做「命令翻译」：软件命令 → 硬件指令。

## KP9 基本文件系统：物理块读写 + 缓冲区管理

**核心结论**：向设备驱动程序发送**通用命令**，读写磁盘上的**物理块**，每个物理块由**唯一的磁盘地址**标识。同时管理**内存缓冲区**，缓存三类东西：

| 缓存内容 | 用途 |
| --- | --- |
| 文件系统元数据 | 避免反复读盘取属性 |
| 目录项 | 加速路径解析 |
| 数据块 | 减少实际 I/O 次数 |

==执行磁盘传输前必须先**分配并维护合适的缓冲区**——缓冲区管理对系统性能至关重要。==

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP33（局部性原理）——缓冲区能起效，靠的是文件访问同样具有时间/空间局部性。

**易错点**：**缓冲区管理在基本文件系统层，不在 I/O 控制层**。这是层次归属题的高频陷阱。

**易错点**：这一层发的是**通用命令**（读第 n 块），转成硬件指令是下一层驱动的事。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 缓冲区具体怎么影响性能？为什么分配到基本文件系统这一块？
> <span style="color: red;">答：命中缓存省掉毫秒级的物理 I/O，并让 CPU 与 DMA 并行、减少中断、把小写合并成整块写。归这一层是因为它缓存的对象是物理块，而认识磁盘地址的正是基本文件系统层。</span>

## KP10 文件组织模块：逻辑块 ⇄ 物理块 + 空闲空间管理

**核心结论**：两大职责：

| 职责 | 内容 |
| --- | --- |
| 地址转换 | 建立文件**逻辑块与物理块的映射**，把逻辑块地址转成物理块地址 |
| 空闲空间管理 | 内含**空闲空间管理器**，跟踪未分配的磁盘块，按需分配给文件 |

文件的逻辑块**按顺序编号 0 到 N**，但物理块布局通常与之不一致（文件可以离散存放），所以必须靠地址转换机制定位。

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP18（分页的逻辑地址结构）——「逻辑块号 → 物理块号」与内存管理的「页号 → 页框号」是同一个套路：都靠一张表把连续的逻辑编号映射到离散的物理位置。区别是页表在内存里，文件的索引结构在磁盘上（4.2 索引分配）。

**易错点**：**空闲空间管理属于文件组织模块**，不属于基本文件系统，也不属于逻辑文件系统。位示图、成组链接法（4.3.2）都归这一层。

**易错点**：逻辑块从 **0** 开始编号，算物理块号时别按 1 起算——这是后面混合索引分配计算题最容易掉的坑。

## KP11 逻辑文件系统：元数据、目录、FCB、文件保护

**核心结论**：最上层，管**文件系统的元数据**——即描述文件系统结构的信息（文件名、目录项、权限、时间戳），**不含实际数据内容**。三件事：

| 职责 | 内容 |
| --- | --- |
| 维护目录结构 | 根据给定**文件名**，向文件组织模块提供所需元数据 |
| 维护文件控制块 FCB | 记录各文件的属性与状态 |
| 实现文件保护 | 权限校验、访问控制 |

**易错点**：**这一层是唯一认识「文件名」的层**。往下走文件名就消失了，只剩逻辑块号、物理块号。所以「按文件名访问文件」这个能力由逻辑文件系统提供。

**易错点**：元数据里**不含文件数据本身**。「文件系统的元数据」和「文件的数据块」是两类东西，前者描述结构，后者是内容。

## KP12 四层职责归属辨析（易混收口）

**核心结论（易错重点）**：层次题只考「这件事归哪层」。把下表背下来，不要靠层名猜：

| 具体工作               | 归属层    | 常被误配到           |
| ------------------ | ------ | --------------- |
| ==把「读第 5 块」翻译成硬件指令==   | I/O 控制 | 基本文件系统          |
| ==中断处理==               | I/O 控制 | 基本文件系统          |
| ==发出「读物理块 n」的通用命令==    | 基本文件系统 | I/O 控制          |
| ==**内存缓冲区管理**==        | 基本文件系统 | I/O 控制 / 文件组织模块 |
| ==**逻辑块号 → 物理块号 转换**== | 文件组织模块 | 逻辑文件系统          |
| ==**空闲空间管理（位示图等）**==   | 文件组织模块 | 基本文件系统          |
| ==维护目录结构、解析路径==        | 逻辑文件系统 | 文件组织模块          |
| ==维护 FCB / 索引节点==      | 逻辑文件系统 | 文件组织模块          |
| ==文件保护、权限校验==          | 逻辑文件系统 | ——              |

判定口诀：

```
出现"文件名 / 目录 / 权限"  → 逻辑文件系统
出现"逻辑块号 / 空闲块"     → 文件组织模块
出现"物理块 / 缓冲区"       → 基本文件系统
出现"驱动 / 中断 / 硬件指令" → I/O 控制
```

**易错点**：**「地址转换」在文件管理里出现两次，别混**：文件组织模块做的是「文件逻辑块号 → 磁盘物理块号」；内存管理做的是「逻辑地址 → 物理地址」（[[知识点/OS-03-内存管理.md]] KP3）。两者层次不同、对象不同。

## KP13 逻辑结构 vs 物理结构（必分清）

**核心结论**：

| 项     | 逻辑结构                 | 物理结构（存储结构）        |
| ----- | -------------------- | ----------------- |
| 是什么   | **用户视角**看到的文件组织形式    | 文件在**外存上的实际存储方式** |
| 对用户   | 可见、创建文件时要选           | **透明**（用户看不见）     |
| 与介质关系 | **与存储介质无关**          | 由介质和分配方式决定        |
| 关心什么  | 文件内部数据在逻辑上如何组织       | 占哪些物理块、是否连续       |
| 本章位置  | 4.1.3（顺序、索引、索引顺序、散列） | 4.2.6（连续、链接、索引分配） |

**易错点**：**「顺序文件」是逻辑结构，「连续分配」是物理结构，两者毫无必然联系**。一个顺序文件完全可以用链接分配离散存放在磁盘上。这是本章最经典的偷换概念点。

**易错点**：逻辑结构的核心是「数据在逻辑上怎么组织」，**不涉及块、扇区**。一旦题目提到块号、簇、磁道，讨论的就是物理结构了。

> [!note] 我的笔记
> 

> [!question] 我的问题
> 顺序和有序是一个概念吗
> <span style="color: red;">答：不是。顺序指依次排列（排列方式），有序指按关键字排好（排列依据），串结构就是顺序而无序；算偏移靠定长，折半靠有序。</span>

## KP14 无结构文件（流式文件）

**核心结论**：最简单的组织形式，==由**连续的字符流**构成，长度以**字节**为单位==，故称**流式文件**。访问方式：靠**读/写指针**定位下一个要操作的字节。

典型例子：源程序、可执行文件、库函数（系统中数量最多的一类）。

**核心结论（易错重点）**：==无结构文件**没有显式的记录边界**==，所以要检索特定内容**==只能顺序查找==**，效率低，不适合频繁随机访问或按记录检索的场景。

**易错点**：「无结构」不等于「不能随机访问字节」。==按**字节偏移**定位是可以的（有读写指针），不能做的是**按记录/按内容**直接定位。==

**易错点**：可执行文件属于**无结构文件**（字节流），不要因为它内部有段、有头部就当成有结构文件——那是文件格式约定，不是文件系统认识的记录结构。

## KP15 有结构文件：定长记录 vs 变长记录

**核心结论**：有结构文件由一个或多个**记录**组成，也称**记录式文件**；每条记录由若干**数据项**组成，数量和长度可固定也可变。按记录长度是否一致分两类：

| 类型   | 定义                            | 定位方式              | 随机访问      |
| ---- | ----------------------------- | ----------------- | --------- |
| 定长记录 | ==所有记录长度相同，**各数据项在记录中位置固定**== | ==按**偏移量直接计算**==  | ==支持，高效== |
| 变长记录 | ==各记录长度不一（数据项数量不同，或某数据项长度可变）==    | ==无法直接计算，**只能顺序查找**== | ==不支持，慢==     |

**易错点**：定长记录要求的是「记录长度相同」**且**「数据项位置固定」两条，缺一条都不能直接算偏移。

**易错点**：变长记录慢的根因是==**无法计算第 i 条记录的起始位置**==，不是「读得慢」。==解决办法就是给它加索引表（KP18）。==

## KP16 顺序文件：串结构 vs 顺序结构

**核心结论**：==顺序文件的记录按**线性顺序**依次排列==，可定长也可变长。按**是否按键字排序**分两种：

| 结构       | 排列依据                         | 检索方式                  | 效率  |
| -------- | ---------------------------- | --------------------- | --- |
| **串结构**  | ==按**存入时间先后**排列，**不按键字排序**== | 必须从头顺序扫描              | 低   |
| **顺序结构** | 所有记录**按键字有序**排列              | 定长+有序时可算偏移，支持**折半查找** | 高   |

**核心结论（易错重点）**：只有**定长记录 + 按键字有序**（即顺序结构）才能同时享受「按偏移直接定位」和「折半查找」两个好处。少任何一个条件都退化成顺序扫描。

**跨科关联**：折半查找的判定树与 $O(\log_2 n)$ 复杂度见数据结构第 7 章（查找）——本仓库该章暂无知识点卡片，二轮补。

**易错点**：==**串结构不是「没有结构」**，它是有结构文件里的一种顺序文件，只是没按键字排。别和无结构文件（流式文件）混。==

## KP17 顺序文件的优劣：批量最优，单条最差

**核心结论（易错重点）**：两条必背结论：

| 结论                                      | 原因                               |
| --------------------------------------- | -------------------------------- |
| ==批量处理时，顺序文件的 **I/O 效率是所有逻辑文件类型中最高的**== | 记录连续存储、访问局部性强，连续读写大量记录时几乎无额外寻址开销 |
| 对**顺序存储设备（如磁带）**，顺序文件是**唯一**能有效工作的组织形式  | ==磁带只能顺序前进/后退，无法随机定位==           |

短板：频繁进行**单条记录**的查找、修改、插入、删除时性能明显不足——缺乏直接定位能力，且插删要**移动大量数据**。

**易错点**：「效率最高」的前提是**批量存取**。题目问「查找单条记录最快的逻辑结构」，答案是散列文件或索引文件，不是顺序文件。

**易错点**：磁带上「只有顺序文件能用」这条常被改成「磁带上只能用连续分配」——那是物理结构的说法，考的是逻辑结构，别接受这个偷换。

## KP18 记录定位公式：定长可算，变长要累加（必会算）

**核心结论**：设记录从 0 号开始编号。

**定长记录**（记录长度为 $L$），第 $i$ 条记录的地址：

$$A_i = i \times L$$

**变长记录**，必须从头依次读前 $i-1$ 条记录、累加其长度：

$$A_i = \sum_{j=0}^{i-1} L_j + 1$$

**易错点**：教材原式写成 $A_{i}=\sum_{i=0}^{i-1}L_{i}+1$，求和变量与外层下标**重名了**，实际含义是「累加第 0 到第 $i-1$ 条记录的长度」，用 $j$ 做求和变量才对。理解意思即可，别照抄下标。

**核心结论（易错重点）**：变长记录必须顺序扫描——**这就是索引文件存在的理由**。索引表把「变长记录的顺序查找」变成「定长索引项的随机查找」。

**易错点**：定长公式里 $i$ 从 0 起算时是 $iL$；若题目记录从 1 起算，要写成 $(i-1)L$。**先看编号起点再套公式**。

## KP19 索引文件：把变长的顺序查找变成定长的随机查找

**核心结论**：为**每条记录**建一个索引项，索引项含：**指向该记录的指针 + 该记录的长度**，索引表整体**按关键字排序**。

关键点在于：**索引表本身由定长记录构成**，所以索引表支持高效的随机访问（可算偏移、可折半）。于是：

```
变长记录顺序文件（只能顺序查找）
        ↓ 建索引表
定长索引文件（可随机查找）→ 查到指针 → 直接定位目标记录
```

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-2.jpg]]（图 4.2 索引文件示意图）

==代价：需额外维护一张索引表，且**每条记录对应一个索引项**，存储开销大。==

**易错点**：**索引项数 = 记录数**，这是索引文件（相对索引顺序文件）开销大的根源。索引顺序文件把它降到「组数」。

**易错点**：==索引文件加速的是**查找**，不是「读取内容」==。找到记录后读数据的开销不变。

**易错点**：==这里的「索引文件」是**逻辑结构**==，和 4.2.6 的「索引分配」（物理结构，索引块记录物理块号）是两回事，只是思想相同。

## KP20 索引顺序文件：分组 + 一级索引

**核心结论**：索引顺序文件 = **顺序文件 + 索引文件的结合**。最简单形式用**一级索引**：

| 步骤 | 做法 |
| --- | --- |
| ① 分组 | 把变长记录的顺序文件划分为若干组 |
| ② 建索引 | 只为**每组的首条记录**建一个索引项（含该记录的关键字 + 指针） |
| ③ 索引表排序 | 所有索引项按关键字**有序**排列 |

**核心结论（易错重点）**：**组内可以无序，但组间必须按键字有序**。这样才能靠索引表判断目标落在哪一组。

检索两步：① 在索引表中定位目标所属的组 → ② 在该组内**顺序查找**。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-3.jpg]]（图 4.3 索引顺序文件示意图，主文件按姓名首字母分组）

**跨科关联**：这就是数据结构里的**分块查找（索引顺序查找）**，本仓库数据结构第 7 章暂无卡片，二轮补。

**易错点**：索引项对应的是**每组首记录**，不是每条记录。索引项数 = **组数 m**，不是记录数 N。

## KP21 索引顺序文件的平均查找次数与 $m=\sqrt{N}$（必会算）

**核心结论**：设文件共 $N$ 条记录，均分为 $m$ 组，每组约 $s=N/m$ 条。

| 情形 | 平均查找次数 |
| --- | --- |
| 普通顺序文件 | $N/2$ |
| 索引表中顺序查找 | $m/2$ |
| 组内顺序查找 | $s/2 = (N/m)/2$ |
| **索引顺序文件总计** | $\dfrac{m}{2}+\dfrac{N}{2m}$ |

对 $m$ 求最小值：当 $m=\sqrt{N}$ 时取到最优，此时

$$\frac{m}{2}+\frac{N}{2m}=\frac{\sqrt{N}}{2}+\frac{\sqrt{N}}{2}=\sqrt{N}$$

**自己复算一遍**（教材数量级感受）：

| $N$ | 顺序文件 $N/2$ | 索引顺序文件最优 $\sqrt{N}$ | 提速 |
| --- | --- | --- | --- |
| 100 | 50 | 10 | 5 倍 |
| 10 000 | 5 000 | 100 | 50 倍 |
| 1 000 000 | 500 000 | 1 000 | 500 倍 |

**核心结论（易错重点）**：记录数极大时可引入**两级或多级索引**，进一步降低开销。三级以上同理，每加一级把 $\sqrt{\ }$ 再开一层。

**易错点**：$m=\sqrt{N}$ 时**组数和组内记录数相等**（都是 $\sqrt{N}$），最优值是 $\sqrt{N}$ 而不是 $\sqrt{N}/2$——两个 $\frac{\sqrt N}{2}$ 加起来正好是 $\sqrt N$。

**易错点**：这个公式的前提是**索引表和组内都用顺序查找**。若索引表改用折半查找，结果不再是 $\sqrt{N}$，要重算。

**易错点**：==索引文件和索引顺序文件提速的代价都是**额外的存储开销**（维护索引表）。问「缺点」时答这个，别答「速度慢」。==

## KP22 直接文件（散列文件）

**核心结论**：记录的**物理地址由关键字经散列函数直接计算**得出，不需要顺序扫描也不需要查索引表。

| 项   | 内容                          |
| --- | --------------------------- |
| 优点  | ==支持**极快的随机存取**（理论上一次定位）==  |
| 缺点  | 不同关键字可能映射到同一地址，产生**冲突**，需处理 |

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP14（基于索引搜索的三种分配算法）里的哈希算法——以空闲分区大小为关键字建哈希表，同样是「关键字直接算位置」的思路。散列函数设计与冲突处理（拉链法、开放定址法）见数据结构第 7 章。

**易错点**：散列文件是**逻辑结构**里唯一不靠「顺序 / 索引表」定位的一类，也是**随机存取最快**的一类。问「随机存取速度最快的逻辑结构」答散列文件。

**易错点**：散列文件**不适合批量顺序处理**——记录按散列值散布，逻辑上相邻的关键字物理上不相邻，顺序遍历反而慢。批量场景仍是顺序文件最优。

## KP23 文件逻辑结构总对比（收口必背）

**核心结论**：一张树 + 一张表收掉 4.1.3。

```
文件的逻辑结构
├─ 无结构文件（流式文件）── 连续字符流，靠读写指针，只能顺序检索
└─ 有结构文件（记录式文件）
    ├─ 按记录长度：定长记录（可算偏移）/ 变长记录（只能顺序）
    └─ 按组织形式
        ├─ 顺序文件 ── 串结构（按时间）/ 顺序结构（按键字）
        ├─ 索引文件 ──── 每条记录一个索引项
        ├─ 索引顺序文件 ─ 每组首记录一个索引项（分块查找）
        └─ 直接文件（散列文件）── 关键字经散列函数直接定址
```

| 结构 | 索引项数 | 随机存取 | 批量存取 | 额外开销 |
| --- | --- | --- | --- | --- |
| 无结构文件 | —— | 仅按字节偏移 | 好 | 无 |
| 顺序文件（串结构） | —— | 差 | **最优** | 无 |
| 顺序文件（顺序结构，定长） | —— | 好（可折半） | **最优** | 无 |
| 索引文件 | = 记录数 N | 好 | 一般 | **大** |
| 索引顺序文件 | = 组数 m | 较好（$\sqrt N$） | 一般 | 中 |
| 直接文件（散列） | —— | **最快** | 差 | 冲突处理 |

**核心结论（易错重点）**：有结构文件的四种逻辑组织方式（顺序、索引、索引顺序、散列）**本质上都是围绕「如何高效查找数据」设计的**，和数据结构第 7 章查找的四条路线一一对应：顺序查找、（有序表）折半查找、分块查找、散列查找。

**易错点**：别把「批量最优」和「随机最快」混着答。**批量 → 顺序文件；随机 → 散列文件**。

## KP24 本节小结：4.1 的两个思考题

**思考题 1：什么是文件？**

文件是操作系统中用于**存储和组织数据的基本单位**，是一组**逻辑上相关**的信息（程序、文本、图像等）的**有序集合**，通常以一个**名字标识**，保存在**持久性存储设备**上。

**思考题 2：文件系统在操作系统中的地位如何？**

文件系统是操作系统的**核心子系统之一**，对存储设备上的文件和目录进行统一管理，提供创建、读取、写入、删除、组织及保护等基本操作。地位是**承上启下**：

| 方向 | 作用 |
| --- | --- |
| 向上（对用户/应用） | 提供简洁一致的**抽象接口**，屏蔽底层存储细节 |
| 向下（对硬件） | 与设备驱动协同，高效调度**物理存储资源** |

**核心结论**：一句话记住定位——文件系统是**用户逻辑视图与物理存储之间的桥梁**。

**跨科关联**：[[知识点/OS-01-计算机系统概述.md]] KP2（OS 的三大角色）——文件系统同时扮演「资源管理者」（管磁盘空间）和「用户接口」（提供文件抽象）两个角色。

## KP25 目录管理的四个基本要求

**核心结论**：文件目录是一种**数据结构**，记录每个文件的属性和存储位置（元数据），供检索时快速定位其在外存中的物理地址。目录管理要满足四条：

| 要求 | 内容 |
| --- | --- |
| 实现按名存取 | 用户只给文件名，系统自动定位其外存位置——**最基本的功能** |
| 提高检索速度 | 合理组织目录结构，加快查找，提升存取效率 |
| 支持文件共享 | 多用户系统中允许多个用户共享同一文件 |
| 允许文件重名 | 不同用户可对各自的文件使用相同名称 |

**跨科关联**：[[知识点/OS-01-计算机系统概述.md]] KP30（系统调用的定义与五类功能）——目录操作（创建、删除、改变目录）全部属于文件管理类系统调用，必须陷入内核态执行。

**易错点**：**目录本身也是文件**（目录文件，KP5），所以目录同样存在磁盘上、同样占盘块，读目录也要磁盘 I/O。

**易错点**：「允许重名」靠的是**不同目录**，不是系统给文件编号。同一目录内文件名仍必须唯一（KP4）。

## KP26 文件控制块 FCB（真题）

**真题**：2009 考过文件属性信息的存储位置。

**核心结论**：FCB（File Control Block）是存放控制文件所需各种信息的数据结构，用来实现按名存取。**每个文件对应一个 FCB**，**所有 FCB 的集合就构成文件目录**（也称目录文件）。每创建一个新文件，系统就为它建立一个 FCB。

FCB 装三类信息：

| 类别 | 内容 |
| --- | --- |
| 基本信息 | 文件名、物理位置、逻辑结构、物理结构 |
| 存取控制信息 | 文件主、核准用户、一般用户各自的访问权限 |
| 使用信息 | 文件创建时间、最后修改时间等 |

**易错点**：**目录 = FCB 的集合**。传统实现里「目录项」和「FCB」是同一个东西；只有引入索引节点后，目录项才瘦身成〈文件名，inode 号〉两项（KP27）。

**易错点**：文件属性存在 FCB / 索引节点里，**既不在文件的数据块里，也不在文件名里**。2009 年真题问的就是这个。

## KP27 为什么要索引节点：目录项瘦身（真题高频，必会算）

**真题**：2020、2022 考过目录项结构的相关分析与计算；2018、2020 考过索引节点与文件容量的关系。

**核心结论**：查找文件时系统要逐块读入目录项、逐个比对**文件名**，只有比中的那一个才需要取它的物理地址。所以在检索阶段，除文件名外的描述信息**根本不必调入内存**。UNIX 的做法是**文件名与描述信息分离**：

```
描述信息 → 独立组织成索引节点 inode（存物理地址、权限、时间……）
目录项  → 只留〈文件名，索引节点号〉
```

**教材算例**（必须能自己复算）：

| 方案 | 每个目录项 | 每块（1KB）容纳 | 640 个文件的目录占块数 | 平均启动磁盘 |
| --- | --- | --- | --- | --- |
| 传统 FCB | 64B | 16 个 | 640/16 = 40 块 | **20 次** |
| UNIX 目录项 | 16B（14B 文件名 + 2B inode 号） | 64 个 | 640/64 = 10 块 | **5 次** |

降到原来的 **1/4**——目录项缩到 1/4，每块能装的目录项就多 4 倍，要读的块数就少 4 倍。

**易错点**：平均启动次数是**总块数的一半**（顺序查找的期望），不是总块数。40 块对应 20 次。

**易错点**：因果链是「**目录项变小 → 每块装的目录项变多 → 读盘次数变少**」，别记反成「inode 变小了」。inode 本身并没有变小，只是被挪出了目录。

**易错点**：加速的是**目录检索**，不是数据读取。inode 还要额外读一次盘，所以小文件访问的**总** I/O 未必减少，减少的是遍历目录的开销。

## KP28 磁盘索引节点的七项内容

**核心结论**：磁盘索引节点存于磁盘，是文件的「永久档案」，**每个文件唯一一个**。七项内容：

| 项 | 内容 |
| --- | --- |
| 文件主标识符 | 文件所属的用户或用户组 |
| 文件类型 | 普通文件 / 目录文件 / 特殊文件 |
| 文件存取权限 | 文件主、核准用户、一般用户各自的权限 |
| 文件物理地址 | **13 个地址项**，以直接或间接方式记录数据所在盘块号（KP45） |
| 文件长度 | 以**字节**为单位的实际大小 |
| 文件链接计数 | 本文件系统中指向该文件的**目录项（硬链接）数量**（KP56） |
| 文件存取时间 | 最近访问、最近修改、以及 inode 最近被修改的时间 |

**易错点**：**文件名不在 inode 里**。文件名只存在目录项中——这正是硬链接能让同一个文件拥有多个名字的根本原因。

**易错点**：文件长度以**字节**计，不是以盘块计。

**易错点**：链接计数只统计**本文件系统内**的目录项，这是硬链接不能跨文件系统的直接原因（KP58）。

## KP29 内存索引节点新增的五项

**核心结论**：文件被**打开**时，对应的磁盘 inode 被载入内存，再附加运行时状态信息成为内存 inode。在磁盘 inode 的基础上新增五项：

| 新增项 | 用途 |
| --- | --- |
| 索引节点号 | 在内存中唯一标识该节点 |
| 状态 | 该 inode 是否被上锁、是否已修改，用于缓存一致性管理 |
| 访问计数 | 每有一个进程访问加 1，访问结束减 1；为 0 时才可释放 |
| 逻辑设备号 | 文件所属文件系统的逻辑设备号，多文件系统环境下尤为关键 |
| 链接指针 | 分别指向空闲链表与散列队列，供内核高效调度和回收 |

**易错点**：新增的五项全是**运行时 / 内存管理**用的，不写回磁盘。磁盘 inode 里没有访问计数、没有状态。

**易错点**：**「访问计数」（内存 inode）≠「链接计数」（磁盘 inode）**。前者数的是当前访问它的进程数，随进程增减、不持久化；后者数的是硬链接数，随目录项增减、要持久化。这一对是本节最容易混的。

## KP30 单级目录结构

**核心结论**：整个文件系统只维护**一张全局目录表**，每个文件对应一个目录项。三种操作：

| 操作 | 做法 |
| --- | --- |
| 创建文件 | **先遍历整张目录表**确认无同名 → 再新增一个 FCB 并填入属性 |
| 访问文件 | 按文件名查到 FCB → 合法性检查 → 执行操作 |
| 删除文件 | 定位其 FCB → 回收所占存储空间 → 清除该 FCB |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-6.jpg]]（图 4.6 单级目录结构）

优点：实现了按名存取。缺点：**查找效率低、不允许文件重名、难以支持文件共享**，完全无法满足多用户需求，仅适用于早期单用户的简单文件系统。

**易错点**：单级目录**已经实现了按名存取**。按名存取是所有目录结构的共同底线，不是树形目录才有的能力。

**易错点**：它的致命缺陷是**不允许重名**——因为只有一个命名空间，创建时必须全表查重。

## KP31 两级目录结构

**核心结论**：目录分两层——**主文件目录 MFD** + **用户文件目录 UFD**：

| 层 | 每个目录项记录什么 |
| --- | --- |
| MFD（Master File Directory） | 一个**用户名** + 该用户 UFD 的存储位置 |
| UFD（User File Directory） | 该用户**所有文件的 FCB** |

用户访问自己的文件时，系统**只在其专属 UFD 中查找**。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-7.jpg]]（图 4.7 两级目录结构）

解决了两件事：**不同用户间的文件重名问题**，以及靠隔离用户命名空间带来的**安全性**增强。同时提升了检索效率，并支持基于目录的访问控制。

缺点：每个用户只有一个**扁平的 UFD**，无法对文件分类管理，组织复杂文件集合时灵活性不足。

**易错点**：两级目录解决的是**不同用户之间**的重名，同一用户自己的 UFD 内仍不能重名。

**易错点**：检索效率提升的原因是**查找范围从全系统缩小到单个用户**，不是因为目录项变小了。

## KP32 树形目录结构与路径名（真题）

**真题**：2010 考过设置当前工作目录的作用。

**核心结论**：两级目录向下推广即树形目录，用**路径名**标识文件。路径名是由路径上所有目录名和文件名用分隔符 `/` 连接成的字符串：

| 路径 | 起点 | 特点 |
| --- | --- | --- |
| 绝对路径 | **根目录** | 系统中每个文件的绝对路径**唯一**，如 Linux 的 `/dev/hda` |
| 相对路径 | **当前目录（工作目录）** | 如当前目录为 `/bin` 时的 `./ls`，`.` 表示当前工作目录 |

**当前目录的作用**：目录层次深时每次从根目录逐级查找耗时巨大，故为**每个进程**设一个当前目录，访问以它为基准，**减少路径检索的磁盘 I/O 次数**。用户登录后系统自动切到默认当前目录（Linux 记在 `/etc/passwd`），`cd` 通过系统调用动态更改。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-8.jpg]]（图 4.8 树形目录结构）

优点：分类灵活、层次清晰，不同性质的文件可分布在不同子树，并能对**各节点单独设置存取权限**，实现精细化控制。缺点：**查找一个文件要按路径名逐级访问中间目录节点，磁盘 I/O 次数增加**。现代 OS（UNIX、Linux、Windows）绝大多数都采用它。

**易错点**：当前目录的作用是**加快检索**，不是「节省内存」也不是「实现共享」。2010 年真题考的就是这一点。

**易错点**：树形目录**不便于文件共享**——一个文件在树里只有一条路径。共享要靠无环图（KP33）。

**易错点**：路径越深，打开文件时读目录的磁盘 I/O 越多（KP51）。这是树形目录唯一的实质代价。

## KP33 无环图目录结构与共享计数器

**核心结论**：在树形结构基础上引入**指向同一节点的有向边**，整个目录结构成为**有向无环图**，于是同一个文件或子目录可同时出现在两个或多个目录中，实现跨目录共享。

**删除操作的处理**（关键）：为每个共享节点维护一个**共享计数器**：

```
新增一条共享链   → 计数器 +1
收到删除请求     → 计数器 -1
计数器 = 0       → 才真正物理删除该节点
计数器 > 0       → 只断开请求用户的那条共享链，节点保留供他人继续使用
```

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-9.jpg]]（图 4.9 无环图目录结构）

代价：管理开销增加，需额外维护引用计数等共享状态。

**易错点**：为什么必须**无环**——有环会导致互相引用使计数永远不为 0，空间无法回收，遍历还可能死循环。

**易错点**：删除共享节点时**不是拒绝删除，而是只删自己的那条链**并把计数减 1。这与硬链接的处理逻辑完全一致（KP56）。

## KP34 四种目录结构总对比（收口必背）

| 结构 | 按名存取 | 允许重名 | 支持分类 | 支持共享 | 主要缺点 |
| --- | --- | --- | --- | --- | --- |
| 单级目录 | 支持 | **不允许** | 不支持 | 难 | 查找慢，只适用单用户 |
| 两级目录 | 支持 | 不同用户间允许 | **不支持** | 有限 | UFD 扁平，无法分类 |
| 树形目录 | 支持 | 允许 | 支持 | **不便** | 逐级查找，磁盘 I/O 多 |
| 无环图目录 | 支持 | 允许 | 支持 | **支持** | 需维护引用计数，管理复杂 |

演进主线——**每一级只解决前一级的一个痛点**：

```
单级（能按名存取，但重名、慢）
  → 两级（解决重名 + 命名空间隔离带来安全性）
  → 树形（解决分类与精细权限，成为现代主流）
  → 无环图（解决共享）
```

**易错点**：别把功劳跨级记错。「树形目录解决了文件共享」是错的，「两级目录支持文件分类」也是错的。

**易错点**：四种结构**都实现了按名存取**，这一列不构成区分点。

## KP35 目录的八种操作

**核心结论**：八个操作，注意区分作用对象是「文件」还是「目录」：

| 操作 | 关键点 |
| --- | --- |
| 搜索 | 可从根目录或**当前工作目录**出发，支持精确匹配或部分文件名检索 |
| 创建文件 | **先检查同目录内是否重名**，确认无重名才新增目录项并初始化属性 |
| 删除文件 | 移除该文件在所属目录中的目录项，并回收其数据块与元数据 |
| 创建目录 | 建立子目录（UFD），用于组织个人文件与嵌套子目录 |
| 删除目录 | 空目录可直接删；非空目录两种策略：① 要求用户先手动（递归）清空 ② 系统自动递归删除全部内容 |
| 移动目录 | 目录项转移到新父目录，**路径名随之自动更新，文件内容保持不变** |
| 显示目录 | 列出文件与子目录名称，通常附大小、最后修改时间等属性 |
| 改变目录 | 切换当前工作目录，可用绝对或相对路径；未指定时默认返回用户主目录 |

**易错点**：**移动文件或目录只改目录项，不搬数据块**。所以同一文件系统内移动一个超大文件几乎是瞬间完成的。

**易错点**：删除非空目录的两种策略**都是合法设计**，教材没规定唯一答案，别把某一种当标准。

## KP36 目录实现：线性列表 vs 哈希表

**核心结论**：目录实现的核心目标是**高效支持查找操作**，两种基本方法：

| 方法 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 线性列表 | 由文件名 + 数据块指针组成线性表，查找时逐项比较 | 实现简单 | **查找效率低**，目录规模越大扫描开销越高 |
| 哈希表 | 文件名算哈希值 → 索引到表中某元素 → 该元素存**指向目录项的指针** | 查找、插入、删除性能都很高 | 必须妥善处理**哈希冲突** |

线性列表中被删目录项的三种重用策略：标记为未使用、加入空闲链表、把末尾项移到空位并缩短目录长度。若以链表组织目录项，还可进一步降低删除的时间开销。

**目录缓存**：目录查询依赖磁盘 I/O，频繁访问开销大，所以系统把**当前活跃的目录缓存到内存**，后续访问直接在内存进行，大幅减少磁盘操作。

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP14（基于索引搜索的三种分配算法）——哈希算法同样是「关键字直接算出位置」；[[知识点/OS-03-内存管理.md]] KP33（局部性原理）——目录缓存能奏效，靠的正是目录访问的时间局部性。

**易错点**：线性列表若**文件名有序**则可用折半查找，但插入新文件要维护有序性，带来额外开销。这是小结思考题的标准答法，别漏掉后半句。

**易错点**：哈希表的表元素里存的是**指向目录项的指针**，不是目录项本身。

**易错点**：目录缓存属于**内存缓冲区管理**的一部分，归**基本文件系统层**（KP9、KP12），不归逻辑文件系统。

## KP37 文件物理结构的两个视角与三种分配方式（真题高频）

**真题**：2009、2011、2013、2020 考过不同物理结构的特点和比较。

**核心结论**：文件的物理结构关注**文件数据如何在磁盘上分布与组织**，可从两个互补视角理解：

| 视角 | 管什么 | 在哪讲 |
| --- | --- | --- |
| **文件分配方式** | 如何为文件分配磁盘块——**非空闲块**的管理 | 4.2.6（本节） |
| **文件存储空间管理** | 如何跟踪和分配空闲磁盘块——**空闲块**的管理 | 4.3 |

分配方式**直接决定文件的物理结构**，三种：**连续分配、链接分配、索引分配**。

理解逻辑/物理关系的标准类比：**线性表（逻辑结构）↔ 顺序表 / 链表（物理实现）**——逻辑结构描述「是什么」，物理结构说明「如何存」。

磁盘同样被划分为若干**磁盘块**，大小通常与内存页面一致；所有磁盘 I/O 均以**块**为单位在内存与磁盘间交换数据。

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP16（分页的基本概念与页内碎片）——磁盘块与内存页面大小一致，正是为了让页面调入调出时一块对一页；参见 [[知识点/OS-03-内存管理.md]] KP44（从何处调入页面：文件区与对换区）。

**易错点**：分配方式决定物理结构，**与逻辑结构无必然联系**（KP13）。顺序文件完全可以用链接分配离散存放。

**易错点**：4.2.6 管**已分配块**，4.3 管**空闲块**，两者是同一问题的两面。看到「位示图、成组链接法」就是 4.3 的内容，归文件组织模块（KP10）。

## KP38 连续分配（真题高频）

**真题**：2011、2012、2014 考过连续分配的应用和分析。

**核心结论**：每个文件在磁盘上占**一组连续的块**。目录项记录**起始块号 + 所占总块数**。若文件长 $n$ 块、从块 $b$ 开始，则占据 $b, b+1, b+2, \cdots, b+n-1$；要访问第 $i$ 块可直接算出 $b+i-1$。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-10.jpg]]（图 4.10 连续分配）

| 优点 | 缺点 |
| --- | --- |
| 支持顺序访问**和**直接访问 | 必须分配连续空间，易产生大量**外部碎片** |
| 顺序访问**效率最高**：块位于一条或少数几条相邻磁道，磁头移动距离最小、寻道时间最短 | 需**预先知道文件长度**，难以支持动态增长（强行扩展会覆盖相邻文件） |
| 无额外指针或索引开销 | 为维持逻辑顺序，删除或插入记录时要**物理移动**后续记录，开销大 |

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP11（动态分区分配的原理、外部碎片与紧凑）——磁盘连续分配的外部碎片问题与内存动态分区完全同构，解法也一样（紧凑 / 磁盘整理）。

**易错点**：连续分配是三种方式中**顺序访问和直接访问都最快**的一种，代价是空间不灵活。别记成「连续分配只支持顺序访问」——那是隐式链接。

**易错点**：访问第 $i$ 块的公式要**先看编号起点**。教材按第 $i$ 块（$i$ 从 1 起算）给出 $b+i-1$；若逻辑块号从 0 起算则是 $b+i$。

**易错点**：**「顺序文件」（逻辑结构）和「连续分配」（物理结构）毫无必然联系**（KP13）。这是本章最经典的偷换概念点，两处都会考。

## KP39 隐式链接（真题）

**真题**：2014 考过链接分配的应用和分析。

**核心结论**：链接分配以**离散**方式分配盘块，三条共同优点：① 消除**外部碎片**，显著提高磁盘利用率；② 支持动态分配，**无须事先知道文件大小**；③ 插入、删除、修改都很便捷。按指针存放位置分隐式和显式两种。

**隐式链接**：目录项存指向文件**第一块和最后一块**的指针；除最后一块外，每个盘块内都存有指向下一块的指针，这些**指针对用户完全透明**。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-11.jpg]]（图 4.11 隐式链接方式）

三个缺点：

| 缺点 | 说明 |
| --- | --- |
| **仅支持顺序访问** | 访问第 $i$ 块必须从首块开始依次跟随指针遍历，随机访问效率极低 |
| **可靠性差** | 链中任一指针损坏，整条链断开，后续数据全部无法访问 |
| 占用存储空间 | 每个盘块都要腾出空间存放下一块的指针 |

**易错点**：隐式链接目录项里存的是**首块和末块两个指针**，不只是首块。存末块是为了追加写时能直接找到尾部。

**易错点**：指针占掉盘块的一部分，所以**一个盘块实际能存的数据不足一整块**。做容量计算题时若题目给出指针占 $n$ B，要从块大小里扣掉。

**易错点**：三种物理结构中**只有隐式链接不支持直接访问**。这是选择题最高频的判据。

## KP40 簇：用内部碎片换指针开销（真题）

**真题**：2017、2018 考过文件空间分配与簇的关系。

**核心结论**：把若干**连续的盘块**组合成一个**簇**（cluster）作为基本分配单位，文件的分配与链接均以簇为单位进行。

| 收益 | 代价 |
| --- | --- |
| 指针数量大幅减少 → 存储开销降低 | 产生**内部碎片**：文件大小不是簇大小的整数倍时，最后一个簇的剩余空间无法被其他文件利用 |
| 链式查找时间显著缩短 → 整体 I/O 性能提升 |  |

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP17（页面大小的权衡）——簇大小的取舍与页面大小完全同构：分配单位越大则管理表项越少，但内部碎片越大。

**易错点**：链接分配本身**没有内部碎片**（以块为单位分配），内部碎片是**引入簇之后**才出现的。这是高频陷阱。

**易错点**：簇是**连续盘块的组合**——簇内连续、簇间可离散，它不改变链接分配的离散本质，也不会带回外部碎片。

## KP41 显式链接与文件分配表 FAT（真题）

**真题**：2019、2025 考过 FAT 表的作用。

**核心结论**：显式链接把链接指针从盘块里抽出来，**集中存放在内存中的一张全局表**——**文件分配表 FAT**（File Allocation Table）。整个文件系统**仅设一张** FAT，**每个表项对应一个磁盘块**、存放指向下一盘块的指针。因此**目录项只需记录起始块号**，后续块号依次查 FAT 即可获得。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-12.jpg]]（图 4.12 磁盘的文件分配表）

FAT 的表项约定：

| 表项值 | 含义 |
| --- | --- |
| 下一块的块号 | 链上的后继 |
| **-1** | 该块是文件的**最后一块** |
| **-2** | 该盘块**空闲**（也可指定为 -3、-4 等） |

所以 FAT **一表两用**：既记录文件的链式结构，又标识空闲盘块。进程请求分配盘块时，系统只需在 FAT 中找一个值为 -2 的表项。

| 优点 | 缺点 |
| --- | --- |
| 支持顺序访问，**也支持直接访问**（访问第 $i$ 块无须依次读前 $i-1$ 个**盘块**） | FAT 需**常驻内存**，磁盘容量越大内存开销越显著 |
| FAT 在系统启动时即载入内存，检索全在内存完成，**大幅减少磁盘 I/O** |  |

**易错点**：显式链接「支持直接访问」的含义是**不必读盘遍历**，但在内存的 FAT 里仍要顺着表项走 $i$ 次。它省的是磁盘 I/O，不是省查找步数。

**易错点**：FAT 的**表项数 = 磁盘总块数**，与文件个数无关。这是 FAT 内存开销随磁盘容量线性增长的原因。

**易错点**：显式链接的**目录项只存起始块号**，不像隐式链接还要存末块号——因为末块可由 FAT 中的 -1 找到。

## KP42 单级索引分配（真题，必会算）

**真题**：2012 考过索引分配的应用和分析。

**核心结论**：打开文件时其实只需要把**该文件**占用的盘块号调入内存，没必要加载整张 FAT。于是给**每个文件**配一个专用的**索引块**（索引表），把分配给它的所有盘块号集中记在其中；访问该文件时一次性把这些盘块号载入内存。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-13.jpg]]（图 4.13 索引分配）

**容量算例**：盘块 4KB、每个盘块号占 4B → 一个索引块容纳 $4\text{KB}/4\text{B} = 1024$ 个盘块号 → 单级索引支持的最大文件为 $1024 \times 4\text{KB} = 4\text{MB}$。

| 优点 | 缺点 |
| --- | --- |
| 支持高效**直接访问**：访问第 $i$ 块只需读索引块第 $i$ 项即得盘块号 | 每个文件都要配一个完整索引块，**小文件的索引块利用率极低** |
| 盘块可离散分配，**无外部碎片** | 文件很大时盘块号超出单个索引块容量，靠链式指针串联多个索引块**效率低下** |

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP19（页表与页表项）——索引表就是文件的「页表」：按逻辑块号顺序排列，表项只存物理块号，**逻辑块号是隐含索引、不必存**。区别是页表在内存、索引块在磁盘上。

**易错点**：索引块里**只存盘块号，不存逻辑块号**。逻辑块号 $i$ 靠「第 $i$ 个表项」隐含表达，和页表项一模一样（OS-03 KP19）。

**易错点**：单级索引的最大文件 = **一个索引块能装的盘块号个数 × 盘块大小**。两处都要用到盘块大小（一次算容纳个数、一次算总容量），别只乘一次。

**易错点**：索引分配**不产生外部碎片，也不产生内部碎片**，代价是索引块的空间开销。

## KP43 多级索引分配（必会算）

**核心结论**：文件过大、索引块不止一个时，为这些索引块**再建一级索引**，称**主索引**。主索引表中依次存放各二级索引块的盘块号，即二级索引分配。其设计思想与内存管理的**多级页表高度相似**。访问数据时先通过主索引定位二级索引块，再通过它找到目标数据块。文件极大时可继续扩展为三级、四级。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-14.jpg]]（图 4.14 二级索引分配）

**容量算例**（盘块 4KB、盘块号 4B，每索引块 1024 项）：

| 级数 | 最大文件 |
| --- | --- |
| 一级 | $1024 \times 4\text{KB} = 4\text{MB}$ |
| 二级 | $1024 \times 1024 \times 4\text{KB} = 4\text{GB}$ |
| 三级 | $1024^3 \times 4\text{KB} = 4\text{TB}$ |

规律：**每加一级，容量乘 1024**。

| 优点 | 缺点 |
| --- | --- |
| 显著提升大型文件的可扩展性与查找效率 | 访问一个盘块所需的**磁盘 I/O 次数随索引级数增加**（$k$ 级索引要 $k+1$ 次） |
|  | 若只用多级索引，**大量小文件访问单个盘块也要多次 I/O**，整体性能难以理想 |

**跨科关联**：[[知识点/OS-03-内存管理.md]] KP23（两级页表：为什么要分级）、[[知识点/OS-03-内存管理.md]] KP24（多级页表的地址变换与访存次数）——「加一级换容量、代价是多一次访问」这条权衡两处完全一致；区别是页表靠 TLB 抵消开销，文件靠混合索引（KP44）抵消。

**易错点**：$k$ 级索引访问一个数据块需要 **$k+1$ 次磁盘 I/O**（读 $k$ 层索引块 + 读 1 次数据块），别只数索引层数。

**易错点**：多级索引的致命缺点是**连小文件一起拖慢**，这正是必须引入混合索引的动机，而不是「容量不够」。

## KP44 混合索引分配的原理（真题）

**真题**：2013 考过混合索引分配的原理。

**核心结论**：按文件大小**动态选用**最合适的分配策略，在空间开销与访问性能之间取平衡：

| 文件规模 | 策略 | 访问方式 |
| --- | --- | --- |
| 小文件 | 全部盘块地址**直接存在 inode / FCB 里** | **直接寻址**，无须读任何索引块 |
| 中型文件 | 单级索引（inode 存一个索引块地址） | **一次间址** |
| 大型文件 | 两级索引 | 二次间址 |
| 特大型文件 | 三级索引 | 三次间址 |

UNIX 正是采用这种混合策略，其索引节点中共设 **13 个地址项** i.addr(0)～i.addr(12)。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-15.jpg]]（图 4.15 UNIX 系统的 inode 结构示意图）

**易错点**：混合索引的全部价值来自**小文件零索引块开销**那几个直接地址项。它相对纯多级索引的优势只在这里，容量上限并没有变大。

**易错点**：「混合」指的是**同一个 inode 内同时使用多种寻址方式**，不是不同文件用不同方式。一个大文件会同时用到直接地址和各级间址。

## KP45 UNIX inode 的 13 个地址项与最大文件长度（真题超高频，必会算）

**真题**：2010、2015、2018、2022 考过混合索引分配的相关计算；2018、2022 考过多级索引块的访问效率分析。

**核心结论**：13 个地址项的分工（**必背**）：

| 地址项 | 数量 | 作用 |
| --- | --- | --- |
| i.addr(0)～i.addr(9) | **10 个** | 直接地址，每项直接存一个数据块的盘块号 |
| i.addr(10) | 1 个 | **一次**间接地址（一级索引） |
| i.addr(11) | 1 个 | **二次**间接地址（两级索引） |
| i.addr(12) | 1 个 | **三次**间接地址（三级索引） |

**容量累加**（盘块 4KB，索引块容纳 1K = 1024 个盘块号）：

| 使用范围 | 本级新增容量 | 累计最大文件长度 |
| --- | --- | --- |
| 仅直接地址 | $10 \times 4\text{KB} = 40\text{KB}$ | **40KB** |
| + 一次间址 | $1\text{K} \times 4\text{KB} = 4\text{MB}$ | **4MB + 40KB** |
| + 二次间址 | $1\text{K} \times 1\text{K} \times 4\text{KB} = 4\text{GB}$ | **4GB + 4MB + 40KB** |
| + 三次间址 | $1\text{K}^3 \times 4\text{KB} = 4\text{TB}$ | **4TB + 4GB + 4MB + 40KB** |

**访问某逻辑块要几次磁盘 I/O**（inode 已在内存的前提下）：

```
落在直接地址区（前 10 块）  → 1 次（直接读数据块）
落在一次间址区             → 2 次（读索引块 + 读数据块）
落在二次间址区             → 3 次
落在三次间址区             → 4 次
```

**易错点**：最大文件长度是**四段相加**，不是只取最大那一段。要写全 $4\text{TB}+4\text{GB}+4\text{MB}+40\text{KB}$。

**易错点**：**直接地址是 10 个**（addr(0)～addr(9)），不是 13 个也不是 12 个。13 = 10 + 3 级间址。

**易错点**：判断某逻辑块号落在哪一区要**逐段累减**：先减 10，再减 $1\text{K}$，再减 $1\text{K}^2$。别直接除。

**易错点**：题目若说明「inode 已读入内存」，则不计读 inode 那次 I/O；若没说明，通常还要**再加 1 次**。先看题目前提再数次数。

## KP46 三种物理结构总对比（收口必背）

| 项 | 连续分配 | 隐式链接 | 显式链接（FAT） | 索引分配 |
| --- | --- | --- | --- | --- |
| 目录项内容 | 起始块号 + 总块数 | 首块号 + 末块号 | **起始块号** | **索引块号** |
| 顺序访问 | **最快** | 慢 | 较快 | 快 |
| 直接（随机）访问 | **支持，最快** | **不支持** | 支持 | **支持** |
| 外部碎片 | **有** | 无 | 无 | 无 |
| 内部碎片 | 无 | 无（引入簇则有） | 无（引入簇则有） | 无 |
| 支持动态增长 | **难**，须预知长度 | 易 | 易 | 易 |
| 额外空间开销 | 无 | 每块一个指针 | **FAT 常驻内存**，随磁盘容量增长 | 每文件一个索引块 |
| 可靠性 | 高 | **差**（断链即丢后续数据） | 较高 | 高 |

判定口诀：

```
"随机访问快 + 空间灵活"     → 索引分配（现代主流）
"顺序访问极快"、长度已知     → 连续分配
"只能顺序访问"              → 隐式链接
"一张全局表、常驻内存"       → 显式链接 FAT
"每个文件一张表"            → 索引分配
```

**易错点**：**只有隐式链接不支持直接访问**，连续、显式链接、索引三种都支持。

**易错点**：**只有连续分配有外部碎片**，其余三种都没有；内部碎片只在**引入簇**后才出现。

**易错点**：FAT 是**全系统一张表**，索引块是**每个文件一个**。这一条区分显式链接和索引分配，别混。

## KP47 创建文件的六步（真题）

**真题**：2025 考过文件创建的过程。

**核心结论**：六步，顺序不能乱：

| 步 | 内容 |
| --- | --- |
| ① 合法性与权限校验 | 文件名是否合法、**同目录下是否重名**、用户对**目标目录**是否有写权限；任一不满足立即终止 |
| ② 分配索引节点 | 从空闲 inode / FCB 池取一项，初始化文件类型、初始大小、访问权限、时间戳、物理块指针，并标记为已占用 |
| ③ 分配磁盘块 | 按预估大小从空闲块管理结构中分配物理块，块地址记入 inode |
| ④ 在目录中新建目录项 | 格式为〈文件名，索引节点号〉，文件从此可被检索 |
| ⑤ 更新文件系统元数据 | 空闲 inode 表、空闲磁盘块结构、目录大小、修改时间 |
| ⑥ 打开并返回文件描述符（可选） | 在进程打开文件表中建表项、分配 fd、初始化读/写指针 |

**易错点**：权限校验查的是**目标目录的写权限**，不是文件本身的权限——此刻文件还不存在。

**易错点**：④ 建目录项要用到 ② 分配的 inode 号，所以**分配 inode 必须在建目录项之前**。顺序题按这个判。

**易错点**：第 ⑥ 步是**可选**的。创建 ≠ 打开，只有需要立即使用时才打开。

## KP48 删除文件的七步（真题）

**真题**：2013、2021 考过文件删除的过程。

**核心结论**：七步，核心判断在第 ② 步的**硬链接计数**：

| 步 | 内容 |
| --- | --- |
| ① 路径解析与定位 | 逐级查目录找到目录项，取得 inode / FCB，校验用户对**文件所在目录**的写权限 |
| ② 检查使用状态与硬链接计数 | 文件正被打开 → 部分系统**延迟物理删除**，待所有引用关闭后再回收；**链接计数 > 1 → 只删当前目录项并把计数减 1，不回收 inode 与磁盘块**；计数 = 1 才走完整删除 |
| ③ 移除目录项 | 文件在用户视角下「消失」，完成**逻辑删除** |
| ④ 释放索引节点 | 链接计数降至 0 时把 inode 标记空闲、归还空闲管理结构 |
| ⑤ 释放磁盘块 | 按 inode 中的块指针，把所有**数据块和索引块**归还空闲块管理结构 |
| ⑥ 释放内存临时资源（可选） | 缓冲区、打开文件表项、内核文件对象 |
| ⑦ 更新文件系统元数据 | 目录大小、空闲 inode 表、空闲块结构，确保一致性 |

**易错点**：**逻辑删除（移除目录项）和物理回收（释放 inode 与磁盘块）是两件事**。硬链接计数 > 1 时只做前者，这是硬链接的核心行为（KP56）。

**易错点**：删除文件**不擦除数据块内容**，只把块标记为空闲。这是数据恢复软件能工作的原因，也是安全删除需要额外覆写的原因。

**易错点**：权限校验查的仍是**目录的写权限**，因为要动的是目录里的目录项，不是文件内容。

**易错点**：⑤ 要连**索引块**一起回收，不只是数据块。索引块也是占盘的。

## KP49 读文件与写文件

**核心结论**：两者流程对称，都先经目录定位再靠指针读写：

| 操作 | 流程 |
| --- | --- |
| 读文件 | 按文件名查目录项 → 取得索引节点号 → 定位外存数据块 → 按**读指针**位置读数据 → **更新读指针** |
| 写文件 | 按文件名查目录项 → 取得索引节点号 → 定位外存数据块 → 按**写指针**位置写数据 → **更新写指针** |

写的额外情形：若写入**超出当前已分配空间**，系统动态分配新磁盘块，并**更新 inode / FCB 中的块指针**。

**易错点**：读写都靠**指针**定位，而指针是**进程私有**的（KP50、KP54），不是文件的持久属性。

**易错点**：只有写操作会触发**动态分配磁盘块并修改 inode 的块指针**；读操作不改块指针（但会更新访问时间）。

**易错点**：这里描述的是**基本操作的完整语义**（含查目录）。实际使用中 `open` 之后的 `read`/`write` 不再查目录，直接用 fd（KP53）。

## KP50 为什么要打开文件：两级打开文件表

**核心结论**：对一个文件多次读写时，若每次都从检索目录开始，性能开销显著。所以大多数 OS 规定首次访问必须先用系统调用 `open` 打开：系统按路径定位到目录项后，把**关键信息载入内存**，在**打开文件表**中建一个表目，并把该表目的索引号（**文件描述符**）返回给用户。此后只凭描述符操作，直接从内存取信息。

**两级结构**（必背分工）：

| 表 | 归属 | 存什么 |
| --- | --- | --- |
| **系统打开文件表** | 全局共享，**唯一一张** | 与**进程无关**的文件属性：磁盘位置、文件大小、访问时间；每项含**打开计数器 Open Count**，记录有多少进程打开了该文件 |
| **进程打开文件表** | **每个进程独有** | 进程私有的访问状态：**当前读/写指针**、访问权限、文件打开模式；每项**指向系统表的对应项** |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-16.jpg]]（图 4.16 内存中文件的系统结构）

多个进程打开同一文件时：各自在自己的进程表里加一项，**都指向同一个系统表项**，无须重复加载文件元数据——既保证了各进程访问上下文的隔离，又实现了底层资源的高效共享。

**跨科关联**：[[知识点/OS-02-进程与线程.md]] KP3（PCB：内容与组织方式）——PCB 里的「文件描述符列表」就是进程打开文件表，属于进程的私有资源，随进程创建/撤销而建立/回收。

**易错点**：**读/写指针在进程打开文件表里，不在系统表里**。两个进程各有自己的指针、互不干扰——这正是设计成两级的根本原因。

**易错点**：**打开计数器在系统打开文件表里**，因为它统计的是全局有多少进程打开了该文件。

**易错点**：`open` 载入内存的是**元数据**（目录项、inode），**不是文件数据**。

## KP51 文件打开的完整过程（真题高频）

**真题**：2014、2017、2020 考过文件打开的过程与分析。

**核心结论**：五步：

```
① 按用户给的路径逐级遍历目录，把需要的目录文件从磁盘调入内存，定位目标文件的目录项
② 从该目录项中提取出索引节点编号
③ 以 inode 号为关键字查系统打开文件表：
     未找到 → 从磁盘读该 inode 到内核缓冲区，在系统表中创建新项，打开计数初始化为 1
     已存在 → 仅把该项的打开计数 +1
④ 在发起请求的进程的打开文件表中分配一个新表项，记录其指向系统表项的索引
⑤ 把该表项的索引号作为文件描述符返回给用户进程
```

**易错点**：查系统打开文件表用的关键字是**索引节点号**，不是文件名。文件名在第 ① 步用完就丢弃了。

**易错点**：`open` **要访问磁盘**（读目录文件，可能还要读 inode），不是纯内存操作。**路径越深，磁盘 I/O 越多**——这也是设置当前工作目录的意义（KP32）。

**易错点**：已被其他进程打开时**只加计数、不重复读 inode**，这是两级表设计带来的直接收益。

**易错点**：`open` 不把**文件数据**读入内存，只读元数据。

## KP52 文件关闭的过程（真题）

**真题**：2023 考过文件关闭的过程。

**核心结论**：三步：

```
① 从该进程的打开文件表中删除对应项
② 系统打开文件表中相应项的打开计数器 -1
③ 计数器减至 0 → 表明再无进程引用 → 删除系统表项、释放所占相关资源
```

**易错点**：`close` **只减计数，不一定删系统表项**。只有计数归零才删——和硬链接的 count 逻辑是同一个套路。

**易错点**：`close`（关闭）和「删除文件」是两件完全不同的事。关闭只撤销本次访问，文件仍完好地在磁盘上。

**易错点**：关闭要做**两张表**的事：删进程表项 + 减系统表计数。只答一张表不完整。

## KP53 文件名不在打开文件表里：文件描述符（真题高频）

**真题**：2012、2017、2024 考过文件名和文件描述符的应用场景。

**核心结论（易错重点）**：**文件名并非打开文件表的组成部分**。一旦系统通过文件名完成对磁盘上 FCB / inode 的定位，后续操作便不再需要文件名。用于访问打开文件表的索引号称为**文件描述符**（Linux）或**文件句柄**（Windows）。

**这是文件管理的核心考点**：`open()` 成功之后，**所有**文件操作 [`read()`、`write()`、`lseek()`、`close()`] 均通过文件描述符进行，**不再使用文件名**。

```
open(文件名)                      → 返回 fd    ← 唯一用到文件名的环节
read / write / lseek / close(fd)              ← 全部只认 fd
```

**易错点**：看到「用文件名执行 read / write / lseek」直接判错。只有 `open`（以及作用于目录项的 `create`、`unlink` 之类）才用文件名。

**易错点**：**fd 是进程打开文件表的索引，进程私有**。同一文件在不同进程里的 fd 可以不同；同一个 fd 号在不同进程里指向的文件也可以不同。

**易错点**：文件名不进打开文件表的**原因是「不再需要」**，不是「太长存不下」。答题要答定位已完成这一点。

## KP54 打开文件关联的四项关键信息

**核心结论**：每个被打开的文件关联四项信息，考点在**它们分别存在哪张表里**：

| 信息 | 存放位置 | 说明 |
| --- | --- | --- |
| **文件指针** | 进程打开文件表 | 当前读/写位置，**每个进程独立维护**，必须与磁盘上的共享属性分离 |
| **文件打开计数** | 系统打开文件表 | 当前打开该文件的进程数；只有最后一个进程 `close()` 后才真正释放系统表项 |
| **文件磁盘位置** | 系统打开文件表 | 缓存在内存，避免每次操作都重新解析路径、读元数据 |
| **访问权限** | 进程打开文件表 | 打开时指定的模式（只读、读/写、追加、创建），OS 据此判断后续 I/O 是否允许 |

记忆判据：**跟「这个进程怎么用它」有关的进程表，跟「这个文件是什么」有关的系统表**。

**易错点**：**访问权限（打开模式）在进程表**，因为同一文件可被进程 A 以只读、进程 B 以读/写方式打开。别和 inode 里持久化的**文件权限**（rwx）混——后者是磁盘上的属性，属于文件保护（KP60）。

**易错点**：**文件大小、磁盘位置在系统表**（与进程无关），**指针、权限在进程表**（与进程有关）。四项二二分开，这是本节最常考的填表题。

## KP55 文件共享的意义与朴素做法的缺陷

**核心结论**：文件共享允许多个用户访问同一文件，系统中**只需保留一个物理副本**。若无共享机制，每个用户都得持有独立副本，既浪费存储空间，又**易导致数据不一致**。

**无环图目录（KP33）的朴素做法为什么不够**：建立链接时把被共享文件的**盘块号复制**到各自目录项里。此后若某用户向文件追加数据、分配了新盘块，这些**新增盘块只出现在他操作的那个目录项中，对其他用户不可见**——所以这不是真正的共享。

```
朴素复制盘块号 → 追加写后各目录项的块表不一致 → 假共享
        ↓ 两条正解
把物理地址集中到 inode，目录项只留指针   → 硬链接（KP56）
目录项只留目标文件的路径名               → 软链接（KP57）
```

**易错点**：共享的本质是**全系统只有一份物理地址信息**。凡是「各自存一份盘块号」的方案，都会因为文件动态增长而失效。

**易错点**：共享要解决的不只是省空间，还有**一致性**——多份副本必然不一致。

## KP56 硬链接：基于索引节点的共享（真题）

**真题**：2009、2017 考过硬链接的原理与相关分析。

**核心结论**：文件的**物理地址和属性信息全部集中存在 inode 里**，目录项只包含**文件名 + 指向该 inode 的指针**。inode 中设**链接计数 count**（引用计数），记录当前指向它的**目录项数量**。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-17.jpg]]（图 4.17 基于索引节点的共享方式）、[[王道教材/27 王道操作系统/pictures/fig-4-18.jpg]]（图 4.18 文件共享中的链接计数）

生命周期（教材主线，必背）：

| 事件 | count | 拥有者 |
| --- | --- | --- |
| A 创建新文件，成为拥有者 | 置 **1** | A |
| B 共享（B 目录里新增目录项 + 指针） | 增至 **2** | **仍是 A** |
| A 不再需要该文件 | **只删自己的目录项**，count 减 1 → 1 | 文件与 inode 保留，B 继续用 |
| count 减到 **0** | 系统才真正释放该文件及其 inode | —— |

A 为什么不能直接删：若连 inode 一起删，**B 的指针悬空**，而 B 可能正在对该文件执行写操作，操作会中断失败。

**易错点**：**共享后拥有者不变**，仍是创建者 A；B 只是多了一个目录项。

**易错点**：count 数的是**目录项（硬链接）数量**，不是打开该文件的进程数——后者是内存 inode 的**访问计数**（KP29）。这一对反复被考。

**易错点**：A 删除后 count = 1，此时**文件的拥有者仍记录为 A**，尽管 A 自己的目录里已经没有它了。这是硬链接最反直觉的一点。

## KP57 软链接：基于符号链的共享（真题）

**真题**：2009、2021 考过软链接的原理与相关分析。

**核心结论**：系统创建一个 **LINK 类型的新文件 L** 写入 B 的目录，**L 的内容仅是被链接文件 F 的路径名**，功能类似 Windows 的快捷方式。B 访问 L 时，OS 识别出它是 LINK 类型 → 按其中记录的路径名逐级查找 → 定位到 F → 对 F 执行读/写。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-4-19.jpg]]（图 4.19 利用符号链的共享方式）

**关键性质**：只有**文件拥有者**持有指向 inode 的指针，其他共享用户仅保存**路径名**。因此：

| 情形 | 结果 |
| --- | --- |
| 拥有者删除了共享文件 F | 其他用户的指针**不会悬空**（他们本来就没有指针） |
| 其他用户再通过 L 访问 | 系统返回**访问失败**，此时可安全地删除该符号链，不引发任何问题 |

两项代价：① 每次访问都要**按路径名逐级遍历目录**，可能涉及多次磁盘读取，开销大；② **符号链本身是一个独立文件，其 inode 同样占磁盘空间**。

**网络共享**：用符号链实现跨机器的文件共享时，只需记录**文件所在机器的网络地址 + 文件路径名**。

**易错点**：软链接**必然比硬链接慢**，因为每次访问都要重新解析路径；硬链接是直接拿指针访问。教材明确给出这个结论。

**易错点**：软链接文件本身**占一个 inode**；硬链接**不占新 inode**，只多一个目录项。

**易错点**：软链接失效后**指针没有悬空**，只是查找失败。「悬空指针」是硬链接方案下若允许直接删 inode 才会出现的问题。

## KP58 软硬链接对比（收口必背）

**核心结论**：一句话——**「文件共享，软硬兼施」**。硬链接是多个目录项指向同一个索引节点，只要至少还有一个指针存在，该 inode 就不会被删除；软链接是把到达共享文件的路径保存下来，访问时依据路径查找。

| 项 | 硬链接 | 软链接（符号链） |
| --- | --- | --- |
| 实现方式 | 多个目录项指向**同一个 inode** | 新建 LINK 文件，内容是**目标路径名** |
| 是否占新 inode | **不占**（只多一个目录项） | **占**（本身是独立文件） |
| 计数机制 | inode 中的**链接计数 count** | 无计数 |
| 访问速度 | **快**（直接通过指针访问） | **慢**（每次逐级解析路径） |
| 拥有者删除原文件后 | 文件**仍存在**（count 减 1，其他人照常用） | 原文件真被删，**软链接失效**，访问返回失败 |
| 能否跨文件系统 / 跨网络 | **不能**（inode 号只在本文件系统内有效） | **能**（记网络地址 + 路径名） |
| 悬空风险 | 靠 count 机制避免 | 不会悬空，只会失效 |

**易错点**：**硬链接的查找速度优于软链接**，这是教材明确的结论，也是最常考的一句。

**易错点**：硬链接的 count **只统计本文件系统内的目录项**（KP28），这正是硬链接不能跨文件系统的根本原因。

**易错点**：两者的删除语义相反——**硬链接删不掉文件（只减计数），软链接删得掉文件（链接反而失效）**。

## KP59 文件保护的三种手段与六种访问类型

**核心结论**：文件保护要控制「哪些用户能对文件做什么」，三种常见实现方式：

| 手段 | 防的是什么 | 能否区分具体操作类型 |
| --- | --- | --- |
| 口令保护 | 防他人非法获取文件 | **不能** |
| 加密保护 | 防文件内容被窃取 | **不能** |
| **访问控制** | 精细管理用户对文件的具体访问权限 | **能** |

受控的六种**访问类型**：

| 类型 | 内容 |
| --- | --- |
| 读 | 从文件中读取数据 |
| 写 | 向文件中写入或修改数据 |
| 执行 | 将文件装入内存并运行 |
| 添加 | 在**文件末尾追加**新数据，**不覆盖**原有内容 |
| 删除 | 移除文件并释放其所占存储空间 |
| 列表清单 | 列出目录中文件的名称及其属性 |

**核心结论（易错重点）**：重命名、复制、编辑等**高层操作由应用程序调用系统调用实现**，真正的保护机制只在底层提供。所以**复制本质上是一串「读」操作——用户只要拥有读权限，就隐含具备了复制和打印的能力**。

**易错点**：**「添加」和「写」是两种不同的访问类型**。只有添加权限的用户不能修改已有内容（日志文件的典型需求）。

**易错点**：**不能靠禁止「复制」来防泄露**，因为复制不是底层受控操作。这是保护机制的固有边界，也是常考的辨析点。

**易错点**：「列表清单」控制的是**目录**的可见性，不是文件内容。目录保护和文件保护是两套需求。

## KP60 访问控制列表 ACL 与精简 ACL（真题）

**真题**：2017 考过文件访问控制表的结构。

**核心结论**：实现访问控制最常用的方法是基于**用户身份**管理权限——为每个文件和目录附加一个**访问控制列表 ACL**（Access-Control List），明确指定各用户名及其被允许的访问类型。

| 优点 | 缺点 |
| --- | --- |
| 支持灵活而复杂的访问策略 | **列表长度不可预知**，带来复杂的空间管理开销 |

**精简 ACL**：把用户压缩成三类：

| 类别 | 含义 |
| --- | --- |
| 拥有者 | 创建文件的用户 |
| 组 | 一组需要共享该文件且访问需求相似的用户 |
| 其他 | 系统中除拥有者和同组用户外的所有用户 |

每种访问类型用**一个二进制位**表示，于是只需一个 **$3 \times 4$ 位的矩阵**就能完整描述三类用户对四种操作（读取、写入、删除、执行）的权限。创建文件时，系统把文件拥有者的用户名及其所属组名记录在该文件的 **FCB** 中。

**匹配顺序（有优先级）**：

```
是拥有者？   → 授予拥有者权限
否则 同组？  → 授予组权限
否则        → 只授予其他用户的权限
```

**易错点**：三类身份是**按优先级依次匹配、只命中一类**，不是权限累加。拥有者不会因为组权限更宽而额外获得权限。

**易错点**：精简 ACL 的规模是 **3 × 访问类型数** 位（教材例子 $3\times4$）。它的核心价值是把「长度不可预知」变成**固定大小**。

**易错点**：拥有者和所属组记在 **FCB** 里，不是记在 ACL 之外的某处。这与 KP4 的「所有者」属性是同一件事。

## KP61 口令与加密的定位

**核心结论**：两者是访问控制的**补充手段**，不能替代它：

| 手段 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 口令 | 创建文件时设口令，系统**存入 FCB**，告知授权共享的用户，访问时须提供正确口令 | 时间和空间开销都小 | 口令以明文或弱保护形式存于系统内部，**安全性较低** |
| 密码（加密） | 对**文件内容**加密，访问时用密钥解密 | 保密性强，**不额外占用元数据空间** | 加解密过程引入**计算开销** |

**核心结论（易错重点）**：口令与加密只用于防止文件被**非法获取或窃取**，**并不区分具体的访问操作类型**（读/写、执行），因此无法替代基于权限的访问控制机制。

对多级目录结构而言，保护需求不仅限于单个文件，还需涵盖**子目录及其全部内容**；由于目录操作与文件操作差异较大，系统必须提供**专门的目录保护机制**。

**易错点**：**口令存在 FCB 里（占元数据空间），加密不占元数据空间**（密钥在用户手上）。这一对差异常被拿来出选择题。

**易错点**：口令的开销小但安全性低，加密的安全性高但有计算开销——两者的优缺点正好互补，别记串。

## KP62 本节小结：4.2 的三个思考题

**思考题 1：目录管理的基本要求是什么？**

① 实现**按名存取**——目录管理最基本的功能；② 提高目录检索速度，从而加快文件的存取效率；③ 提供**访问控制信息**，管理不同用户对文件的使用权限，以支持安全共享；④ 支持**重名**，允许不同用户为各自的文件使用相同名称。

**思考题 2：在目录中查找某个文件可采用哪些方法？**

**线性列表法**：把文件名组织成一个线性表，查找时依次与各表项比较；若文件名有序则可采用**折半查找**，但插入新文件需维护有序性，带来额外开销。**哈希表法**：通过哈希函数把文件名映射为指向目录项的指针，查找迅速，但需妥善处理**哈希冲突**。

**思考题 3：单个文件的逻辑结构与物理结构之间是否存在制约关系？**

**二者无直接制约关系**，但若物理结构选择不当，逻辑结构的特点就难以体现。教材例子：一个逻辑上为**顺序结构**的文件，若采用**隐式链接**的物理结构，即使理论上能算出某条记录的位置，实际仍需在磁盘上逐块查找。

**核心结论**：现代 OS 的设计处处可见面向对象的影子。**文件本质上是一种抽象数据类型**，所以研究文件就是研究三件事：**逻辑结构、物理结构、支持的操作**——与数据结构的研究套路完全一致。

**4.2 全节骨架**：

```
4.2.1 目录管理四要求        → 按名存取、检索快、支持共享、允许重名
4.2.2 FCB → inode           → 目录项瘦身（16B/项），磁盘 inode 七项 + 内存 inode 五项
4.2.3 目录结构              → 单级 → 两级 → 树形 → 无环图（每级解决一个痛点）
4.2.4/4.2.5 目录操作与实现  → 八种操作；线性列表 / 哈希表 + 目录缓存
4.2.6 物理结构（本章重点）   → 连续 / 链接（隐式、簇、FAT）/ 索引（单级、多级、混合 13 项）
4.2.7 文件操作              → 创建六步、删除七步；open/close 与两级打开文件表、fd
4.2.8 文件共享              → 硬链接（inode + count）/ 软链接（路径名）
4.2.9 文件保护              → 六种访问类型、ACL 与精简 ACL、口令与加密
```

**下一步（4.3）要解决的问题**：文件系统在磁盘上如何布局（引导块、超级块、inode 区），以及**空闲盘块怎么管理**（空闲表法、空闲链表法、位示图、成组链接法）——4.2 管的是已分配块，4.3 管的是空闲块，两者合起来才是完整的磁盘空间管理。
