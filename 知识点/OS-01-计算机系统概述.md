## KP1 操作系统的定义与系统层次

**核心结论**：OS 是控制和管理计算机软/硬件资源、合理调度任务与分配资源、并为用户及其他软件提供统一接口与运行环境的**最基本的系统软件**。

使用层次自下而上四层：**硬件 → 操作系统 → 应用程序 → 用户**。

**易错点**：这个四层划分是人机交互视角，和计组里的结构分层不是一回事，别混着答。

## KP2 OS 的三大角色

| 角色       | 含义                  |
| -------- | ------------------- |
| 资源管理者    | 管处理机、存储器、文件、设备四大资源  |
| 用户与硬件的接口 | 用户接口 + 程序接口         |

|          |                     |

**记忆锚**：雇主（用户）、工人（OS）、机器（硬件）。工人协调机器＝资源管理；工人听命令＝接口；工人让机器发挥超出本身的能力＝扩充。

**易错点**：裸机指未装任何软件的机器，是==物质基础==；用户实际面对的是被 OS 抽象扩展后的**扩充机器**。

## KP3 四大管理功能

| 管理    | 主要任务                      |
| ----- | ------------------------- |
| 处理机管理 | 进程控制、进程同步、进程通信、死锁处理、处理机调度 |
| 存储器管理 | 内存分配与回收、地址映射、内存保护与共享、内存扩充 |

## KP4 用户接口的三种形式

| 接口             | 面向    | 机制                         |
| -------------- | ----- | -------------------------- |
| 联机用户接口（命令行）    | 交互式用户 | 键盘命令 + 命令解释程序，==输一条执行一条==  |
| 脱机用户接口（作业控制语言） | 批处理系统 | 命令写进作业说明书，随作业一起提交，调度到了自动执行 |

## KP5 程序接口＝系统调用（真题高频）

**真题**：2010 考过「操作系统为应用程序提供的接口」。

**核心结论**：系统调用是应用程序请求 OS 服务、访问系统资源的==**唯一合法途径**==。每个系统调用对应内核中实现某特定功能的子程序。

**易错点（这是考点核心）**：库函数**不是** OS 提供的接口，它只是对系统调用的封装。

| 库函数 | 是否触发系统调用 |
| --- | --- |
| `printf()` | 是，底层走 `write` |
| `malloc()` | 需要更多内存时走 `brk` / `mmap` |
| `strlen()`、`sqrt()` | 否，纯计算，全程在用户空间 |

所以「OS 给应用程序的接口是什么」答**系统调用**，不是库函数。

> [!note] 我的笔记
> 系统调用是唯一的途径，用别的方式没有办法，而库函数可能会触发系统调用

## KP6 并发 vs 并行（真题高频）

**真题**：2009 考过并行性的定义及分析。

|     | 定义                     | 单处理机能否实现 |
| --- | ---------------------- | -------- |
| 并发  | 两个或多个事件在 同一**时间间隔**内发生 | 能        |
| 并行  | 两个或多个事件在同一**时刻**真正同时发生 | 进程级不能    |

**核心结论**：单处理机上多道程序宏观上像同时运行，微观上任一时刻只有一个在执行，是**并发不是并行**。

**但是**：单处理机下 CPU 与 I/O 设备之间、多个 I/O 设备之间**可以真正并行**——这是硬件并行，容易被漏掉。进程级并行才需要多核/多处理机。

**记忆锚**：交替吃面包和写字＝并发；左手吃右手写＝并行。

**核心结论**：引入**进程**这一概念的核心目的之一就是支持程序的并发执行。

> [!note] 我的笔记
> 并发：假的并行，区别于真的并行

## KP7 共享的两种方式

| 方式   | 约束              | 例子              |
| ---- | --------------- | --------------- |
| 互斥共享 | 任一时间段内只允许一个进程访问 | 打印机、磁带机、栈、变量、表格 |
| 同时访问 | 宏观上同时，微观上可分时交替  | 磁盘只读文件、可重入代码    |

**核心结论**：==在一段时间内只允许一个进程访问的资源叫**临界资源**。==

**易错点**：「同时访问」的「同时」是逻辑上的，微观上可能是分时共享；只要最终效果对用户等同于连续访问就行。

## KP8 并发与共享互为前提

**核心结论**：==并发和共享==是 OS **两个最基本的特征**，互为存在前提。

1. 共享以并发为前提——单道程序系统无须考虑资源共享。
2. 并发以有效的共享机制为基础——无法协调资源访问，并发程序会因竞争冲突而无法正确运行。

**易错点**：==问「最基本的特征」答**并发与共享**两个，虚拟和异步是在此基础上的；四个一起问才是「基本特征：并发、共享、虚拟、异步」。==

## KP9 虚拟的两类复用技术

**核心结论**：虚拟＝把一个**物理实体**映射为多个逻辑上的**对应物**。

| 复用技术 | 实现           | 效果                    |
| ---- | ------------ | --------------------- |
| 时分复用 | 多道程序设计、时间片轮转 | 一个物理 CPU 逻辑上表现为多个处理单元 |
| 空分复用 | 虚拟存储器        | 有限物理内存扩展为更大的逻辑地址空间    |

虚拟设备技术（**SPOOLing**）：把独占型 I/O 设备（如打印机）转化为多台逻辑设备，每个用户仿佛独占一台，系统后台排队处理。

**核心结论（关键转化）**：SPOOLing 把原本要**互斥访问的临界资源，转化为可并发使用的共享资源**。

## KP10 异步性

**核心结论**：进程以==**不可预知的速度==断续推进**，这叫异步性。根源是系统资源有限，进程执行并非连续。

**易错点**：异步性会导致「与时间相关的错误」（如多进程并发改全局变量无同步保护），==但这不等于结果一定不可控==——**只要正确使用 OS 提供的同步机制，执行结果的正确性和可再现性是有保障的**。选项里说「异步性导致结果不可再现」要看有没有同步前提。

# 1.2 操作系统发展历程

## KP11 手工操作阶段：两个缺点

**核心结论**：程序和数据穿孔在纸带/卡片上，装入、执行、输出全靠人工。

两个缺点（成对记）：

1. **用户独占全机**——无资源竞争，但资源利用率极低。
2. **CPU 长时间空闲**——等人工完成 I/O，计算能力浪费。

**易错点**：「用户独占全机」听起来像优点，在这里是**缺点**。独占＝别人用不了＝利用率低。矛盾的本质是**人机速度不匹配**。

## KP12 脱机 I/O vs 联机 I/O

**核心结论**：引入**外围机**（小型专用计算机），在 CPU 不参与的情况下预先完成 I/O。

|        | 谁管 I/O               |
| ------ | -------------------- |
| 脱机 I/O | ==外围机独立完成==，脱离主机直接控制 |
| 联机 I/O | 主机直接管理 I/O 设备        |

数据流向：输入时外围机把纸带/卡片读入**磁带**，CPU 再从磁带调入内存；输出时 CPU 先写磁带，外围机再把磁带输出到外设。

两个优点：① 装带卸带传输在脱机状态完成，减少 CPU 空闲；② CPU 直接读写高速磁带，I/O 效率大幅提升。

**易错点**：判断脱机还是联机，看的是「**I/O 由谁控制**」，不是「设备是否连着主机」。「脱机」不等于「断网/关机」。

> [!note] 我的笔记
> 关键在于cpu是否干预了这次io，联机情况下cpu管理io所以只能处理io，而脱机情况下cpu就无需管理了，相当于找了一个代理来进行io，~~转而可以运行别的程序~~
> 
> 更正（2026-08-19 错题 01）：脱机只是让 CPU **少等**，这一阶段内存里仍然只有一道程序，空出来的时间没有第二个程序可用，CPU 还是闲着。「转而运行别的程序」是**多道程序设计**（KP14）的收益，别记到脱机头上。

## KP13 ==单道批处理系统==三大特征（真题）

**真题**：2016 考过批处理系统的特点。

**核心结论**：一批作业脱机输入到磁带，配一个**监督程序**（Monitor）控制作业自动顺序运行。

| 特征  | 含义                            |
| --- | ----------------------------- |
| 自动性 | ==作业自动连续执行==，无须人工干预           |
| 顺序性 | 按磁带上的顺序依次装入，先装入者先完成           |
| 单道性 | 内存中**仅一道**用户程序，完成或异常终止后才装入下一道 |

**易错点（关键区分）**：==作业是**成批提交**的，但内存里**始终只有一道**。「批处理」说的是提交方式，不是内存驻留数量。==

**局限**：正在运行的作业发起 I/O 请求时，CPU 只能空闲等待——这是引入多道程序设计的直接动因。

## KP14 多道批处理系统与多道程序设计（真题高频）

**真题**：2017、2022 考过多道批处理系统的特点。

**核心结论**：==作业先存**外存的后备队列**==，作业调度程序按算法选若干作业调入内存并发执行。某道程序因 I/O 暂停时，CPU 立即切换到另一就绪程序。==**该机制依赖中断技术**==。

多道程序设计三特点：

| 特点    | 含义                  |
| ----- | ------------------- |
| 多道    | 内存中同时驻留多道相互独立的程序    |
| ==宏观上并行== | 多道程序都在运行过程中，但都未全部完成 |
| ==微观上串行== | 各程序轮流占用 CPU，交替执行    |

需解决的四个关键问题：处理器分配策略、内存分配与保护、I/O 设备分配与调度、大量程序数据的组织存储与安全一致性。

**优点**：资源利用率高、系统吞吐量大。
==**缺点**：**缺乏交互能力**，用户无法了解运行状态或干预，响应时间长。==

**易错点**：「宏观上并行」用的是教材原话，但它实质是并发（单处理机下微观串行）。选择题里「宏观上并行、微观上串行」是标准表述要记住；但若问「单处理机多道程序是并发还是并行」，答**并发**。

> [!note] 我的笔记
> 缺乏能力引出分时操作系统和实时操作系统，两个具有交互能力的系统
> 
> 补（2026-08-19 错题 01/18）：多道程序设计才是**提高单机资源利用率的关键技术**——CPU 等 I/O 时切去跑别的程序，所以 CPU 和 I/O 设备**两边**的利用率都提高。代价是调度、切换、内存保护的开销比单道更大（2017 真题唯一错项就是「系统开销小」）。
> 
> 补：为什么 I/O 利用率也高——==利用率 = 设备工作时间 / 系统总时间==。
> 设备工作量没变（分子不变），但多道把 CPU 段和 I/O 段叠在一起，总耗时被压缩（分母变小），==所以空转占比下降==。
> 两道程序各需 CPU 20 + 打印 40：单道要 120ms（打印机利用率 33%），多道只要 80ms（50%）。
> 关键那一格是「CPU 跑 B 的计算 + 打印机输出 A 的数据」同时发生 —— 单 CPU 下的真并行。

## KP15 分时操作系统四大特征

**核心结论**：把处理器时间划分为很短的**时间片**，轮流分配给各用户程序。时间片内没算完就暂停、让出处理器，下一轮再继续。

| 特征       | 含义                      |
| -------- | ----------------------- |
| 同时性（多路性） | ==多个终端用户==同时使用同一台计算机    |
| 交互性      | 用户以==人机对话方式==直接控制程序运行   |
| 独立性      | 各用户操作互相隔离，==都感觉自己独占系统== |
| 及时性      | 请求能在较短时间内获得响应           |

**核心区别（必考）**：

|       | 目标                 |
| ----- | ------------------ |
| 多道批处理 | 高吞吐量、高资源利用率，无须人工干预 |
| 分时系统  | **人机交互**为核心        |

**易错点**：分时系统也是**基于多道程序设计**的，两者不是互斥技术路线，区别在设计目标。分时的「独立性」和 KP2 的「扩充机器」、KP9 的「虚拟」是一脉相承的——每个用户仿佛独占一台机器。

## KP16 实时操作系统：硬实时 vs 软实时

**核心结论**：**摒弃时间片轮转**，==改用基于任务**紧迫性/截止时间**的调度策略==。

| 类型  | 时限要求               | 例子            |
| --- | ------------------ | ------------- |
| 硬实时 | 必须在截止时间前完成，否则灾难性后果 | 飞机控制系统、导弹制导系统 |
| 软实时 | 允许偶尔错过，只要不造成永久损害   | 飞机订票系统、银行管理系统 |

三个特点：==**确定性**（响应时间可预测）==、==高可靠性、强时效性==。

**易错点**：实时系统的核心指标是**及时性和可靠性**，不是吞吐量和资源利用率。别把「实时」理解成「快」——关键是**可预测、有保障的时限**，一个响应慢但时限确定的系统也是实时系统。

**易错点**：分时系统有「及时性」，实时系统也讲及时——但分时的及时是「让用户感觉不到等待」，实时的及时是「错过就出事」，严格程度完全不同。

## KP17 网络操作系统 vs 分布式操作系统

**核心结论**：

|      | 网络 OS           | 分布式 OS                       |
| ---- | --------------- | ---------------------------- |
| 节点关系 | 各计算机独立运行        | 节点**地位对等**，无固定主从             |
| 资源访问 | 需**显式指定**远程资源位置 | 用户**透明地**共享                  |
| 任务   | 只做资源共享与通信       | 一个任务分解为多个子任务，分布到不同节点**并行执行** |
| 用户视图 | 无统一全局视图         | **单一系统映像**                   |

分布式 OS 三特点：分布性、并行性、**透明性**（最关键——用户无须感知底层多机结构）。

**易错点**：判据是**透明性**。要用户自己写明「去哪台机器取文件」的是网络 OS；用户不知道也不用管文件在哪台机器上的是分布式 OS。

## KP18 微机操作系统三类（真题）

**真题**：2018 考过多任务操作系统的特点。

| 类型     | 能力                       | 代表                             |
| ------ | ------------------------ | ------------------------------ |
| 单用户单任务 | 一个用户跑一个程序                | MS-DOS（16 位）                   |
| 单用户多任务 | 一个用户同时跑多个程序，靠**时间片轮转**切换 | Windows XP 及之后、macOS、Linux 桌面版 |
| 多用户多任务 | 多用户同时登录，各自并发多任务          | UNIX、Linux 服务器版、Windows Server |

**易错点**：分类的两个维度是**用户数**和**任务数**，别混。Windows XP 是单用户多任务——虽然能建多个账户，但同一时刻只支持一个用户登录使用。

此外还有嵌入式 OS、服务器 OS、智能手机 OS。

# 1.3 操作系统的运行环境

## KP19 内核：装了什么、为什么这么装

**核心结论**：内核＝==**紧靠硬件、常驻内存**的核心组件==。放进内核的三类模块：

1. 与==硬件紧密相关的==（中断处理程序、设备驱动程序）
2. ==运行频率高的==（时钟管理、进程调度）
3. 各模块共用的基础操作

==两个设计目的：① **保护**核心模块不被应用程序破坏；② **提升运行效率**。==

内核两类功能：

| 类别     | 内容              |
| ------ | --------------- |
| 支撑功能   | 时钟管理、中断机制、原语    |
| 资源管理功能 | 进程管理、存储器管理、设备管理 |

**易错点**：==内核**常驻内存**，不参与换出==。「不同 OS 内核功能有差异」是教材原话，别背成有统一标准。

> [!note] 我的笔记
> 中断处理程序、设备驱动程序都存在内核里，属于操作系统程序

## KP20 时钟管理（真题）

**真题**：2018 考过时钟中断服务的内容。

**核心结论**：时钟两大功能——**计时** + **产生定时中断**。

## KP21 中断机制（真题）

**真题**：2016 考过中断机制在多道程序设计中的作用。

**核心结论**：中断是现代 OS 运行的基础，它让 CPU 在 I/O 期间**能去执行其他指令**，从而提高资源利用率。

中断发生时内核做三件事：==**保存现场 → 转交对应处理程序 → 恢复现场**。==

中断来源很广：键盘输入、鼠标事件、系统调用、设备驱动、文件访问。

**易错点**：中断机制的作用是「==提升**并发**处理能力==」。追到根上：==没有中断，CPU 就没法在 I/O 等待时切走，多道程序设计（KP14）也就无从实现。==

## KP22 原语

**核心结论**：原语＝若干条指令组成的、完成特定功能的操作，特征是**原子性**——执行过程**不可被中断**，必须一气呵成。

| 属性       | 说明             |
| -------- | -------------- |
| 运行态      | ==内核态==        |
| 执行时间     | 短，调用频繁         |
| 实现原子性的手段 | ==**关中断**==    |
| 常见例子     | 进程切换、进程同步、资源分配 |

**易错点**：==「原语靠关中断实现原子性」是标准答法。==关中断本身是**特权指令**（KP24），所以原语只能在内核态跑——这两条互相印证。

## KP23 用户态与内核态、模式位（真题超高频）

**真题**：2011、2012、2014、2021 反复考「两种模式下发生或执行的事件分析」。

**核心结论**：硬件用一个**模式位**标识当前模式。

| 模式 | 别名 | 模式位 |
| --- | --- | --- |
| 内核态 | 管态、系统态 | ==0== |
| 用户态 | 目态 | ==1== |

切换的完整链条：

1. 系统引导时硬件**从内核态开始**工作
2. 加载完 OS 后切到用户态执行用户程序
3. 发生中断或陷阱 → **硬件自动**置模式位 0，进内核态
4. OS 交还控制权前 → 置模式位 1，回用户态

**易错点（这是考点核心）**：==两个方向**不对称**——用户态→内核态由**硬件自动**完成（用户程序无法自己切）；内核态→用户态由**内核主动执行返回指令**（如 IRET）完成，该操作在内核态执行。==

**易错点**：「==OS 一旦获得控制权就处于内核态==」——反过来说，==只要在跑用户程序就是用户态。==

## KP24 特权指令 vs 非特权指令（真题）

**真题**：2022 考过特权指令和非特权指令的特点。

|         | 特权指令                        | 非特权指令     |
| ------- | --------------------------- | --------- |
| 可执行模式   | ==仅内核态==                    | 任意模式      |
| 可访问地址空间 | ==全部（用户空间 + 系统空间）==         | 仅用户地址空间   |
| 典型操作    | 启动外设、设置系统时钟、关中断、修改模式位、返回用户态 | 一般计算和数据处理 |

**核心结论**：用户程序试图执行特权指令 → 硬件产生**非法指令异常** → OS 捕获后**终止该程序并重新调度**。

**易错点**：注意「修改模式位」本身就是特权指令——==这就堵死了用户程序自行提权的路==，和 KP23 的「硬件强制」闭环。

**易错点**：非特权指令不是「不能在内核态执行」，是**两种模式都能执行**。别答成互斥。

> [!note] 我的笔记
> 用户要请求OS服务必须使用系统调用，不能手动修改至管态

## KP25 「门」：进内核态的唯一合法途径（真题）

**真题**：2013、2015 考过用户态切换到内核态的事件分析。

**核心结论**：内核里设有若干受控入口称为「**门**」，用户程序进入内核态的==**唯一合法途径就是中断或异常**==。

==机制由**硬件强制保障**，确保切换的**安全性与原子性**。==

**核心结论（背下来）**：常见用户态→内核态的四种情形：

1. 用户程序请求 OS 服务（==**系统调用**==）
2. 发生==**外中断**==（I/O 完成、时钟信号）
3. 用户程序产生==**异常**==（除零、缺页）
4. 用户程序试图执行==**特权指令**==，触发异常

**易错点**：这四条里只有**系统调用是主动的**，另外三条都是被动的。而系统调用底层靠陷入指令，本质仍是异常——所以「唯一途径是中断或异常」和「四种情形」不矛盾。

## KP27 中断和异常的分类（真题）

**真题**：2016 考过中断和异常的分类。

**外中断**两类：

| 类型     | 引脚       | 说明                |
| ------ | -------- | ----------------- |
| 可屏蔽中断  | ==INTR== | 改屏蔽字可实现多重中断，处理更灵活 |
| 不可屏蔽中断 | ==NMI==  | 紧急硬件故障，如电源掉电      |

**异常**三类：

| 类型          | 含义                         | 例子                  |
| ----------- | -------------------------- | ------------------- |
| 故障 Fault    | 指令执行引起的异常                  | 非法操作码、缺页、除数为 0、运算溢出 |
| 自陷 Trap（陷入） | **事先安排**的「异常」事件，用于用户态调内核程序 | 条件陷阱指令、==系统调用指令==   |
| 终止 Abort    | CPU **无法继续执行**的硬件故障        | 控制器出错、存储器校验错        |

**核心结论（易混必背）**：

| 归类          | 成员           |
| ----------- | ------------ |
| 软件中断（程序性异常） | ==故障 + 自陷==  |
| 硬件中断        | ==终止 + 外中断== |

**易错点**：==**终止属于异常，但归到硬件中断**==——这条最容易错。别按「异常＝软件、中断＝硬件」一刀切。

**易错点**：自陷是**程序员事先安排**的，不是意外，所以系统调用可预期、可复现。

## KP28 中断和异常的处理过程：返回地址差异（真题高频）

**真题**：2015、2020、2024 考过中断和异常的处理过程。

**核心结论**：CPU 执行用户程序第 i 条指令时，

| 情形 | 检测时机 | 处理完后返回 |
| --- | --- | --- |
| 异常 | 该指令**执行过程中**引发（缺页、除零） | ==返回第 i 条指令**重新执行**== |
| 中断 | 该指令**执行结束后**检测到请求信号 | ==返回第 $i+1$ 条指令继续执行== |

若处理程序判定为不可恢复的致命错误 → **终止该用户程序**。

具体处理由**操作系统（及设备驱动程序）完成。

**易错点（几乎年年考）**：==返回地址不同的根源是「指令有没有做完」——异常时第 i 条**没成功**（缺页处理完要重访原地址），中断时第 i 条**已经做完**了。==

## KP29 中断处理 vs 子程序调用：六点区别（真题）

**真题**：2012 考过中断处理和子程序调用的比较。

| 维度        | 中断处理                           | 子程序调用                  |
| --------- | ------------------------------ | ---------------------- |
| ① 程序关系    | 与被中断程序**相互独立**，无固定关联           | 与主程序属同一程序，**主从关系**     |
| ② 产生时机    | 通常**随机**                       | CALL 指令显式触发，程序员事先安排    |
| ③ 实现方式    | ==需**硬件电路**支持==                | ==完全由**软件**实现==        |
| ④ 入口地址来源  | ==**中断向量表**直接提供==              | CALL 指令的**地址码**指定      |
| ⑤ PC 保护方式 | 都要保护 PC，但由==**硬件**在中断响应中自动保存== | 由 ==CALL 指令执行时**压栈**== |
| ⑥ 优先级裁决   | 多个请求同时到达要**优先级裁决**             | 无此操作                   |

**易错点**：⑤ 的考法是「两者都需要保护 PC 吗」——**都需要**，区别只在**谁来做**。答「子程序调用不保护 PC」是错的。

> [!note] 我的笔记
> **PSW 是中断处理独有的，子程序调用不用保存。** 原因：中断要改 CPU 状态（置模式位 0、可能关中断），原 PSW 不先存就永久丢了；子程序调用前后特权级和中断允许位都不变，PSW 没被动过，自然不用存。
> 
> 所以 2012 真题问「中断一定保存、而子程序调用不需要保存的是」，答 **PSW**。**PC 是两者都要保存的**，区别只在谁来做（硬件 vs CALL 压栈），别选成 PC。

> [!question] 我的问题
> 中断向量表由谁提供？储存在哪里？

## KP30 系统调用的定义与五类功能（真题高频）

**真题**：2019、2021、2024 考过系统调用的定义、功能及性质。

**核心结论**：系统调用是 OS 提供给应用程序（程序员）使用的接口，==可视为一种**特殊的公共子程序调用**==。==凡涉及**共享资源**的操作都必须通过系统调用==，由 OS 代为完成再返回结果。

五类功能（==记「设文进通内」==）：

| 类别 | 内容 |
| --- | --- |
| 设备管理 | 设备的请求、释放、启动 |
| 文件管理 | 文件的读、写、创建、删除 |
| 进程控制 | 进程的创建、撤销、阻塞、唤醒 |
| 进程通信 | 进程间消息传递、信号传递 |
| 内存管理 | 内存分配、回收，获取作业占用内存区的大小和起始地址 |

一个 OS 有几十到上百条系统调用，==每个都有**唯一的系统调用号**==。必须由**内核程序在内核态**完成。

**易错点**：判据是「==**是否涉及共享资源**==」。`strlen`、`sqrt` 纯计算不需要系统调用；打开文件、申请内存必须走。呼应 KP5。

## KP31 系统调用 vs 普通过程调用：四点区别

**核心结论**：系统调用本质是一种特殊的过程调用，但有四点显著差异。

| 维度     | 系统调用                           | 普通过程调用       |
| ------ | ------------------------------ | ------------ |
| 运行状态   | 调用者**用户态**，被调用者**内核态**         | ==两者同一特权级==  |
| 状态转换   | 需==**陷入指令（Trap）**==触发，先切内核态再分派 | 无须特权级切换，直接跳转 |
| 返回机制   | ==内核可能按调度策略决定**是否切换进程**==      | 总是直接返回原调用点   |
| 嵌套深度限制 | 受==**内核栈**==空间限制               | 受**用户栈**大小约束 |

**易错点**：返回机制这条最容易漏——系统调用返回后，==**不保证还是原进程在跑**==。这也是「系统调用可能引起进程调度」的依据。

> [!note] 我的笔记
> **每个进程有自己的内核栈**，不是全系统共用一个。进程在用户态用用户栈，陷入内核后**硬件自动切换**到它自己的内核栈。
> 
> 为什么不沿用用户栈：① 用户栈指针由用户程序控制，可能非法或被恶意构造，内核不能把返回地址交给它保管；② 用户栈那一页可能已被换出，压栈会再触发缺页。内核栈在内核空间、常驻内存，没这两个问题。
> 
> 内核栈通常只有 8KB / 16KB 且**不可增长**（用户栈可自动扩展）——这就是上面「嵌套深度受内核栈限制」的实质，内核代码不能深递归、不能在栈上开大数组。

## KP32 系统调用的处理过程：四阶段（真题高频）

**真题**：2012、2017、2022、2023 考过系统调用的处理过程及相关分析。

| 阶段          | 做什么                                                          |
| ----------- | ------------------------------------------------------------ |
| ① 传递参数      | 用户程序将**系统调用号 + 参数**压入堆栈（或通过寄存器）                              |
| ② 执行陷入指令并切换 | 陷入指令触发 CPU 从用户态切内核态；硬件与内核协同保存现场，将 ==PC、PSW、通用寄存器压入**内核堆栈**== |
| ③ 定位并执行服务程序 | 内核按系统调用号查==**系统调用表**==，找到入口地址，执行服务逻辑                         |
| ④ 恢复现场并返回   | 恢复 CPU 现场，模式位切回用户态，从断点继续执行                                   |

教材图示：[[王道教材/27 王道操作系统/pictures/fig-1-4-system-call.jpg]]（图 1.4 系统调用的执行过程）

**易错点（三个都常考）**：

1. ==**陷入指令本身在用户态执行**==，它是「引起切换的指令」，**不是特权指令**。
2. 现场压入的是==**内核堆栈**==，不是用户栈。
3. 查的是==**系统调用表**（按系统调用号索引）==，不是中断向量表。

> [!note] 我的笔记
> **硬件 / OS 分工判据：这件事有没有对应的程序代码。**
> 
> 没有代码、纯电路动作 → **硬件**：保存 PC 和 PSW、置模式位为 0、按中断号查中断向量表取入口地址。这些发生在**中断周期**，由「**中断隐指令**」完成——它不是指令系统里的指令，程序里写不出来。关中断也在这一步，硬件自动清 PSW 的中断允许位（后续要开关中断则用 STI/CLI 这类特权指令，属内核代码）。
> 
> 有代码 → **OS**：保存通用寄存器（PUSHA 之类，必须由指令完成）、保存中断屏蔽字、执行中断服务例程 / 系统调用服务例程、开机时初始化中断向量表。
> 
> 注意「由 OS 完成」≠「不由 CPU 执行」。所有指令都跑在 CPU 上，题目问的是**这段活由谁的代码负责**，不是问谁通电。
> 
> 真题对照：2020 答 II III IV｜2022 答 II III｜2015 答通用寄存器。

> [!question] 我的问题
> 硬件与内核协同保存现场，将 ==PC、PSW、通用寄存器压入内核堆栈== ，哪些是由硬件保存的？哪些是由内核程序保存的？开关中断又是由什么来操作的？
>

## KP33 运行环境总图（本节收口）

**核心结论**：一句话概括 OS 的运行环境——

> 用户程序运行在受限的**用户态**，通过**系统调用（主动）**或**异常/中断（被动）**两种受控途径进入**内核态**，请求内核提供资源管理与服务；内核处理完毕后，再安全返回用户态继续执行。

这种**用户态与内核态的隔离**，构成现代 OS 安全、高效运行的基础环境。

OS 课关注**软件实现与切换机制**，硬件支持细节归计组的中断与异常部分。

**易错点**：进内核靠中断/异常（硬件自动），回用户态靠内核执行 ==IRET== 等返回指令（在内核态执行）。方向不同、机制不同，别答成同一套。

# 1.4 操作系统结构

## KP34 分层法

**核心结论**：层 0 是**硬件**，层 N 是**用户接口**。各层==**只能调用紧邻下层**==提供的功能与服务（**单向依赖**）。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-1-5-layered-os.jpg]]（图 1.5 分层的操作系统）

|     | 内容                                               |
| --- | ------------------------------------------------ |
| 优点① | ==**便于调试与验证**，自底向上逐层开发测试；某层出错能定位在该层内部（下层都已验证过）== |
| 优点② | ==**易于扩充与维护**，层间接口不变时可独立改/换/增某一层==               |
| 缺点① | ==**层次划分困难**，依赖关系一旦固化就缺乏灵活性==                    |
| 缺点② | ==**效率较低**，高层功能要穿越多个中间层，每层的参数传递与控制转移都有开销==       |

**易错点**：注意是「只能调用**紧邻**下层」，不是「可以调用任意下层」。这个严格单向依赖既是它可验证的原因，也是它慢的原因——一条链上的两个性质，别只记一半。

## KP35 模块化：内聚与耦合

**核心结论**：按功能划分为若干具有一定独立性的模块，明确定义模块间**接口**，模块可再分子模块——==这叫**模块-接口法**。==

教材图示：[[王道教材/27 王道操作系统/pictures/fig-1-6-modular-os.jpg]]（图 1.6 模块化操作系统结构）

衡量模块独立性的两个标准：

| 标准  | 含义                 | 越好的方向        |
| --- | ------------------ | ------------ |
| 内聚性 | 模块**内部**各部分联系的紧密程度 | ==越**高**越好== |
| 耦合度 | 模块**之间**相互依赖和影响的程度 | ==越**低**越好== |

模块粒度要权衡：==模块过小 → 模块间交互频繁，整体复杂度反而上升；模块过大 → 内部结构复杂，难维护。==

|     | 内容                                                |
| --- | ------------------------------------------------- |
| 优点  | ① 提高正确性、可理解性、可维护性；② 增强可适应性，便于扩展；③ 支持**并行开发**，加速研制 |
| 缺点① | ==模块间的**接口规定很难满足实际需求**==                          |
| 缺点② | 各模块设计者齐头并进，决定无法建立在已验证的正确决定之上，==**找不到可靠的决定顺序**==   |

**易错点**：模块化和分层法的优缺点正好互补——分层法「有可靠的决定顺序但慢」，模块化「能并行开发但没有可靠的决定顺序」。成对记，选择题里常拿一个的缺点安到另一个头上。

## KP36 宏内核 vs 微内核（架构分野）

**核心结论**：从**内核架构**划分，分宏内核和微内核。

|           | 宏内核（单内核/大内核）         | 微内核                     |
| --------- | -------------------- | ----------------------- |
| 内核里放什么    | 主要功能模块**全部**集成在内核态   | ==仅最基本功能（进程调度、进程间通信等）== |
| 文件系统、设备驱动 | 在**内核态**             | ==移到**用户态**运行==         |
| 地址空间      | 各模块**共享**，可直接调用彼此函数  | 服务器各自独立，靠**消息传递**       |
| 性能        | ==高==（少上下文切换和消息传递开销） | 低（多次穿越用户态/内核态）          |
| 一个模块崩溃    | ==整个系统崩溃==           | ==仅该服务崩溃，可重启恢复==        |

宏内核的问题：服务日益复杂 → 代码规模急剧膨胀 → 维护困难、可靠性下降，即典型的「**软件危机**」。这是微内核出现的动因。

现状（记结论就行）：

| 架构                     | 代表                                   |
| ---------------------- | ------------------------------------ |
| 宏内核 / 混合内核             | Linux、Windows、Android                |
| 混合（Mach 微内核 + BSD 宏内核） | macOS、iOS 的 **XNU** 内核               |
| 微内核                    | 谷歌 **Fuchsia**、华为 **HarmonyOS NEXT** |

**易错点**：==宏内核与微内核**不是对立**关系，是相互借鉴融合==。「主流 OS 都是微内核」是错的，主流是宏内核或混合内核。

## KP37 微内核的组成与「机制与策略分离」

**核心结论**：微内核结构＝**微内核 + 多个服务器**。微内核只实现最核心机制，通常包括：

1. 与硬件紧密相关的部分
2. 基本的资源管理机制
3. **客户与服务器间的通信支持**

绝大部分功能放在微内核外的一组 **服务器（进程）** 里，运行在**用户态**（进程/线程服务器、虚拟存储器服务器等）。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-1-7-microkernel-client-server.jpg]]（图 1.7 单机环境下的客户/服务器模式）

**设计原则：==机制与策略分离==** —— 机制留在微内核，策略交给用户态服务器。

| 功能      | 微内核负责（机制）                   | 用户态服务器负责（策略）  |
| ------- | --------------------------- | ------------- |
| 进程/线程管理 | 创建、切换、调度队列管理                | 进程分类、优先级分配    |
| 低级存储器管理 | 与硬件相关的地址转换（页表管理、逻辑→物理映射）    | 页面置换算法、内存分配策略 |
| 中断和陷入处理 | ==捕获中断/陷入，识别类型后**分发**给服务器== | 具体处理逻辑        |

**核心结论**：==**只有微内核运行在内核态**==，其余模块全在用户态——这是它高可靠的根本原因。

**易错点**：微内核里管的是「**低级**存储器管理」——==页表映射这种硬件相关的机制在内核==，置换算法这种策略在外面。==问「页面置换算法在微内核里吗」答**不在**。==

**易错点**：中断的**捕获与分发**属于微内核核心功能，不能移出去——因为它与硬件紧密相关。

> 本质就是微内核负责比较抽象的东西，然后用户态服务器负责比较具体的东西，比如使用什么算法

## KP38 微内核的优缺点（真题）

**真题**：2023 考过微内核操作系统的特点。

四个优点（记「扩可移分」）：

| 优点      | 原因                           |
| ------- | ---------------------------- |
| 扩展性和灵活性 | 增/改功能只调整对应服务器，==**无须改动内核**== |
| 可靠性和安全性 | 用户态服务故障不导致系统崩溃，且**攻击面更小**    |
| 可移植性    | ==仅微内核含硬件相关代码==，其余服务器与平台无关   |
| 分布式计算   | 客户/服务器靠**消息传递**通信，易扩展到网络环境   |

**核心结论（缺点只有一条）**：==**性能问题**——每次服务请求要**多次穿越内核态与用户态**，系统调用延迟增加。==

缓解办法：**混合内核**——把高频服务移进内核，但==代价是微内核容量明显增大==。

应用领域：对可靠性要求极高的关键任务领域——实时操作系统、工业控制、航空航天、军事。

**易错点**：==可移植性好==的原因要说准：不是「代码少」，==是「硬件相关代码集中在微内核一处」==。

**易错点**：微内核的性能损失来自==**态切换和消息传递**==，不是来自「内核太小算不快」。

## KP39 外核 exokernel

**核心结论**：外核的思路和传统 OS 相反——==传统 OS 用**抽象层**提供统一接口；外核把**物理资源直接暴露**给用户级系统，自己只负责资源的**安全分配与隔离**==。

工作方式：外核是运行在**内核态的极小程序**，把底层硬件资源（磁盘块、内存页、网络包缓冲区）划分成==**互不重叠**==的子集分给各用户级系统（如一个拿磁盘 0～1023 块，另一个拿 1024～2047 块），并通过**权限检查**防止越权。

外核之上，用户空间构建**库操作系统（library OS）**，自主实现文件系统、进程调度、虚拟内存管理。

三个优点：

| 优点        | 说明                                             |
| --------- | ---------------------------------------------- |
| 减少抽象开销    | 不强制引入虚拟内存、虚拟文件系统等映射层，==避免不必要的数据拷贝、地址转换、上下文切换== |
| 提升灵活性与性能  | 用户级系统按应用特性优化策略（如数据库直接管理磁盘块）                    |
| 清晰分离保护与实现 | ==外核**只管保护**，功能实现全在用户空间==，易于验证                 |

**易错点**：外核和微内核容易混。==微内核仍然**提供抽象**（只是把服务搬到用户态）；外核**取消抽象**，直接给物理资源。== 一句话判据：微内核搬家，外核拆墙。

# 1.5 操作系统引导

## ==KP40 引导过程七步（真题高频）==

**真题**：2021、2022 考过操作系统的引导过程；2013 考过操作系统运行的存储器。

**核心结论**：OS 以程序形式存储在**硬盘等外存**中，引导是一个==**链式**过程==：定位启动设备 → 确定可引导分区 → 加载内核 → 完成启动。

| 步   | 谁在做      | 做什么                                                                     |
| --- | -------- | ----------------------------------------------------------------------- |
| ①   | CPU      | 通电后从 ==**ROM**== 中读取并执行 **BIOS**；BIOS 初始化基本硬件，**建立中断向量表**               |
| ②   | BIOS     | 通电自检 **POST**（查 CPU、内存、外设）；按 ==**CMOS**== 设置确定启动设备优先级，选首个有效启动设备         |
| ③   | BIOS     | 把启动设备的**首扇区**即 ==**MBR**（主引导记录）== 加载到内存。MBR = **引导代码 + 硬盘分区表**          |
| ④   | MBR 引导代码 | 解析分区表，找到标记为「**活动**」的分区，把它的首扇区即 ==**PBR**（分区引导记录）== 加载到内存                |
| ⑤   | PBR 代码   | 加载活动分区内的**启动管理器**（Linux 的 **GRUB**、Windows 的 **Bootmgr**），提供多系统/多内核选择界面 |
| ⑥   | 启动管理器    | 把选定的**内核映象**加载到内存并跳转执行。==内核接管控制权，**重建中断处理机制，不再依赖 BIOS**==               |
| ⑦   | 内核       | 初始化核心子系统，然后启动**首个用户态进程**（Linux 的 **init**）                              |

第 ⑦ 步内核初始化的三块（对应四大管理，容易考细节）：

| 模块   | 建了什么                         |
| ---- | ---------------------------- |
| 内存管理 | 内核页表、用户进程地址空间框架              |
| 进程调度 | **PCB 链表**、**就绪队列**、**阻塞队列** |
| 设备驱动 | 设备控制块、设备分配表、**I/O 缓冲区**管理结构  |

**易错点（2013 那道的核心）**：==BIOS 在 **ROM** 里，操作系统在**硬盘**里，运行时被装入**内存**。== 问「OS 存放在哪」答硬盘/外存，问「OS 运行时在哪」答内存，别混。

**易错点**：==中断向量表**建了两次**——BIOS 先建一份供引导阶段用，内核接管后**重建**自己的一套。== 「内核启动后仍靠 BIOS 提供服务」是错的。

**易错点**：MBR 是**整个磁盘**的首扇区，PBR 是**活动分区**的首扇区，顺序是 MBR → 分区表 → 活动分区 → PBR。别把两者说反。

# 1.6 虚拟机

## KP41 虚拟机与两类管理程序（真题）

**真题**：2025 考过虚拟化技术的原理与特点。

**核心结论**：虚拟机＝把一台物理计算机抽象为多台**逻辑上独立**的计算环境，每台都是==**完整硬件系统的精确复制品**==。核心在于**隐藏底层物理硬件细节**，向上提供统一且隔离的执行平台。

教材图示：[[王道教材/27 王道操作系统/pictures/fig-1-8-virtual-machine.jpg]]（图 1.8 两类虚拟机管理程序在系统中的位置）

|      | 第一类（==裸金属架构==）          | 第二类（==寄居架构==）                            |
| ---- | ----------------------- | ---------------------------------------- |
| 运行位置 | ==**直接运行在物理硬件之上**==     | 作为**应用程序**跑在**宿主操作系统**上                  |
| 特权级  | 系统中==**唯一处于最高特权级**==的软件 | 本质是一个==**用户态进程**==                       |
| 资源管理 | 自己管硬件资源、调度多个虚拟机         | ==依赖宿主 OS 做资源分配与调度==                     |
| 类比   | 类似一个轻量级操作系统             | 向客户 OS **伪装**成完整硬件平台                     |
| 代表   | —                       | ==**VMware Workstation**==（x86 上首个广泛使用的） |

第二类的细节：首次启动时模拟一台新计算机，客户 OS 装进**虚拟磁盘**——==实际上就是宿主 OS 里的一个**普通文件**==。

应用：Web 主机 / 云服务器。没有虚拟化时只能二选一——**共享托管**（用户无法控制软件环境）或**独占托管**（成本高昂）；虚拟化让单台物理服务器跑多个虚拟机，每个对用户都是一台完整服务器，可自定义 OS 与软件且成本低。这是==当前主流云服务器服务的基础==。

**易错点**：判据是**下面压着谁**——第一类下面是硬件，第二类下面是宿主 OS。「第二类管理程序运行在内核态」是错的，它就是个用户态进程。

## KP42 虚拟内核态与敏感指令

**核心结论**：在第一类架构中，

| 谁            | 跑在哪个态                               |
| ------------ | ----------------------------------- |
| 客户操作系统       | ==**虚拟内核态**——它**以为**自己在真实内核态，实际不是== |
| 客户 OS 上的用户进程 | ==**真实的用户态**==                      |

客户 OS 执行一条仅允许在**真实内核态**执行的**敏感指令**时 → ==触发**异常**并**陷入虚拟机管理程序**==。

管理程序怎么处理，==取决于 CPU 支不支持硬件虚拟化：==

| CPU     | 行为                                                                                       |
| ------- | ---------------------------------------------------------------------------------------- |
| 支持硬件虚拟化 | 按执行上下文判断指令来自客户 OS 还是用户程序：来自客户 OS → ==**代为完成其功能**==；来自用户程序（非法执行敏感指令）→ ==**模拟真实硬件的异常响应**== |
| 早期不支持   | ==**所有**敏感指令都被**透明重定向**到管理程序，由其**软件模拟**==                                                |

**易错点**：客户 OS 的用户进程跑在**真实用户态**，只有客户 OS 自己在「虚拟」内核态。别以为整台虚拟机都跑在虚拟态里。

**易错点**：==「陷入虚拟机管理程序」用的还是 KP25/KP27 那套机制——敏感指令触发异常。== 虚拟化不是新机制，是把双重模式的陷入机制又套了一层。
